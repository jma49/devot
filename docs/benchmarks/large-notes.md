# Large-note storage and sync benchmark

Run `node scripts/bench/large-notes.ts` or `pnpm bench:large` from the repository root.
`--quick` takes five runs instead of thirty; `--out file` changes the JSON destination from `docs/benchmarks/large-notes.json`.
The launcher runs the opt-in Vitest harness so the existing SQLite adapter's Vite migration imports and test lifecycle work unchanged.
It uses a real temporary SQLite file, `createNoteService`, `fromWire(toWire(store))`, Yjs editor updates and flush, and the real sync engine with the same JSON/base64 copies as `sync-push.bench.test.ts`.
Every size gets an untimed warmup, then fresh-service-cache opens, a one-line edit, a roughly 10 KB Markdown paste, first and warm searches after each save, and a forced sync push after each edit.
The note is reset outside timing after every run, so its text does not grow across runs; Yjs edit history does grow as in an editing session.
Search and sync report sixty observations in a full run, the other paths thirty.
The injected sync clock advances a minute per run to avoid the repeated-push circuit breaker; durations use the real wall clock.
Cold means the core's memory cache is empty, not that OS or SQLite caches are empty.
The actual generated byte lengths are recorded alongside the requested sizes.

The relay is the actual Worker entry bundled with esbuild and hosted by Miniflare, with SQLite Durable Objects and a real loopback WebSocket.
Its measurements include client framing/copies and loopback transport as well as server processing, not isolated Worker CPU time.
The relay stores an unencrypted record of the same size except for cipher overhead.
**The client sync measurement excludes encryption: production AES-256-GCM runs in Rust (`src-tauri/src/sync/record.rs`), which this Node/Vitest harness does not execute.**
It also excludes Rust IPC scheduling and all renderer work.
Consequently this is not yet an end-to-end encrypted sync benchmark.

## Machine

The committed `large-notes.json` is the schema v32 run on a Linux cloud VM: Intel Xeon, 8 cores, 31 GB, Linux 6.8 (AWS), Node 24.22, load average 0.33 at the start (its `machine` field).
Numbers are not comparable across machines; compare runs only on the same quiet machine.
Its `commit` ends in `+dirty` because the migration was measured before committing it.

Rust and TypeScript tests check MATCH, `fts5vocab` and raw database bytes after purge, including stale text in the TypeScript test.

### Migration cost

`DEVOT_FTS_MIGRATION_BENCH=1 pnpm exec vitest run --project slow tests/core/fts-contentless-migration.bench.test.ts --silent=false` measures five fresh file-backed v31 stores per fixture, WAL and synchronous FULL, including the v32 rebuild, v33 history bookkeeping and commit but excluding fixture setup and post-migration optimization/vacuum.
The typical notes use deterministic short `libraryBody` fixtures; the large note uses `sampleNote(5_000_000)` (5,149,729 bytes).
Index sizes sum FTS shadow-table pages through `dbstat`, with optimized indexes before and after and vacuum after; all five runs returned identical sizes.

| Library              | Migration p50 / p95 (ms) | Sampled peak RSS delta p50 / p95 (KiB) | Before index bytes | After index bytes |       Difference |
| -------------------- | -----------------------: | -------------------------------------: | -----------------: | ----------------: | ---------------: |
| 1,000 typical notes  |            6.240 / 7.535 |                                  0 / 0 |            438,272 |           438,272 |                0 |
| 10,000 typical notes |          66.666 / 74.508 |                             640 / 1152 |          4,165,632 |         4,177,920 | +12,288 (+0.30%) |
| One 5 MB note        |        179.735 / 187.616 |                             128 / 5248 |          9,482,240 |         9,482,240 |                0 |

These are clean-index sizes, not a bound on tombstones accumulated between merges or on peak migration disk/WAL space.
An already-running worker thread samples whole-process RSS every 1 ms while the main thread executes synchronous SQLite; delta is relative to RSS immediately before migration, includes a final sample, and excludes worker startup.
This is sampled resident growth, not SQLite allocation high-water or total app memory; zero means existing resident pages sufficed, not zero allocations, and sub-millisecond peaks can be missed.
The 10,000-note p95 stays well below one second, so rebuilding stays inside the migration.
The normal first-launch main window is built only after migration: `tauri.conf.json:18` disables automatic window creation, `lib.rs:498` opens the store before `lib.rs:653` builds the window, and `storage/db.rs:187–197` waits for `Store::open` to finish before returning.
`storage/open.rs:141–143` runs migrations and pending purge recovery before that return; `main_windows.rs:286` constructs the window afterward, with no migration progress window in this path.

### Purge cost

`DEVOT_FTS_PURGE_BENCH=1 pnpm exec vitest run --project slow tests/core/fts-purge-cost.bench.test.ts --silent=false` measures 20 fresh file-backed stores per case after two warmups, WAL and synchronous FULL.
Every sample copies a closed, fully indexed and optimized seed database outside timing; fixture setup, database opening, cloning and correctness checks are excluded.
The libraries contain 10,000 deterministic short `libraryBody` notes, or one `sampleNote(5_000_000)` plus one retained typical note.
The large-note case purges the 5 MB note itself.
There are no attachments or pending index changes in these fixtures; purge cost with a stale backlog or attachments is not measured here.
Timing includes the real note service's `purge` or `emptyTrash` call, including storage transactions and, for Empty Trash, listing the 100 trashed notes.
The benchmark is opt-in and uses the identical fixture and service path on base `bf53e90d`, initial contentless-delete commit `a0c6f70e`, and the batched implementation.

Milliseconds, **p50 / p95**:

| Case                              | Base external-content | Initial contentless-delete | Batched contentless-delete |
| --------------------------------- | --------------------: | -------------------------: | -------------------------: |
| One note in a 10,000-note library |         2.783 / 3.780 |            65.844 / 96.947 |            53.155 / 57.732 |
| Purge the 5 MB note               |     198.613 / 257.232 |            75.137 / 90.566 |            54.951 / 58.472 |
| Empty Trash: 100 of 10,000 notes  |     177.947 / 287.230 |        4497.734 / 5476.375 |          134.566 / 137.964 |

The original `emptyTrash` loop called `purgeNote` 100 times, so the initial contentless-delete implementation optimized 100 times in separate transactions.
Empty Trash now sends its IDs through the wire to `notes_purge` in batches of at most 500, which purges each batch in one transaction and runs FTS5 `optimize` once at its end, matching the TypeScript adapter.
The batch shares one timestamp and HLC, preserves attachment handover and revision deletion, refuses live non-empty notes, and rolls back every purge on any failure.
Per-note notifications are sent only after each batch commits; a failed batch sends none, while earlier committed batches remain purged and announced.
Rust and TypeScript tests cover empty batches, missing and duplicate IDs, refusals, database-error rollback, retained matches, vocabulary removal and byte scans including older indexed versions.
Batching removes the multi-second Empty Trash regression and brings its measured p95 below 250 ms and below the base.
Single-note purge in a 10,000-note library still costs about 19 times the base p50 because it must compact the index to remove tombstones; batching cannot amortize a singleton, though its measured p95 is below 60 ms.
The byte-removal guarantee is retained rather than replacing compaction with a bounded merge that might leave deleted postings behind.

### Incoming sync purges

`DEVOT_PURGE_REVIEW_BENCH=1 pnpm exec vitest run --project slow tests/core/fts-purge-review.bench.test.ts --silent=false` measures 20 pulls after two warmups against copies of an optimized 10,000-note file-backed library, using WAL and synchronous FULL.
Each pull receives 100 encoded tombstones through the real sync engine, including decoding, preserving merge revisions and storage commits; fixture setup, opening the database and connecting are outside timing.
On reviewed commit `7cb8d072`, each synced purge optimized separately: **4942.812 / 5117.352 ms p50 / p95**.
Deferring optimization until the end of the pull reduces this to **372.637 / 475.248 ms**, a 92.5% / 90.7% reduction.
The remaining time includes per-record transactions and merge-version writes, not just FTS maintenance.
Synced purges now persist a compaction-pending marker atomically with the deletion; a `finally` completes compaction after every pull, including failures, and opening the store recovers a marker left by a crash.
Tests verify vocabulary, MATCH and database bytes through the deferred sync path, recovery after reopening and compaction failures; the two-device engine tests retain sync's existing local merge revision while removing the purged index terms.

### Blank-draft discard

The same opt-in review benchmark discards a never-typed draft through the note service in each copied 10,000-note library.
The draft is caught up before timing, so the test exercises an existing zero-token FTS row rather than inferring emptiness from current note text.
Milliseconds, **p50 / p95**:

| Case                        | Reviewed `7cb8d072` |     Sync batching | Sync batching and blank-draft check |
| --------------------------- | ------------------: | ----------------: | ----------------------------------: |
| Pull 100 incoming purges    | 4942.812 / 5117.352 | 372.637 / 475.248 |                   350.286 / 519.753 |
| Discard a never-typed draft |       0.783 / 2.218 |     1.307 / 3.019 |                       0.703 / 1.058 |

An already optimized seed makes the old blank-draft optimization cheap; timings alone do not demonstrate that it was skipped, so SQL tracing explicitly tests that no `optimize` command runs.
The contentless table has `notes_fts_docsize`; its two zero token counts are encoded as `x'0000'`, with the contentless-delete origin stored in a separate column.
A zero-token row alone is insufficient: a typed-then-cleared draft that was caught up again can still have old deletion tombstones.
Schema v33 therefore remembers indexed history when a row becomes stale, reading the token counts from the index, and clears those markers only after compaction.
Existing v32 rows are marked conservatively during upgrade because their earlier tombstones cannot be inferred from current docsize.
Rust and TypeScript tests cover never-indexed and indexed blank drafts, cleared drafts both before and after catch-up, vocabulary and byte removal, and the v32 zero-token upgrade case.

## Top bottleneck

The original external-content full run made deferred search catch-up the slowest measured path at both 1 MB and 5 MB.
To reproduce the separate profile run:

```sh
DEVOT_LARGE_PROFILE=<dir>/large-search node scripts/bench/large-notes.ts --quick --out <dir>/large-notes-profile.json
```

This writes one inspector CPU profile around each 5 MB catch-up search, ten profiles in quick mode.
The profile files are `<dir>/large-search-{0,1,2,3,4}-{edit-save,paste-save}.cpuprofile`.
Aggregate time-delta-weighted samples total 4,097 ms: `catchUpSearchIndex` / `sqliteTransaction` account for 86.77% inclusive, `catchUpNote` for 60.02% inclusive, and the entire `searchNotes` call for 88.88%.
Inspector `post` overhead accounts for 10.64%; excluding it puts the catch-up transaction at approximately 97.1% of the remaining sampled time.
SQLite native frames have no JavaScript function name; their parent stacks identify the transaction and statement calls, not SQLite's internal tokenization functions.
Do not interpret these samples as a breakdown of SQLite tokenization versus B-tree work.

Reachability is explicit: the benchmark calls `notes.search('planning')` immediately after applying an editor update and flushing it.
`src/core/notes/search.ts` passes the parsed query to `storage.searchNotes`; the adapter's `search` sees an indexable term and calls `catchUpSearchIndex`.
Before schema v32, `tests/support/sqlite-adapter.ts` ran `CATCH_UP_SQL` in an immediate transaction, deleting the old complete title/body from the trigram FTS index, inserting the new complete title/body and clearing its stale marker.
The production Rust store has matching `CATCH_UP_SQL` in `src-tauri/src/storage/search.rs`.
As a disconfirming check against excerpt generation or query execution being the main cost, the identical warm query is measured after catch-up: its full-run p95 is 3.266 ms at 1 MB and 11.141 ms at 5 MB, versus 101.474 ms and 509.688 ms for catch-up.
The profile agrees: `bodyOf` and `foldText` each account for only about 0.75% self time.

A separate test-store experiment timed each `CATCH_UP_SQL` statement inside the immediate transaction over twenty runs after two warmups, changing one line per run in the same `sampleNote` fixtures.
Save/setup and correctness assertions were outside the timed transaction.
Values below are milliseconds, p50 / p95.

| Operation                                           |   Current, 1 MB |     Current, 5 MB |
| --------------------------------------------------- | --------------: | ----------------: |
| FTS5 `'delete'` of the old text from `search_stale` | 20.953 / 21.340 | 108.859 / 118.098 |
| Insert the new title/body into FTS5                 | 26.585 / 28.375 | 153.345 / 165.816 |
| Delete the `search_stale` row                       |   0.060 / 0.077 |     1.852 / 6.491 |
| Transaction time outside the three statements       |  7.913 / 30.477 |   40.599 / 84.990 |
| Complete catch-up transaction                       | 56.208 / 77.204 | 318.985 / 365.081 |

Deleting the old entry accounts for approximately 44% of the sum of median statement times at 1 MB and 41% at 5 MB, not half the complete transaction time.
The installed SQLite source corroborates re-tokenization: `sqlite3Fts5StorageDelete` calls `fts5StorageDeleteFromIndex`, whose indexed-column loop invokes `sqlite3Fts5Tokenize` with `FTS5_TOKENIZE_DOCUMENT`.
Transaction time outside statements includes begin/commit, deferred FTS work and disk synchronization; those components were not measured separately, and independent percentiles do not add up.

## Original candidate prototype

A throwaway migration on temporary test-store databases replaced the external-content trigram table with `content='', contentless_delete=1`, changed catch-up to `DELETE FROM notes_fts WHERE rowid=@rowid` followed by the existing insert and stale-marker deletion, and made stale-update triggers keep only the rowid.
The throwaway prototype is not committed; schema v32 implements the migration separately from the benchmark-only PR #1048.
The prototype's twenty-run measurements use the same fixtures and timing method as the statement breakdown above.

| Operation                                     | Contentless-delete, 1 MB p50 / p95 | Contentless-delete, 5 MB p50 / p95 |
| --------------------------------------------- | ---------------------------------: | ---------------------------------: |
| Delete the old FTS entry by rowid             |                      0.021 / 0.025 |                      0.028 / 0.047 |
| Insert the new title/body                     |                    26.092 / 26.554 |                  131.194 / 141.914 |
| Delete the `search_stale` row                 |                      0.007 / 0.008 |                      0.009 / 0.013 |
| Transaction time outside the three statements |                    19.446 / 21.166 |                  118.076 / 124.437 |

| Complete catch-up | Current p50 / p95 | Prototype p50 / p95 | Reduction p50 / p95 |
| ----------------- | ----------------: | ------------------: | ------------------: |
| 1 MB              |   56.208 / 77.204 |     45.516 / 47.492 |       19.0% / 38.5% |
| 5 MB              | 318.985 / 365.081 |   250.657 / 258.021 |       21.4% / 29.3% |

The old-text deletion becomes negligible, but increased time completing the transaction prevents an equivalent reduction in total catch-up time.
For 10,000 short one-line `libraryBody` notes, after FTS optimization, vacuum and WAL truncation, FTS shadow-table size was 4,255,744 bytes with external content and 4,284,416 bytes with contentless-delete: an increase of 28,672 bytes (0.67%), entirely in `notes_fts_docsize`.
This clean-index measurement excludes accumulated deletion tombstones and pending stale-body snapshots.

The installed better-sqlite3 13.0.3 reports SQLite 3.53.4 at runtime.
`src-tauri/Cargo.toml:42` enables rusqlite's `bundled`, `backup`, `functions` and `hooks` features; the lockfile pins rusqlite 0.41.1 and libsqlite3-sys 0.39.1, whose bundled SQLite is 3.54.1.
An isolated Rust probe compiled with those exact versions and features reported SQLite 3.54.1 and successfully created, inserted into and deleted from a contentless-delete trigram table; the full Tauri app was not built for this check.
Both stores support `contentless_delete=1`, introduced in SQLite 3.43.

No production search or excerpt query reads title/body values from `notes_fts`, and no FTS `snippet()` or `highlight()` usage was found.
The Rust searches use matching rowids at `src-tauri/src/storage/search.rs:376,395,444` and BM25 at `:492`; excerpts read `notes.body_md` at `:669`.
The adapter mirrors those rowid/BM25 queries at `tests/support/sqlite-adapter.ts:103,113,422,452` and reads bodies from `notes` at `:803,1103,1208`.
Attachment handover uses matching FTS rowids but reads the body from `notes` (`src-tauri/src/storage/purge.rs:17–20`, adapter `:514–518`).
The prototype checked new/removed term visibility and excerpts after every catch-up, and the top five BM25 rowids and scores matched exactly between schemas for the 10,000-note library query.

A real migration is cross-store work: replace both stores' catch-up deletion SQL and the stale-text/deletion triggers from `src-tauri/migrations/0029_search_catch_up.sql`, populate the replacement index from `notes`, and preserve freshness across upgrades and concurrent writers.
The repair path at `src-tauri/src/storage/search.rs:584` also needs replacement: its FTS `'rebuild'` command was verified to fail with `'rebuild' may not be used with a contentless fts5 table`.
Purge and FTS `secure-delete` need dedicated cross-store correctness and forensic-removal validation before adopting deletion tombstones; accepting the configuration command alone does not establish equivalent guarantees.
These migration and security implications kept contentless-delete out of the benchmark-only PR #1048; schema v32 handles them in its stacked follow-up.

Another candidate is to process the existing stale-index queue after idle saves, coalescing while typing and retaining synchronous catch-up when a query needs freshness.
If caught up before a query, the observed warm timings suggest an upper bound of 97–98% less foreground search latency, but this moves work rather than reducing indexing CPU and is not an implemented or measured fix.

The unscaled sync-push budget also fails at the unchanged base on a slower Linux container; set `DEVOT_BUDGET_SCALE` for that environment.
