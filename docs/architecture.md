# Devot architecture

Status: **v2, agreed 2026-10-09** (moved the shell from Electron to Tauri). Items marked _open_ are not decided yet and do not block phase 1.

## Product

- A local-first Markdown note-taking app for daily personal use, source-available under FSL-1.1-MIT (`LICENSE`): each release becomes MIT two years after it is published. A three-day trial unlocks everything; after it, notes are read-only (read, search, copy and export) and sync and AI are locked until a license bought once unlocks them all (docs/adr/0006-source-available-and-sold-once.md).
- No account is needed for anything: sync's identity is device pairing, and each owner runs their own relay (docs/adr/0004-sync-without-accounts.md). Accounts and Share on Web wait until a hosted service is decided.
- Billing: one license bought once, checked offline, no account; a three-day trial first, then read-only (docs/adr/0006-source-available-and-sold-once.md; see Licences). Features ask `createEntitlements().has(feature)` (`src/core/entitlements.ts`) with a typed `Feature`. `PLAN_GATED_FEATURES` is `editing`, `sync`, `aiProviders` and `semanticSearch` (`localNotes`, reading, searching, copying and exporting, is never gated); a license names a plan (`pro`), and `PLAN_FEATURES` says what the plan grants, so a paid feature added later reaches every license. The `EntitlementSource` is the license as Rust checked it (`enforced`, its state and plan, and whether the trial runs): a gated feature needs `valid` and `pro`, or a running trial; nothing is gated while the build holds no production key (`enforced` false). The windows only show what is locked; Rust enforces it (`E_LICENCE_REQUIRED`).
- Usage data: the app records usage events through one local interface (event name, time, a few anonymous properties; never note content, titles or names). Nothing leaves the device until an opt-in upload ships with accounts (see Usage events).
- Platforms: macOS 26 and later first, then iOS and iPadOS. Windows and Linux are out of scope for now; platform code stays isolated (`src-tauri/src/native/`) so they remain possible.
- Layout: three panes (sidebar, note list, editor and preview), keyboard-driven. In a narrow window (the minimum is 760 px) the list shrinks to `size.list-min-width` before the editor, which keeps `size.pane-min-width` for each split pane; below `size.sidebar-collapse-width` (1000 px) the sidebar is hidden until Show Sidebar (or Cmd+/) asks for it, a request that lasts until the window crosses that width again and is not stored. A split pane's selection toolbar stays on one row and scrolls sideways when the pane is narrower.
- Workspaces: Open as Workspace (the notebook menu, or Cmd+Return on a notebook in the palette) makes one notebook the whole sidebar: a title (Go Up a Level, the notebook's icon and name, the notebooks above it, each opening as the workspace; its menu renames, changes the icon or copies the ID), All Notes (the notebook with its sub-notebooks), its sub-notebooks, and Status and Tags counted over its notes only, listing only the tags they have. Pinned, Templates and the Trash are hidden, and the tag menu has no Delete Tag there. Go Up a Level (Backspace on a row that is neither a notebook nor a tag, where Backspace deletes; Cmd+Up on any row) opens the parent notebook as the workspace, or leaves workspaces at the top level; Leave Workspace in the palette leaves at once. A view outside the workspace (All Notes, Templates, the Trash, a notebook outside it), a note opened outside it (a note link, the palette, a search over every note) or the notebook being deleted leaves it. The workspace is per window, kept in the window's last state (`lastState.ts`) and dropped on restore when its notebook is gone.
- Language: the UI ships in English. Other languages come later (see Localisation).

### Why Tauri

Measured on the same CodeMirror page with a 10k-character note, M1 Pro, macOS 27.2, built-in 120 Hz display:

| Metric                         | Electron 44           | Tauri 2                              |
| ------------------------------ | --------------------- | ------------------------------------ |
| App bundle                     | 288 MB (runtime only) | 9.5 MB                               |
| Launch to first editor paint   | 891–1147 ms           | 583–638 ms                           |
| Memory footprint with the note | 262–279 MB            | about 160–230 MB (approximate)       |
| Change to paint, median / p95  | 8.3 / 9–10 ms         | 8 / 10 ms with the 60 fps cap lifted |
| Idle CPU, static page          | ≈ 0 %                 | ≈ 0 %                                |

Tauri also runs the same code on iOS. Its costs: WKWebView paces rendering at 60 fps unless a private WebKit preference is turned off, and window transparency (needed for the sidebar material) uses a private API too; both rule out the Mac App Store. Window transparency has a reported GPU power cost on some Macs (tauri-apps/tauri#15471); GPU power is measured in the phase 2 harness.

## Process model

```
┌────────────────────────── WKWebView (UI) ──────────────────────────────────┐
│ React UI · CodeMirror 6 · preview DOM · strict CSP, no Node                 │
│                                                                             │
│  Core worker (Web Worker): data model · Yjs · Markdown · link index ·       │
│  import / export rules · sync engine (phase 2)                              │
└──────────────┬──────────────────────────────────────────────────────────────┘
               │ Tauri commands (each one granted by a capability file)
┌──────────────┴────────────── Rust (app process) ───────────────────────────┐
│ storage: SQLite + FTS5 (own thread) · files · encryption ·                  │
│ native: window material, 120 Hz, SF Symbols, accent colour · menus          │
└─────────────────────────────────────────────────────────────────────────────┘

devot-mcp (separate CLI, stdio, Node) ── runs the same core library with a
better-sqlite3 adapter on the same SQLite file (WAL)

devot --crash-reporter (builds with a Sentry DSN only) ── a second copy of
the app binary that waits for the app to crash and saves a scrubbed report
```

### Who does what

- **Rust:** what is performance-sensitive or needs the system: SQLite reads and writes (on a dedicated thread), FTS5, file I/O, encryption, native window features, and later local embeddings.
- **TypeScript core:** the logic: data model, Yjs, Markdown, link index, import and export rules. It runs in a Web Worker so the UI thread never waits on it.
- **Moving work to Rust:** when a piece of core logic is measured as a bottleneck, or must keep running with no window open (for example the sync engine), it moves to Rust behind the same interface.

### Core library boundaries

The core is plain TypeScript, so the UI worker, `devot-mcp` and the iOS app share it.

- The core imports neither `@tauri-apps/*`, `better-sqlite3` nor Node built-ins. It talks to storage through an adapter interface: the app's adapter calls Tauri commands; `devot-mcp` and tests use better-sqlite3.
- Tauri commands are reachable from the page only, so the core worker's storage calls cross to the page (`src/renderer/src/storage/wire.ts`). A note's or a version's Yjs state crosses as the base64 string the commands take, coded in the worker (by the engine's own `toBase64` and `fromBase64` where it has them), and the worker also finds a note's links and checks its limits; the page hands what it gets to the commands as it is, so a save or an open costs the UI thread no work for each byte of a state (several MiB for a long, much-edited note). Opening a note for its editor sends the whole state once; selecting a note asks the core for its title alone (`title`), and when another process wrote to the open note, the editor's replica takes in only what it lacks (`open` with the replica's state vector). A first open still builds the replica from the whole state, which for a heavily edited note costs what its history weighs (sync does not change this, ADR 0002).
- Every data API is async.
- No plugin process: third-party plugins run in sandboxed frames of the main window (see Extensions, ADR 0005).

## Data model

- IDs are UUIDv7. Deletes are soft (tombstones), so they sync.
- **Note body:** a Yjs document per note, holding the Markdown text in a `Y.Text`. The Yjs document is the source of truth for the body.
- **Authorship** (ADR 0007, `src/core/authorship.ts`): beside `body`, the note's Yjs document holds two root maps. `writers` maps a session (one MCP connection, one start of the HTTP API, one Edit with AI sheet) to its kind (`mcp`, `http`, `aiEdit`, set by Devot), its name (the MCP client's `clientInfo.name`, one line of at most 100 code points without control or bidirectional characters; only shown, never trusted) and its process's HLC node ID. `writes` maps each agent write to its session, its time, the Yjs item IDs it inserted into and deleted from `body` (varuint ranges), the text it deleted (at most 1 MiB per note, the oldest writes' dropped first), the metadata it changed and whether it made the note. A write and its record are one Yjs transaction. Text is attributed by item ID, so the records sync, merge and survive restarts and compaction with the body; a record that does not parse is skipped and kept. Undo All for one writer (`reverseWrites`, `NoteService.undoAgentWrites`) puts back what it deleted where the deleted items sit and deletes what it inserted, keeping the owner's and other writers' text; Clear Authorship (`clearAuthorship`) empties both maps.
- **Agent writes index** (schema v20 `agent_writes`): one row per write, derived from the maps as `body_md` is from the body and written with the note in the same transaction (devot-mcp's included); never synced, rebuilt by the note's next write when missing. `seen` is this device's: a row starts unseen, an `aiEdit` one seen, and so does a duplicate's (the owner made the copy). The main window marks the writes its review notice showed seen when the owner leaves the note, dismisses the notice or closes the window (`NoteService.markWritesSeen`, which saves the note first). Purging a note deletes its rows; the Trash keeps them. `agent_writes_list` and `agent_writes_seen` read it and mark rows seen; Rust checks every row `note_put` brings.
- **Body versions:** a write replaces a note's stored Yjs state whole, so every write compares before it overwrites. A note's body has a version (schema v16 `notes.body_version`; bodies from before are at 0), which every write moves on by one, and a record carries the version of the body its writer last saw (`bodyVersion`: the stored one when it is read). Storage writes a note only while its body is still at that version (`putNote`, in the Rust store, the better-sqlite3 adapter and the UI tests' memory storage alike; a new note is stored at the next version too); a write based on another version would go over a body another writer wrote since (devot-mcp, any other connection, the core of another window showing the note, later sync), so it is refused with `E_NOTE_BODY_STALE` and changes nothing, and a purged note is left alone whatever the version. The note service then takes the stored copy in, as when it hears of an outside write (`takeIn`: a Yjs merge, so neither side's text is lost, and the newer HLC of each metadata field), and writes again (`put` in `src/core/notes.ts`), five times a write at most (`WRITE_TRIES`): a save the other keeps getting ahead of fails like any other, keeping its changes, and is tried again later (see Saving and quitting). A change written without loading the note and a restore from the Trash read the note again and write again the same way; moving a note to the Trash writes the body as its document holds it, with what it took in since its last write. A write may be based on a whole number below 2^53 − 1 (`MAX_BODY_VERSION`), so the version it moves on to is still exact in JavaScript; `note_put` refuses any other with `E_NOTE_VERSION_INVALID`, as every storage adapter does (`checkNote`).
- **Hand-set dates:** the preview's info card sets a note's created and updated dates (a click opens a date-time field; Return saves, Escape cancels). Both dates share one HLC (schema v17 `notes.dates_hlc`, `datesHlc` on a record, '' when never set): a write with a newer one sets both as written, any other keeps `created_at` and moves `updated_at` only forward, in every storage adapter alike. `NoteService.setDates` refuses a time that is not a whole, non-negative millisecond count, or a note updated before it was created (`E_NOTE_TIME_INVALID`, as `note_put` does). The next edit moves the update date on as usual.
- **Metadata** (title, notebook, tags, status, pinned): SQL rows. Each field is last-writer-wins, ordered by a hybrid logical clock (HLC) timestamp. Storage enforces it: writing a record merges it field by field and keeps the value with the newer HLC, so writing a stale copy never undoes a newer change (Rust store and the TypeScript adapter use the same SQL). The core's clock takes in (`receiveStored` in `src/core/hlc.ts`, through `Clock.receive`) the stamps of every record it reads before writing over it: a note when it is loaded, read from the Trash or merged with what another process wrote (`mergeStored`), notebooks and tags when listed, and a note's tag membership row before a tag goes on or off (`getNoteTag`, command `note_tag_get`). So a write always wins over the value it is based on, even when that value was written while the system clock ran ahead and the clock has been set back since; a restore from the Trash, a rename or a move would otherwise lose to it, silently, until the clock caught up.
- **Tags** may have a colour (schema v11 `tags.color`, a field merged by HLC like the others). It is an ID from a fixed palette (`TAG_COLORS`: red, orange, yellow, green, blue, purple, pink, gray), never a colour value: each theme gives every ID its colour through the tokens `color.tag.<id>`, light and dark. Rust accepts only palette IDs; storage reads an ID it does not know (a later palette, through sync) as no colour, keeping its HLC.
- **Notebook icons** (schema v18 `books.icon`, `books.icon_color`, one HLC `icon_hlc` for both, since they are picked and reverted together): Change Icon… in the notebook menu opens a picker (search over names and keywords, a tab per category, a palette colour row) over a fixed catalog of SF Symbol names (`design/icons/notebook-symbols.json`, read by `src/core/notebookIcons.ts` and embedded in Rust). The icon is a catalog name, the colour a `TAG_COLORS` ID; Revert to Default clears both. An icon is drawn in the theme's `color.tag-icon.*` token for its colour: the tag colour, darkened in the light themes only as far as 3:1 on the sidebar, lists, editor and popovers needs (yellow, orange, green and gray on white; `contrast.test.ts`). Rust accepts only catalog names and palette IDs (`E_BOOK_ICON_INVALID`), and every storage reads a name or ID it does not know (a later catalog, through sync) as unset, keeping its HLC. The icon shows in the sidebar, the note's notebook picker, the Move dialogs and the palette's notebook rows; the picker renders only the symbols scrolled into view (rendered symbols are cached per name, size and appearance).
- **Names** (notebooks, tags): trimmed by one whitespace rule on both sides, Unicode's White_Space as Rust's `str::trim` reads it (`trimWhitespace` in `src/core/text.ts`; JavaScript's own `trim()` differs on U+0085 and U+FEFF), one line, at most 200 (notebook) or 100 (tag) code points. The name fields stop at those limits, counted in code points (`src/renderer/src/nameLimit.ts`; HTML's `maxLength` counts UTF-16 units). Tag names are unique in any case: a rename onto another live tag's name is refused (`E_TAG_NAME_TAKEN`). A name typed is looked up by name (made when missing); a tag picked from a list (a drop on its row, the palette's Add Tag, the tag picker) goes on by ID, so two tags of one name that sync brings stay apart. A refused notebook or tag change is logged by code and shown in a notice that says the rule broken (or the code).
- **Notebooks** nest through `parent_id` (no foreign key, so sync can deliver children first). Deleting a notebook deletes its sub-notebooks; their notes are kept and count as in no notebook (they keep `book_id`, so restoring the notebook brings them back). A missing parent makes a notebook top level, and a parent cycle from concurrent moves is broken at its smallest ID, the same way on every device. Selecting a notebook lists its notes and those of its sub-notebooks. Deleting a notebook (Delete Notebook, Backspace or Delete on its row) asks first, like deleting a tag: the question names the sub-notebooks that go with it and the notes that stay, Return confirms, Escape or Cancel keeps it and the keyboard returns to the row. Phase 1 has no restore for a deleted notebook (a backup restore brings it back).
- **Notebook order** is the user's own (schema v10). Each notebook has a sort key, a fractional index (`src/core/order.ts`: base-62 strings compared as plain strings, with a key between any two), merged by its own HLC. Siblings show in key order, equal keys (two devices moving notebooks into the same gap) by ID, so every device shows the same order. A move writes one row: the moved notebook's key and, when it changes, its parent; only when its neighbours share a key (or a key from sync is malformed) do the siblings get fresh keys. A reorder keeps a stored parent that is missing (the notebook shows at the top level until it arrives). New notebooks go after their siblings. The v10 migration adds empty keys. Notebooks without a key show as before, by name in the locale's collation (then ID), ahead of keyed siblings, and the core keys them in that order when it starts (`BookService.settleOrder`, one write per such notebook), so names with accents or in other scripts keep their place. These keys carry no clock: any later move wins, and when two such keys meet the greater wins, so devices that keyed apart still converge.
- **Markdown snapshot:** derived from the Yjs document on save (debounced). FTS5 search, export and MCP read the snapshot.
- **Rule:** nothing writes the snapshot directly. Import and MCP note creation both compute a text diff and apply it to the Yjs document as Yjs operations.
- **Lineage** (ADR 0002, risk 1): every write to a body changes the note's existing Yjs document, so two devices' states of one note always merge without duplicating text. Typing reaches the core as the editor replica's Yjs updates (`applyUpdate`); every write that has only the new text (`setBody`: import, devot-mcp's `create_note` and `update_note`, the local HTTP API's, templates, Restore) applies the edits `textEdits` (`src/core/diff.ts`) finds: a line diff, each run of changed lines trimmed to the characters that differ, so lines the write leaves alone are never rewritten and an edit another device made to them stays in its place (past the line diff's work bound, 2,000 changed lines and fewer in a long note, the changed middle is one replacement). Appending a template, putting in a pasted image's link (`insertAt`) and the attachment IDs of a duplicate are Yjs operations on the note's document too. A new note (create, Duplicate, New Note from Selection, an import) starts its own lineage, which every later write continues; a duplicate starts from a copy of its source's state. Writes that do not touch the body (a batch, the Trash and restoring from it) store the body's Yjs state as it was. The Markdown mirror never reads a file back. First-launch notes, the one body every device writes under the same ID, are seeded as the same Yjs state everywhere (see First-launch notes). `tests/core/lineage.test.ts` checks each path: two devices write to one note, and merging both states shows each change once, where it was made.
- A note's stored Yjs state is one whole document, replaced on each write (see the Body versions item above), so there is no update log to compact. _Phase 2:_ sync keeps this shape: the relay stores each record's latest encrypted state and clients merge on a rejected push, so there is still no update log (ADR 0002).
- Core tables: `notes`, `books` (nestable notebooks; one reserved for templates, see Note templates), `tags`, `note_tags`, `files` (attachments), `links` (link index), `revisions` (revision history, local), `agent_writes` (derived, local; see Authorship), `sync_records` and `sync_state` (what sync knows of each record, schema v19; see Sync and encryption). _Phase 2:_ `chunks` (a vector column for semantic search) is not created yet. AI edit proposals have no table: a proposal lives in the Edit with AI sheet until it is accepted or discarded, and an accepted one follows the same rule as import and MCP, a text diff applied as Yjs operations (see AI > Edit with AI).
- FTS5 uses the `trigram` tokenizer, so Chinese substring search works. Triggers keep the index in step with `notes`; a write puts a note's text in again only when its title or its Markdown changed (schema v15), so a notebook, status, pin or Trash change costs no indexing.
- Markdown export (see Export and print) writes notes and notebooks as Markdown files that import back as they were.

### Schema and migrations

- Migrations are numbered SQL files in `src-tauri/migrations/`, shared by the Rust app and the TypeScript better-sqlite3 adapter, so both always see the same schema. A released migration is never edited.
- `PRAGMA user_version` records the applied version. A database from a newer Devot is refused rather than opened.
- A fixture database is kept for every released schema version and must upgrade cleanly (`src-tauri/tests/fixtures/schema-v<N>.sqlite`: 18 for v1.0.4, 19 for the v1.0.5 betas, each with live, trashed and purged notes, notebooks, a tag, an attachment, a link and versions, made as `schema-fixtures.sql` there says; v1 from before).
- Pragmas: WAL, `synchronous = FULL`, `foreign_keys = ON`, a 5 s busy timeout (so devot-mcp and the app can share the file), and `secure_delete = ON` (overflow pages too, unlike `FAST`), so a note deleted for good leaves no readable text in free pages, which every later backup would copy. A purge also takes the note's text out of the search index's pages (FTS5 `secure-delete`, on only for the purge: on for every change it would make indexing a long note's edit about 30 times slower). Other changes only mark a note's old text deleted in the index, so earlier text of a purged note stays there until FTS5 merges its segment. Pages freed before a version that set these keep their text until reused; frames in the write-ahead log keep it until the log restarts after a checkpoint (backups read the database, not the log).
- Every write transaction begins `IMMEDIATE` (the Rust store sets it on its connection; the better-sqlite3 adapter uses `.immediate()`): it takes the write lock first, so it waits out the other writer for the busy timeout. A deferred one that read first (an attachment's note, the search index on its first use after launch) would fail at once with `E_STORAGE_BUSY` instead (`tests/core/busy-writes.test.ts` and the Rust store's tests hold the lock from another connection).

### App data folder

- A release build keeps everything in `<app data>`, `~/Library/Application Support/io.github.jma49.devot`: the database (`devot.sqlite`), `backups/`, `logs/`, `crash-reports/`, `usage.sqlite`, `editor-settings.json`, `ai-settings.json`, `fonts/` (imported editor fonts), `keyboard-shortcuts.json`, `note-windows.json` (where each note window was, see Note windows), `plugins/` and `plugins.json` (installed plugins and what each was granted, see Extensions) and `pdf/` (a PDF while it is printed, see Export and print).
- A debug build (`pnpm dev`, `pnpm build:debug`, every test build) uses `io.github.jma49.devot.dev` instead: `src-tauri/src/data_folder.rs` adds `.dev` to the identifier Tauri names the app's folders after, so development never opens, migrates or deletes the notes of an installed Devot, whichever branch it was built from. The bundle identifier stays the same, and WebKit keeps website data per bundle identifier, so a debug build also gives every window a WebKit data store of its own (`web_data_store` in `data_folder.rs`, a fixed identifier): its local storage (focus mode, the sort order, recent templates, pane widths) and caches stay apart from an installed release app's. The release app keeps WebKit's default store. The HLC node ID is not kept there: each start of the window makes a new random one (`newNodeId` in `src/core/hlc.ts`, 64 bits), so two processes never stamp a write alike.
- **One Devot per data folder:** at launch the app locks its data folder (an advisory `flock` on the folder itself, `take_folder` in `src-tauri/src/startup.rs`, so no file is written for it) and holds it for the life of the process; the system lets go of it when the process ends, however it ends. A second Devot on the same folder (another copy of the app, or the binary started again while the single-instance socket cannot be used, see URL scheme; otherwise a second launch hands over its arguments and quits first) opens nothing: it logs `E_STARTUP_FAILED E_DATA_FOLDER_IN_USE`, says in the launch alert that Devot is already open, and exits. A folder that cannot be locked at all (a file system without locks) is logged (`W_DATA_FOLDER_LOCK_FAILED`) and used without the lock. devot-mcp takes no lock: it is the other writer meant to share the file.
- **A launch that cannot open the notes** (`src-tauri/src/startup.rs`): every step of setup fails with a code rather than handing Tauri an error, which it would turn into a panic (no window, no message, the code lost). The failure is logged as `E_STARTUP_FAILED <code>`; a native alert (`NSAlert`, its text from `strings.rs` by the code's kind: already open, a database from a newer Devot, a damaged database, a full disk, a folder that cannot be written, a busy database, anything else) says what happened, where the data folder is and the code; the app exits with status 1 once it is dismissed.
- Scripts never name the release folder (`tests/policy/data-folder.test.ts`); `scripts/app-data.sh` knows the dev folder. `scripts/smoke/quit-saves.sh` runs the debug bundle on it: it refuses while another process has the dev database open, copies a dev database that is there with SQLite's online backup (into `smoke-backups/`, where the copy stays) and puts it back afterwards, and stops if the app it started opened any other database. It starts the app with HOME in a temporary folder in which only the dev folder is real, a link to it, so a bundle that keeps its data elsewhere (one built before debug builds had a folder of their own) opens a new database in that folder and is stopped having touched nothing real. `scripts/perf/launch-cost.sh` runs the app with HOME in a temporary folder, so even a release build starts on a data folder of its own. Both end only the processes they started, by process ID.
- The UI tests keep notes in an in-memory storage (`src/renderer/src/storage/memory.ts`), chosen at build time: Vite's `define` sets `DEVOT_UI_TEST`, true only in the UI tests' config (`vite.ui-test.config.ts`), so no environment variable or `.env` file can turn it on. The app's builds leave that storage out, and the release UI build fails if the bundle holds it (`scripts/sentry/ui.ts`; `tests/policy/source-maps.test.ts`). `pnpm vite --config vite.ui-test.config.ts` serves that build in a browser.

### Saving and quitting

- The core saves a note 300 ms after the last edit. Writes of one note go one at a time, in order, each with the note as it is when the write starts, so an older snapshot never lands after a newer one; a flush waits for a write under way.
- **Notes in memory:** the core keeps a note's Yjs document in memory while it is used, and only the most recently used notes once nothing uses them (`NOTES_IN_MEMORY`, 8), so browsing a library does not keep every note it opened. A note leaves memory only when nothing of it can be lost: no call is using it, no editor shows it (the editor holds its note while it is open, `hold` and `unhold`, so its replica and the core's document never part), no write is asked for or under way, no change is waiting for its save or failed to save, and its title is not being typed (quick title edits stay one event). Typing not kept as a version yet becomes one first, as when quitting. A note that left is read from storage again when it is next used, with what was saved and what another process wrote meanwhile; calls that ask for a note while it is being read share that read, so a note is never in memory twice.
- **A save that fails loses nothing:** the note keeps its changes in memory and stays pending. The core tries it again 1 s later, waiting twice as long after each failure in a row (at most 30 s), and whenever something else saves it (opening another note, searching, quitting). It reports the note to the window (`onSaveProblems`; the worker sends the list on the channel its replies take, so the window hears of a failure before the reply of the call it happened in), which logs `W_NOTE_SAVE_FAILED <note ID> <code>` once per note and code and shows a notice while any note is unsaved: how many notes, the code, Try Again and Dismiss (a new failure brings it back). Everything else goes on: a flush saves the other notes and then rejects with `E_NOTE_SAVE_FAILED` and the IDs it could not save, which the window's own saves ignore. A metadata change written at once (`writeMeta`, a batch change) that fails takes back only its own field. For a note not in memory it does not load the note: the stored record is written back with the field changed and its body as stored (no Yjs document is built), after the body is kept as a version when the history does not end with it, as a write of the note in memory would; a load of the note waits for such a write. A batch checks its notebook once for all its notes (a notebook that is not live refuses the batch), so a move costs five storage calls a note (300 notes of 3.5 KB: 1,804 calls and 221 ms before, 1,505 and 116 ms after, better-sqlite3); `release` (import, devot-mcp) lets the note go and throws, since its caller undoes it.
- **The core must start, visibly:** the core worker starts when the window opens (`connectCore` in `src/renderer/src/coreConnect.ts`). A worker that does not load or raises an error before it is ready (`E_CORE_WORKER_FAILED`), a core that takes longer than 30 s to start (`E_CORE_START_TIMEOUT`) and a first load of the lists that fails (the load's own code, such as `E_STORAGE_BUSY`) are logged as `W_CORE_START_FAILED` with the code, and the window shows an error state in place of the library (`StartFailure.tsx`): what failed, the code, a pointer to Help > Export Diagnostics… and Try Again, which stops the worker and starts the core again. An empty library is never shown for a core that is not running. An error the worker raises after it started (an uncaught error or an unreadable message) is logged and shown as a notice with its code; the worker is kept, since it may hold unsaved changes. A worker that stops without any event cannot be told from a slow one and is not detected.
- **Note limits:** a title is one line (no line feed or carriage return) of at most 1,000 code points, a body at most 32 MiB of UTF-8, a Yjs state at most 64 MiB, and a body links to at most 10,000 notes. Rust's `note_put` refuses anything else, so the core keeps titles within the limit: line breaks become spaces and a longer title is cut (`clipTitle`, applied by the title field, `setTitle` and every way a note is made; import and templates also tidy spaces first). A title stored past the limit (by an older build) is cut when the note is loaded or restored from the Trash, so its writes are taken; the stored title stays until a rename, since a write with the same HLC never replaces it. Every storage adapter refuses the rest with `note_put`'s codes (`checkNote` in `src/core/noteLimits.ts`), so the core and its tests see what the app would; a policy test keeps the numbers equal to Rust's.
- Quitting does not lose that window: Rust holds the exit, emits a flush event, and exits when the UI reports that the core has saved (or after 2 s, so a stuck UI never blocks quitting). Every window with a core of its own saves, each main window and each note window, and the exit waits for all of them (`ExitGate` in `src-tauri/src/exit.rs` keeps the windows it waits for; one that closes meanwhile counts as saved). When the quit's save fails (any failure counts, whether or not the window has heard which notes failed), the first such quit is called off instead (`app_exit_cancel`): the window stays open with the changes and the notice says that quitting again quits without them.
- A quit stops a running Rebuild Search Index, whose one statement would otherwise keep the saves queued behind it on the database thread waiting past the 2 s: a progress handler, installed for the rebuild alone, asks `exit::quitting` every 100 SQLite steps, and a stop rolls the rebuild's transaction back, leaving the index as it was (`E_SEARCH_REBUILD_STOPPED`). Not `sqlite3_interrupt`, which is lost when it lands between two statements and could stop the save that runs next.
- On macOS the standard Quit menu item terminates without an exit event Rust can hold, so the app menu has its own Quit item (Cmd+Q) that starts the handshake, as does Quit Devot in the menu bar icon's menu; closing the last main window shown (Cmd+W or the close button) is held the same way, or in menu bar mode hides the window and quits nothing (see Menu bar mode); closing one of several main windows quits nothing (see Several main windows). Quitting from the Dock or at logout still bypasses it, and autosave bounds the loss to the last 300 ms.
- `scripts/smoke/quit-saves.sh` checks both paths on the real app (types, quits at once, reads the database). It runs the debug bundle on the debug builds' data folder (see App data folder), needs Accessibility permission for the terminal and switches the keyboard to ABC while it runs, because an input method rewrites simulated keystrokes.

### Note windows

- **What:** a note in a window of its own (#3), beside the main window: Shift+Return on a row of the note list, Open in New Window in the note menu, or the palette for the open note (`note.openInWindow`; not for templates or several notes). The main window saves its edits first. Opening a note that has a window brings that window forward; a note link clicked in a note window opens that note in its own window. Desktop only (`src-tauri/src/note_window.rs`, `cfg(desktop)`); a phone has one window.
- **The window** (`note.html`, `src/renderer/src/noteWindow/NoteWindow.tsx`): the title, the editor and the view modes (edit, split, preview), on an opaque window named after the note. The window's label is `note-<note ID>`, so Rust knows its note from the label alone (`note_window_note`) and the page can ask for no other. Its capability (`capabilities/note-window.json`) grants what one note needs: reading, searching and writing notes, their versions and attachments, reading the notebooks (a note a `[[` link makes goes in the same notebook) and purging the empty note a link made and dropped, the relay and its own close; no notebook or tag changes, imports, exports, backups or settings changes, which stay in the main window. Menu commands (Format, View) still act on the main window.
- **Size and position:** each note's window opens where it was last, at its size: Rust keeps the frames of the last 100 note windows (moves and resizes are kept in memory, written to `<app data>/note-windows.json` when a note window closes and when the app exits; a local preference, read leniently, never synced). A frame whose title bar is on no screen now is not used; a note without one opens beside the main window, 720 x 780 points.
- **Closing saves first,** as quitting does: Rust holds the close, sends the window `devot://note-window-close`, and closes it when the page has saved (`note_window_close_ready`), or after 2 s. The page hears closes and quits from the start, and a window still opening, or one that could not open its note, answers at once: it has nothing of its own to save. When the save fails, the first close is called off (`note_window_close_cancel`) and the window's notice says that closing again closes it without the changes.
- **One note, two cores** (`src/core/noteRelay.ts`): each window runs a core of its own, which holds a Yjs copy of the note. Every change a core makes to a note's document (typing, which comes as the editor's updates, and its own edits and merges) is relayed at once as the Yjs update it made, and a title change as the title and its HLC. A core that reads a note in sends its state vector (`want`), and every core that holds the note answers with what it lacks, so a window opened after the other typed starts with the unsaved typing (a note window listens to the relay before it reads its note, so the answer cannot arrive unheard). The receiving core applies what it is sent (`NoteService.receive`) and tells its window (`onTakenIn`), whose editor takes it in as a change from outside (not undone by Cmd+Z), and its title field the title. Yjs merges updates in any order, so delivery may lag or reorder. Each window saves its own changes: a relayed change is not a pending edit of the window it reaches, which also keeps no version or baseline of it (the window that made the change does). Saves merge into the stored state rather than replace it: two windows writing the same note are two writers on one body version, so the second write is refused (`E_NOTE_BODY_STALE`), takes the stored copy in and writes again (see Body versions), and what it takes in reaches its editor too. Each write is relayed as `saved` with its date, so the main window's lists move the note without a reload (a note made in a note window, through a `[[` link, reloads them). `tests/core/note-windows.property.test.ts` types into one note in two windows at random, with deliveries late and reordered and saves at any time, and checks that both windows and the stored note end with every edit either made; `tests/core/lineage.test.ts` checks that two windows' edits keep the note's lineage.
- **The note relay** (`src-tauri/src/note_relay.rs`, `note_relay_send`): the page hands Rust what its core sends (Yjs data stays the base64 the worker coded, never decoded), and Rust checks it (a note ID, base64 within a Yjs state's limit, a title within the title limit, an HLC) and passes it to the windows that may show the note: every main window, and the note's own window; each page listens on its own window only. A main window sends a note's changes only once another window has spoken of the note (`relayGate` in `src/renderer/src/noteRelay.ts`; a note window always sends), so a window alone pays nothing for each keystroke. A note window's core leaves compaction and the notebooks' order to the main window's.

### Several main windows

- **What:** File > New Window (Shift+Cmd+N, or New Window in the palette) opens another main window (#9), as many as 12 at a time. Each has its own library view (starting at All Notes), open note, selection, scroll position, focus mode, sidebar and size, and a core of its own on the one library. Desktop only (`src-tauri/src/main_windows.rs`); a phone has one window. A new window opens at the size of the frontmost one, a little down and to the right (`CASCADE`, 32 points), or centred when that would leave its title bar off every screen.
- **Labels and permissions:** the first window is `main` and the others `main-<n>` (2, 3, ... in the order they are made, never reused in a run). `is_main` in Rust and `isMainLabel` in the page tell them from every other window, and they share one capability (`capabilities/main.json` names `main` and `main-*`), so each has what the main window has. A window other than `main` keeps its view preferences (the last state, focus mode, the sidebar) in the webview's session storage, which goes with the window and survives its reloads, so a later window with the same label starts fresh; `main` keeps them in local storage as before (see Restoring the last state).
- **The frontmost main window** is the one focused last of those shown (a minimized window counts as shown), else the one focused last of all, so it follows the user (`front_label`). What belongs to one window of the user's choice goes to it: the View, Format and Revision History menu items and the palette, Backups, Export All, Rebuild Search Index, the HTTP API's calls and quick capture's notes, a deep link, and the files the `devot` command hands over (which also bring it forward); import dialogs hang off it, and an import's events go back to the window it began in (the frontmost one if that window is gone). A note-less event for all of them (an outside change found in the database, a failed backup) goes to every main window. The Text Look Up, Speak and editor context menu popups open in the window that asked, not in `main`.
- **What runs once** runs in `main`: the Markdown mirror (the other windows' writes reach it as writes from outside, see below), compaction and the order of notebooks. A core of another main window is lean, as a note window's is (`lean` in `init`).
- **Closing:** closing a main window quits Devot only when it is the last one shown (and menu bar mode is off, where it hides it instead). With another main window shown, closing `main` hides it (it hosts the mirror and holds unsaved edits, so it stays alive), and closing any other main window saves it and closes it, the way a note window closes (`close_after_saving`, `note_window_close_ready`, `note_window_close_cancel`; the first close whose save fails is called off and the window's notice says so). Only `main` runs the sync engine (`runsSync`), for the same reason: Rust holds one socket, and `main` stays alive while the app runs. A hidden `main` comes back with Open Devot in the menu bar icon, the Dock icon, or when no other main window is shown and a link comes in.
- **Quitting saves every window:** a quit asks every main window, hidden ones included, and every note window to save and waits for all of them (`savers_among` in `exit.rs`); a window the quit called off for (its save failed) is the one shown, if it was hidden.
- **Consistency:** two main windows on one note are two cores and two editors on it, kept together by the note relay as a main window and a note window are (the relay reaches every main window; a main window sends a note's text once another window has spoken of it, and a core that reads a note in always asks, so two windows that both have a note open start sending to each other). Everything else a window writes (a status, a pin, a notebook, a tag, a note made, trashed or purged) reaches the other main windows' lists by `devot://lists-changed`: a window that wrote tells Rust (`main_windows_changed`) 250 ms after the first write of a burst, Rust tells the other main windows, and each loads its lists and merges what is stored into the notes it holds 400 ms after the news, the way it does for a change another process made (`DB_CHANGED`, `externalChanges.ts`). The merge is field by field on the notes' HLCs, so a window's later save never undoes another's change (`tests/core/main-windows.test.ts`).

### Merging and history

- Concurrent edits merge automatically.
- When a sync brings in offline edits made on both sides, Revision History keeps the local text from before the merge, labelled as such, and can restore it (see Revision history). _Later:_ the note shows a notice ("Merged offline edits from iPhone · View changes") that opens the diff.
- Every note keeps version history (Yjs snapshots); see Revision history.
- **Undo** (#186): the editor has one undo system, CodeMirror's history (`history()` in `src/renderer/src/editor/settings.ts`, the rest in `editor/undo.ts`); there is no Yjs undo manager (`yCollab` gets `undoManager: false`), so no deleted Yjs items are kept alive for undo. Cmd+Z and Shift+Cmd+Z (CodeMirror's history keys) and Edit > Undo and Redo (they reach the page as `historyUndo` and `historyRedo` input events, which the history takes) all go to it.
  - It holds only the user's own edits in this editor. A change that reaches the editor from its Yjs document (sync, another process such as devot-mcp or the Markdown mirror, the core merging what was stored) is applied without entering the history (`Transaction.addToHistory` false, added by a transaction extender to every change y-codemirror brings in): undo never takes it back, and the history maps its steps through it, so it never joins the typing around it. Edits that arrive from AI (devot-mcp's `update_note`) are not undone by it either.
  - Each editor command (a format from the toolbar, the Format menu or its key, a slash menu item, a table command, Replace, New Note from Selection) is one step (`isolateHistory`); so is an image pasted or dropped, which lands a moment later, apart from typing done meanwhile. An input method's composition is one step however long it takes (the history always joins `input.type.compose` changes).
  - A restored version is the user's own change: one step of its own (see Revision history).
  - **Per note:** leaving a note keeps its history with its text and its replica's Yjs state (the last 10 notes left, `UNDO_NOTES`); shown again, the Yjs changes the core's document has beyond that state are applied outside the history, each where it was made (as y-codemirror applies a change while the note is open, never one text difference over everything between them), so undo goes on with the user's own edits in their places and leaves what changed meanwhile. When the core's document does not hold the kept state (it was made anew) or those changes do not lead to its text, the note starts with no history. The history lives in the window, not in the core, so the core letting the note go from memory does not touch it; a note left longer ago, or a reload of the window, starts with no history. Typing after coming back is a new step.

### Revision history

- **Storage:** the `revisions` table (schema v9). A body version holds the note's whole Yjs state (`Y.encodeStateAsUpdate`, not `Y.snapshot`: documents are garbage-collected, so a snapshot could not rebuild old text) and its length in characters; a metadata event holds the new title, notebook ID (null for none), status or pinned flag. Revisions are local to this device: they carry no HLC and are not synced (ADR 0002). Before a state from another device changes a note's body, and before another device's purge removes a note, the sync engine keeps the local body as a version with `value` 'merge' (`MERGE`); Revision History labels it "Before a merge with another device", so either side of an interleaved paragraph can be restored, and compaction keeps it. When both bodies held changes the other lacked, the version is always kept; when the change came only from the other device, at most one every 10 minutes (`REVISION_EVERY_MS`, a body version taken here counts), the rate typing here takes versions at, so a note typed on another device does not leave a never-compacted version per push. A welcome note nobody edited that gives way keeps none. A purge that came through sync keeps the note's revisions (`syncPurge`); a purge made here deletes them. Purging a note deletes its revisions; the Trash keeps them.
- **When a version is taken** (the core note service, `src/core/notes.ts` and `revisions.ts`): once editing pauses for a minute, and at least every ten minutes while editing goes on. A version with the same text as the newest one is skipped. Leaving a note takes no version: the saved body is the latest text, and the first change to the note in a later session (an edit, or a title, notebook, status or pin change, saved before it moves `updated_at`) keeps it as a version dated when the body was saved, unless the history already ends with it. For a note without history, that version is its baseline (`value` 'baseline'): the text it arrived with (an import, devot-mcp, a duplicate) or had from before history existed, kept without writing a version for every imported note. An accepted AI edit takes a version of the text it replaces and then one of the text it leaves, marked as AI's (`value` 'ai', `AI_EDIT`): its authorship. Quitting, moving a note to the Trash and opening the Activity sheet take a version of typing that has none yet.
- **Events:** title, notebook, status and pin changes are recorded when they are saved locally; quick title edits (within a minute of each other) update one event, which goes away when they end at the title they started from.
- **Compaction** keeps every version from the last 24 hours, the last of each hour for a week, the last of each local day before that, and always a note's ten newest versions (`KEEP_NEWEST`), whatever their dates; events, baselines and AI versions are small or needed, and kept (only plain versions, `value` null, are ever dropped). Ages are measured by the system clock, from now or from the note's newest version, whichever is earlier: the spacing between versions taken at real times decides, so a clock running fast (a session a day or more ahead, which makes the latest work look old) cannot thin a note's last day of work, and the ten newest versions bound what it can thin of a note with a version taken while it ran fast. A note whose newest version is dated after now (the clock was set back since it was taken) is left alone until the clock passes it.
- **Sweeps:** a sweep runs after a save of any note, at most hourly, so notes that are no longer edited are thinned too. It runs on a queue of its own: switching notes, the Trash, History, Activity and quitting never wait for it. The time of the last sweep is kept in the database (schema v13 `compaction`, one row), so a sweep, the first of a session too, looks only at notes with a version that has turned a day or a week old since the sweep before (`compactionWindows`), the only ages at which the policy keeps less; when no sweep ran yet, or the clock was set back past the last one, it looks at every note with more than one version older than a day. Storage lists the plain versions (baselines left out) of those notes 500 notes a call (`listCompactable`, command `revisions_compactable`), from covering indexes (schema v13 `revisions_history`, which history lists read too, and `revisions_by_time`): it scans only the window's versions and each listed note's, never a Yjs state. The dropped versions are deleted as the pages come, in calls of at most 200 (`compactRevisions`, command `revisions_compact`, which deletes only plain body versions); the last call records the sweep's time, so an interrupted sweep runs again. Restoring a backup first holds compaction (`holdCompaction`): no sweep starts, and the restore waits for a running one to finish, so a sweep never deletes from the restored database what it chose from the old one, nor records its time there (a restore from another main window holds `main`'s through Rust, see Backups); the window reloads after the restore, and a failed restore lets sweeps start again (`resumeCompaction`). Measured on 10,000 notes with 20 versions each (better-sqlite3, M1 Pro): a page takes about 95 ms and 1.1 MB the first time every note is weighed, and an hour's window about 15 ms. Tests check that the Rust and TypeScript statements are the same, their query plans, and that the UI tests' memory adapter answers like SQLite. devot-mcp never compacts (see AI).
- **Restore** computes the text difference from the current body to the version and applies it through the same path as `NoteService.setBody`, as one Yjs transaction; the version's state is never written back. Unsaved edits become a version first. The core returns the transaction's update; the editor applies it to its replica as one undo step of its own (`isolateHistory`), not joined with typing just before or after, so Cmd+Z takes back the whole restore and Shift+Cmd+Z brings it back. A restore is an edit like typing: undoing it is a new change the core saves. A restore made while the note is not in the editor reaches it as a change from outside, which undo does not take back. An image the version shows whose attachment was purged meanwhile does not come back (see Purging attachments).
- **UI:** the Revision History sheet (`RevisionHistory.tsx`) opens from the note context menu, the editor toolbar's More menu and View > Revision History… (Option+Cmd+Y). It lists versions (time, characters added or removed since the version before; the oldest kept version, which has none before it, reads "Earliest version" with its length; an AI version reads "Edited with AI" before its change) and events, newest first, as a keyboard-navigable listbox. Selecting a version shows a line diff (`src/core/diff.ts`, Myers' algorithm, unchanged runs folded) of the changes in the note since that version, with Restore.
- **History bar** (`HistoryBar.tsx`, `historySteps.ts`): View > Show History Bar (the `historyBar` editor setting, off by default; Rust toggles it and relabels the item Hide History Bar, and the palette has the same command) shows the open note's kept body versions along the editor's bottom edge as ticks on a time axis from the oldest version to now, each tick's height the square root of its characters changed. The handle is an ARIA slider with one tab stop: its steps are the versions, oldest first, and then the current text, each named by its date and totals ("Earliest version", characters added or removed). Dragging the handle shows the version under it while the button is held, and letting go returns to the current text; a click on the bar or a slider key (arrows, Page Up and Down, Home, End) keeps the version shown until Escape (pressed in the bar or the overlay), End or another note. A shown version is a read-only overlay over the editor (and the preview beside it), never a change to the note, and the panes under it are inert while it shows: the current text with what changed since that version (`inlineDiff` in `src/core/diff.ts`, the line edits split into words), removed text struck through, added text highlighted, the rest dimmed, and the version's date on the handle. The overlay is drawn from the editor's live text, so an outside change (sync, devot-mcp) while a version shows appears in it at once. Selecting struck text (or tabbing to a struck run, which takes it in whole) offers Restore This Passage (`NoteService.restorePassage`): the removed text the selection takes in goes back where it stood (`passageInserts`, before any text that replaced it; text the note still has is left alone) as one edit, one undo step, with the text before and after kept as versions; Restore Whole Version is Revision History's Restore. Once a version is over a day old, the bar says that compaction keeps one version per hour for a week and one per day before that.

### Activity heatmap

- **What it shows:** View > Activity… (no shortcut) opens the Activity sheet (`src/renderer/src/Activity.tsx`): the last 52 weeks as a grid, weeks as columns, Monday first (ISO weeks; the current week is the last column, days after today are blank). Each square is a day, shaded from five theme colours (`color.activity.level-0` to `level-4`, light and dark) through CSS classes; a summary, a legend and a footnote go with it. Nothing is uploaded and no new data is recorded: it is counted from the notes and the revision history already on this device.
- **What a day counts** (`src/core/activity.ts`): notes created (`created_at`); notes edited, each once (a body version or a title change); and characters changed: for each body version taken that day, how far the note's text length moved from its version before (from empty for its first). Opening the sheet first keeps typing that has no version yet as one (`NoteService.activity`), so it counts at once, and quitting does the same, so it counts on the day it was typed. Notebook, status and pin changes are not writing and never count, nor move a count: a version they lead to is dated by the body's own last save. Text a note had before its history began (an import, devot-mcp, a duplicate, a note from before history existed) is never counted: its baseline is not activity, only the version the next one is measured from. Typing a crash left out of a version counts on the day of the body's last save, once the note is changed again; typing a crash lost on a note without history is not counted. Notes in the Trash count; purging a note removes its activity with its history.
- **Honest about compaction:** history keeps every version from the last day, one per hour for a week and one per day before that (and each note's ten newest versions), so older days may count only each note's net change over the day (typing 500 characters and deleting 400 shows 100), and never more than was typed. The sheet says so.
- **Days and zones:** a day is the local calendar day of the system time zone: an instant's day is its wall-clock date there (`localDay`, from the zone's offset at that instant), so DST days of 23 or 25 hours and zones such as +05:45 need no special case. Compaction uses the same day. Unit tests inject the zone (Los Angeles across both 2026 transitions, Shanghai, Kathmandu).
- **Shades:** an idle day is level 0; a day with activity but no characters changed is 1; otherwise a day's level is its percentile rank among the days that changed characters, in four steps, so the busiest day is always 4 and one huge import does not wash out the rest.
- **Storage:** `listActivity(since)` returns the notes created since then and the body versions (baselines left out) and title changes taken since then, each body version with the length of the note's version before it (a baseline included) (ordered by time, then length, then storage order). The Rust store (`activity_list`), the better-sqlite3 adapter and the UI tests' memory adapter implement it; a test checks that the Rust and TypeScript statements are the same and that the memory adapter answers like SQLite. Migration 0012 adds covering indexes (`notes_created`, `revisions_by_time`, `revisions_activity`), so counting reads only the year in view and never a Yjs state; a test checks the query plans, and a benchmark keeps 10,000 notes with history under 250 ms.
- **Activity strip in the note list** (`ActivityStrip.tsx`, `buildStrips`): each row shows its note's last 14 local days (today last) as small squares in the same five colours, named for assistive tech by its active days, each square titled by its date and totals; Settings > General > Show Activity in the Note List (the `activityStrip` editor setting, on by default) hides it. A note with no edit in its 14 days shows no strip. The strip ends the row's meta line, which stays one line: what does not fit is cut, never wrapped under the strip. A day counts the note's body versions and title changes as the heatmap does, and typing not kept as a version yet counts today, without taking a version. Shades are fixed steps, not percentiles, so a day keeps its shade as rows scroll in and out: level 1 for a day with activity, then 2, 3 and 4 from 100, 500 and 2,000 characters changed. Rows read their strips with their excerpts, in one read so a change renders a row once (`withStrips`; the rows rendered only, again when a note's `updated_at` moves), through `listNoteActivity(ids, since)` (command `activity_notes_list`, at most 500 IDs a call like `notes_bodies`): the same columns as `listActivity`'s versions, from schema v13's covering `revisions_history` index, so it reads the 14 days of the notes asked for and never a Yjs state. A test checks the Rust and TypeScript statements match and the query plan; a benchmark keeps 60 rows of a 10,000-note library under 10 ms and 500 rows proportionally.
- **Keyboard and assistive tech:** the grid is an ARIA grid with one tab stop (today when it opens); arrow keys move a week left or right and a day up or down, Home and End go to the first day and today; up and down stay within the day's week. Each day's square is named by its date and totals (from the catalog), which a line under the grid also shows for the day under the pointer or in focus.

## Markdown dialect

- CommonMark and GFM: tables, task lists, strikethrough, autolinks, footnotes.
- YAML front matter: lines between `---` fences at the very start of a note, closed by the first later line that is `---` (spaces or tabs may follow a fence). The preview, import and the editor read it alike (the editor through a Lezer Markdown extension, `src/renderer/src/editor/markdown.ts`): nothing inside it is Markdown (the editor's Markdown helpers, such as pasting a URL as a link or HTML tag completion, are off there), the editor shows it in the secondary and tertiary text colours, and formats leave its lines alone. A note that starts with `---` and has no closing fence starts with a thematic break.
- Alerts: `> [!NOTE]`, `> [!TIP]`, `> [!IMPORTANT]`, `> [!WARNING]`, `> [!CAUTION]`.
- Math: `$…$` and `$$…$$`. Mermaid in fenced code blocks. Emoji shortcodes (`:tada:`).
- Inline code that holds only a colour (`#RRGGBB`, `rgb(…)`, `hsl(…)`) renders a swatch.
- Note links: `[title](devot://note/<id>)`. Attachments: `![](devot://file/<id>)`. Links resolve by ID, so renaming a note never breaks them. An attachment belongs to one note (`files.note_id`; see Purging attachments), so a note made from another note's text (Duplicate, New Note from Selection, a note from a template) gets its own copies of the images the text shows: each under a new ID, copied in one write (`files_copy`), with the links changed to the copies' IDs (only the ID; a size preset such as `#half` stays). Duplicate and New Note from Selection store the new note already showing the copies (`insertNote` in `src/core/notes.ts`; Duplicate changes only the IDs' characters, as edits to a copy of the source's Yjs state), then copy the files; if they cannot be copied, the new note is purged and the copy's error is thrown (the window logs its code).
- **Purging attachments:** purging a note deletes its attachments, except each one that another note, not purged (live or in the Trash), still shows: its Markdown holds the address `devot://file/<id>` as written (in capitals, cut short or only in the title it does not count). That one passes to such a note, a live one before one in the Trash, then the smallest ID, in the purge's own transaction, so no attachment is ever left to a purged note. A link can reach another note without a copy (cut, copied or dragged Markdown, Paste as Plain Text, devot-mcp's `create_note` with a body from `read_note`, a restored version, a duplicate or a note from a template made before those copied their images), and its image keeps working; emptying the Trash deletes only the images no note left shows. The Rust store and the TypeScript adapter run one statement (`HAND_OVER_FILES_SQL`, a test compares them); it finds the notes that show an attachment through the search index (a phrase match on the address, then the address checked as written), never by reading every note, and the UI tests' memory adapter follows the same rule. The core saves pending edits before it purges, so a link pasted a moment before counts. A link only an older version in a note's history shows keeps nothing (history is local and its states are not searched): restoring that version brings back the link, not the image. The rule reads only the notes' text, so devices that hold the same notes keep the same attachments; attachment sync (#13) has to follow it.
- **Images:** an image's size preset is the fragment of its URL: `![](devot://file/<id>#small)`, `#half` or `#full`; no fragment is Auto (its own size, no wider than the page). Other Markdown tools ignore a fragment when they load an image, so they show it at its own size. `src/core/images.ts` reads and writes it (round-trip tests in `tests/core/images.test.ts`); only the destination changes, and a URL with another fragment cannot take a size. The preview's `devot.images` renderer turns the preset into a class (Small is `size.image-small` wide, Half and Full half and all of the page) and loads the image without it; it also marks where each `![alt](url)` is in the Markdown (`data-image-from`, `data-image-to`), so the image menu can set a size from the preview (reference images and raw HTML have no destination of their own and get no Size submenu). The size is set from the image context menu or the palette (`image.size*` commands, for the image at the cursor or the first on its line), as one editor transaction, after checking the text there is still that image.
- **Pasting and dropping images:** each image goes straight from the page to storage (`src/renderer/src/attachments.ts`) and its link goes in at the cursor or the drop point. The page refuses what Rust would refuse (over 10 MiB, not a supported raster image) before sending the bytes. An image that cannot be stored (refused as not an image or too large, or the database busy past its timeout) is skipped, logged by code and reported in a notice: how many images could not be added and the first one's code. The link lands where the image was pasted or dropped, not where the caret is when the file is stored: the place is remembered as a Yjs relative position (`src/renderer/src/editor/anchoredInsert.ts`), which follows every edit made meanwhile (text typed at the place goes after the link) and means the same place in the editor's replica and in the core's document. If the note was left meanwhile, `NoteService.insertAt` puts the link into the note at that place (the file is never left without a link); if the note is open again by then, its editor takes the link. Only a note deleted meanwhile loses it, and its files go with it. The caret moves after the link only if it is still at the place.
- **Image viewer** (`src/renderer/src/ImageViewer.tsx`): double-clicking an image in the preview (or under its line in the editor) opens it in a modal over the whole window, fitted to the window or at its actual size (scrolling when larger; a segmented control or a click on the image switches). Tab and Shift+Tab go round every stop of it (Fit, Actual, Close, the scrolling stage) without leaving the dialog, Escape or Close dismisses it, and focus goes back where it was. The registry's `image.view` (View Image, no default key) opens it from the palette for the attachment image at the cursor, so it has a keyboard route; the Preview offers no key for it (its images are not focusable).
- Typing `[[` opens note search (full-text, live notes only; the first notes of the list for an empty query) and inserts a standard note link, replacing the `]]` that bracket closing added. The popup never opens in code (fenced, indented or inline), HTML, comments, front matter or a link's address (the places the slash menu skips too), nor while the parser has not reached the cursor. A lookup runs on every key, so it finds notes as stored (`search` with `flush: false`) and never saves the open note, and an empty query takes only the notes the popup shows. Picking "New Note …" closes the popup at once (a second Return cannot make a second note), moves the cursor after the brackets and remembers the `[[query]]` as a range that follows the edits made while the note is made; when the note exists, exactly that range becomes the link, and text typed before, after or elsewhere is untouched. If the brackets were edited meanwhile or the editor was closed, nothing is linked and the new note is deleted again (as New Note from Selection does), so no note is left behind. There is no `[[wikilink]]` storage syntax.
- **Link index:** the `links` table (schema v7) holds, per note, every `devot://note/<UUIDv7>` in its Markdown (`noteLinks` in `src/core/links.ts`; the v7 migration backfills with the same rule in SQL). Each body write replaces the note's rows in the same transaction, only when the write lands; purging removes them; trashed notes keep theirs. A property test checks the table always equals the stored bodies.
- A video URL alone on its own line renders as an embedded player.
- **Editor commands**: Insert Horizontal Rule (Shift+Cmd+H) is a format command (`src/renderer/src/editor/rule.ts`, in the Format menu after the alerts): it puts `---` on a line of its own after the line with the cursor (the line a selection ends on, whose text stays), with a blank line before it so the text above never becomes a setext heading, and the cursor on a new line under it; a blank line, an empty list item or an empty heading takes the rule itself (a setext underline stays). In a quote it keeps the quote markers; in a table or a setext heading it goes after the block; in code, HTML and front matter it does nothing. A rule that would be the note's first line, or could close a `---` the note starts with, is `***`, since `---` there would make front matter. New Note from Selection (the palette, while text is selected) moves the selected text into a new note in the open note's notebook (none when that notebook was deleted), titled after its first line with text (code fences, rules and setext underlines skipped), without quote, list, task or heading markers (`src/core/extract.ts`, `NoteService.extract`: the body goes in as Yjs operations and the note is stored with it in one write, never empty; images the text shows become the new note's own copies under new IDs (`files_copy`), since purging a note deletes its attachments, and the source keeps its files, so undo there shows its images again), and leaves a note link to it in its place, as one undo step; the open note stays open. Undo puts the text back but keeps the new note (undo reverts edits to the open note only). A selection that starts or ends inside code, an HTML block or front matter is not offered (a whole block may be selected): a link there would be plain text. The range is tracked through edits made while the note is created (`src/renderer/src/editor/extract.ts`); if the selected text itself was edited meanwhile, or another note was opened, the text stays and the new note is deleted again. Paste as Plain Text (Shift+Opt+Cmd+V, and the palette) inserts the clipboard's text as it is: no link, no image, no autolink. It reads the clipboard through Rust (`clipboard_read_text`): WebKit lets a page read the clipboard only during a key press in the page and then shows its own Paste button, and the palette runs commands after its own keys.
- **Context menus in the note**: a right-click in the editor text (or Shift+F10 / the Menu key at the caret) shows a native menu (`editor/editorMenu.ts`, shown by Rust: `editor_menu_popup`, `editor/systemMenu.ts`): Open Link and Copy Link Address on a link (`linkAt`), Look Up, New Note from Selection and an Edit with AI submenu (see AI > Edit with AI) with a selection, Undo and Redo (CodeMirror's history), the system's Cut, Copy, Paste and Select All (which act on the web view), Paste as Plain Text and a Speech submenu. The page lays the menu out as for any context menu and sends it to Rust with the word at the point (`spellingWordAt`; none when a selection is something else), which builds an NSMenu in `native/macos.rs`, waits until it closes and answers with what was picked. Rust adds what the Tauri menu API cannot hold: the system's guesses when that word is misspelled (`NSSpellChecker`; a guess picked replaces the word as one undo step) and Learn Spelling, then Writing Tools (`NSMenuItem.writingToolsItems`), Spelling and Grammar (Show Spelling and Grammar, Check Document Now, Check Spelling While Typing, Check Grammar With Spelling, Correct Spelling Automatically) and Services (the app's Services menu for as long as the menu is open). Those items have no target: AppKit sends them to the web view and enables and checks them as in its own menus. Off macOS (the web view's user agent says so) the Tauri menu API shows the page's items alone. The app's own Services menu comes back through a drop guard, also when AppKit throws, and Writing Tools is added only when `NSMenuItem` answers `writingToolsItems`. A harness test builds the menu on the main thread and checks the guesses, keys, system items and that a pick arrives. A right-click outside the selection moves the caret there first. The preview has its own (`preview/previewMenu.ts`: Copy Link Address on https and note links, Look Up, Copy, Select All limited to the preview, Speech; images keep the image menu). Look Up and Speech are Rust commands (`text_look_up`, `text_speak` in `native/macos.rs`): Look Up shows the system dictionary for a word at the pointer, Speech speaks the selected text the page sends with a speech synthesizer (the editor draws only the lines near the view, so the web view's own selection can hold a fraction of a long one), uses the web view's own `startSpeaking:` only when the page sends none, and stops both (`stopSpeaking:`); each selector is checked with `respondsToSelector:` and a harness test checks them on a real web view. A tag chip and the notebook label in the note header have menus too (`headerMenus.ts`): Tag Settings, Remove Tag, Filter by Tag, Copy Tag ID; Open Notebook (also the command `note.showNotebook`) and Copy Notebook ID. WebKit's own Inspect Element is not offered.
- **Pasting URLs** (`src/renderer/src/editor/paste.ts`; the Markdown language's own paste-as-link is off, so a paste is handled once): a URL (`https:`, `http:`, `mailto:`, `devot:` such as a copied note URI, or `www.` given `https://`) pasted over selected text makes the text a link to it, the way Option+Cmd+K links it (line by line, widened over syntax it would cut through, lone brackets escaped; in the address `|`, which would end a table cell, `\`, which would escape the next character, and unpaired parentheses are percent-encoded), the cursor after the link; over a link, a selected address, code or front matter it replaces the text as usual. A lone URL (nothing selected) goes in as Settings > Editing > Paste URL as Link says: as copied, as an autolink `<url>`, or as a link with empty text `[](url)` with the cursor in its text; inside code, front matter, a link or an autolink it goes in as copied.
- **Formatting:** selecting text shows a toolbar above it (below when there is no room), and each format has a shortcut. Every format is a named command in `src/renderer/src/editor/formats.ts` that turns the editor state into one transaction (one Yjs update, one undo step) editing the Markdown source: bold `**`, italic `*`, strikethrough `~~`, highlight `<mark>` (there is no `==` syntax), inline code, links and ATX headings (a setext heading becomes an ATX one, or a paragraph, without its underline). Applying a format the whole selection already has removes it; a multi-line selection is formatted line by line, after block markers, leaving code blocks, thematic breaks, HTML blocks, front matter and table delimiter rows alone (table rows are formatted cell by cell). New markers and links widen over syntax they would cut through, and marker characters or lone brackets inside them are escaped. At a cursor, a format inserts an empty pair to type into, except where the pair would make block syntax (`~~~~` opens a fence, `****` is a thematic break); there it does nothing, as it does at a cursor in code (a blank line of a code block included). A command does nothing while the parser has not reached the selection. The toolbar works out its pressed buttons again on every selection change, so it reads at most 300 lines of selection (all ranges together; `TOOLBAR_MAX_LINES`): a longer selection shows no button as pressed except Heading, and the commands still act on the whole selection. Emphasis, strong and strikethrough markers must flank their text (CommonMark's rule: a marker next to punctuation opens or closes only against white space or punctuation on its other side, and CJK prose has no spaces), so punctuation at the selection's edges that would keep them from parsing goes outside them (an ideographic full stop selected with the text before it stays outside: `XX**YY**<stop>ZZ`; `a **word**.b`). Markers are written only where the editor's parser (Lezer, which counts every symbol as punctuation) and the preview's (micromark, which counts ASCII punctuation and Unicode punctuation) read them alike (both read the one UTF-16 unit beside a marker, so an emoji or other character outside the BMP is never punctuation to them); a selection of nothing but such punctuation is left as it is. The selection keeps the punctuation, and the same key on it takes the format off again. Inline formats, headings and links leave an alert's `> [!KIND]` header line alone, and a link made right after `!` escapes the bang (`\!`), which would otherwise turn it into an image. The formats take only the quote and list markers the parser has as the start of a line's text: `2020.` or `3)` on the second line of a wrapped paragraph is text (it is no list item in CommonMark), so a list or heading format keeps it (as an item's text it is escaped, `2020\.`, so it is not read as a nested list). Headings go after list markers; task items do not take headings. Bracketed text that is not a link (`[draft]`, `[[Note]]`) is wrapped like other text, never unlinked; image text takes no link. Block formats (`src/renderer/src/editor/blocks.ts`) act on every line the selection touches, after the line's quote markers: a code block wraps the lines in a backtick fence longer than any fence among them (inside their shared quote, or at the text of the list item they continue); in an empty list item (`2. `, from Shift+Cmd+C) the fence goes after the marker and its lines are lined up with the item's text (`2. ` + three backticks), under the box of an empty task item, and on an indented blank line at the column of the item it continues and unwraps the fenced block a selection is in; bulleted (`- `), numbered and task (`- [ ] `) lists toggle, and switching kinds converts the markers; quotes toggle `> `; alerts add a `> [!KIND]` line (the toolbar's Alert pop-up picks Note, Tip, Important, Warning or Caution) and are changed or removed as a whole block. When a marker gets wider or narrower, the lines under its item move with it, so nesting is kept; numbered lists that gain an item are renumbered from their first number, and the items after one that leaves a numbered list count from 1 again, in the same step. Only the selected lines change; a line next to them may still read as the lazy continuation of the block above, as Markdown has it. Lines of fenced code, tables, rules and HTML blocks are left alone, and front matter by every block format, the code block included; lists also skip setext headings and lines that continue an item (unless only those are selected). A line that continues a list item is quoted inside that item, unless the item's own line is selected too; a list item is quoted with its children and a setext heading whole. Lines of fenced code inside a quote are code too. Code blocks wrap each range of a multiple selection on its own and take in the whole of a fenced block the selection cuts into. Shift+Cmd+C makes a code block in the editor and copies a note's URI on a note list row; each area handles only its own keys. The toolbar, the shortcuts, the menu bar's Format menu, the command palette and the slash menu run these commands. Their keys come from the command registry (see Commands and shortcuts).
- **Return in lists and quotes** (`src/renderer/src/editor/enter.ts`, ahead of the Markdown language's own Return): Return on an empty list item (including the second item of a two-item list, which the language's Return would turn into a loose list) or on an empty quote or alert line leaves it with one blank line between it and the cursor, so text typed there is a paragraph of its own (without the blank line it would continue the last item lazily); a nested list or quote goes out one level (the outer quote's or item's markers stay). With no line of text above, or a blank one, the marker only goes. On an empty quote line in the middle of a quote (a line of the quote follows, also when the line is in a list in the quote), or in a code block in a quote, Return continues the quote instead (keeping the indent typed after its markers), so it is never split in two; a quote that opens a list item (`- > `) is left for the empty item (`- `). Markers are read from the syntax tree with the scan the formats use (`lineMarks.ts`). It is one transaction and one undo step.
- **Slash menu:** typing `/` at column 0 of a line opens a list at the cursor (`src/renderer/src/editor/slashMenu.ts`) in three groups, each with a small header that scrolls with the list: Basic Formatting (Blockquote, Codeblock, Heading 1 to 4, Horizontal Rule, Image File, Link, Ordered List, Remote Image, Task List, Unordered List), Alerts (Caution, Important, Note, Tip, Warning, each icon in its alert colour) and Other (Note Link). Each row shows an icon, the label and, on the right, the Markdown it writes. Most items are registry commands (a format above, or an insertion from `src/renderer/src/editor/insert.ts`); Remote Image writes `![alt](url)` as a snippet (Tab goes from `alt` to `url`), Image File takes the query out and opens the system file panel for images, stored as a pasted image is, and Note Link puts `[[]]` there and opens the `[[` note popup. Table is a palette command only. The text typed after the slash filters the list: a case-insensitive substring of the label, ordered by where it matches, then by the menu's order (`ist` gives Task List, Ordered List, Unordered List); the matched letters are bold. An item whose command would do nothing there or take a format off is left out. Up and Down wrap around. Return picks: the `/query` goes and the command runs in its place, as one transaction and one undo step. A query that matches nothing closes the list, and that slash does not open it again (Backspace included); nor does Escape's or a lost focus's. It never opens with several cursors or a selection, nor in code, HTML, comments, front matter, or a link's address. The empty line holding the cursor shows `Type '/' for commands...` as ghost text (drawn by CSS, not text of the note), and an empty note shows a chip that runs New Note from Template. The same popup style serves the `[[` note popup, `:` plus two or more word characters (emoji shortcodes; picking one inserts the emoji) and `> [!` (the alert kinds). While an input method composes, no list opens, and keys of a composition never reach an open list (WebKit may report the Return that ends one, key code 229, after it has ended). The popups, their sources and the editing aids around them are put together in `src/renderer/src/editor/completions.ts`.
- **Code blocks in the editor** (`src/renderer/src/editor/codeBlocks.ts`): every line of a fenced block, its fences included, sits in one box (line decorations; an unclosed fence boxes the rest of the note, as the parser reads it); the fence takes the markup colour and its info string the heading colour. The box's own background carries the active line's tint, so it keeps to the box's rounded edges and its margins; while text is selected, the selection's tint stands instead. The editor pads both sides of a line equally, and that padding is the note's text column. A code block's box and a table's sit on that column, with the text inside set further in, so the box lines up with the prose. CodeMirror's full rows stop at the first line's padding; a row that stops inside the box grows out to the column, and a short first or last row reaches the rest of the way (`editor/selectionEdges.ts`), so the tint wraps the box and lines up across formats. A quote's bar is drawn in the line's border and shifted out to that same column, so a quote keeps every line's padding and does not shift the selection's width. While the selection is in a block that is not in a quote or alert, a copy button in the box's top-right corner copies the code without its fences (and without the indentation of a list item's block). On an opening fence line, right after the fence, a list offers every alias `@codemirror/language-data` knows with the language's name, filtered fuzzily; picking one writes it after the fence and keeps the cursor there. Code Block on a blank line (from the slash menu, the toolbar or its key) writes the fences around an empty line, puts the cursor after the opening fence and opens that list; a fence typed by hand opens nothing and gets no closing fence. In a block, Tab inserts the indent unit and Return starts a line with the block's quote or list prefix and the indent its language gives (`src/renderer/src/editor/codeIndent.ts`): the line's own, a level in after what opens one (a bracket; a trailing colon in Python and YAML; `do`, `then` and block keywords in Ruby, Lua and shell; an open tag in HTML and XML), a level out after `return`, `pass`, `break`, `continue` or `raise` in Python; between a pair (brackets, tags) the closing one goes to a line of its own. The indent unit (Return and Tab) is the block's own when its lines are indented, else its language's convention (a tab for Go and Makefiles, four spaces for Python, Rust, Java, Kotlin, C, C++, C#, Swift, PHP), else the editor's.
- **Tables:** while the cursor is in a GFM table, Tab and Shift+Tab go to the end of the next and previous cell (Tab in the last cell adds a row), Return goes to the same column of the next row (to its first cell after a row's closing pipe; adding a row at the end; on an empty last row it removes that row and leaves the table below a blank line; before a row's first character it opens a line above the row as elsewhere, so a table at the top of a note can get a line before it), Option+Return inserts a row below, and Option+Up and Option+Down move the row. Outside a table, with several cursors, or with a selection over several lines, these keys do what they do elsewhere in the editor (Tab indents the line, Shift+Tab outdents it; Control+Tab leaves the editor, see Keyboard navigation). The command palette offers, while the cursor is in a table, inserting, deleting and moving rows and columns, setting a column's alignment (left, center, right, none) and Format Table. The model (`src/renderer/src/editor/table.ts`) reads the table as GFM does: cells are trimmed of spaces and tabs only (U+3000 and U+00A0 are cell text), a pipe ends a cell unless a backslash escapes it, also inside a code span, outer pipes are optional, and ragged rows are padded with empty cells (no cell is dropped). Every table command and key prints the whole table formatted (outer pipes, columns padded to their widest cell by display width, wide East Asian characters and emoji counting two, cells placed by their alignment, the delimiter row keeping its markers) as one transaction, one undo step, like the formats (`src/renderer/src/editor/tableCommands.ts`); a table in a quote or a list keeps each line's markers. A row can also be typed by hand (`src/renderer/src/editor/tableTyping.ts`): on an empty row that Tab, Return or Insert Row left the cursor in, and while the cursor stays on that row, the first pipe typed is the row's opening pipe (the cursor goes to the first cell), a pipe typed at the end of a cell's text or in an empty cell goes to the next cell (from the last cell, past the closing pipe) and formats the table, and a space typed right after such a pipe is dropped as padding; so `| 1 | 2 |` typed after Return fills two cells. A pipe inside a cell's text, after a backslash or after the closing pipe, input during IME composition or with the completion list open, and every other row are typed as written. Each cell's typing and the pipe that ends it are one undo step (the padding a pipe removes is taken next to the cursor, so its change joins the typing). Changes from elsewhere (sync) keep the row being typed.
- Import keeps the source text as-is. `[[…]]` from other tools stays plain text.

### Import

File > Import has three items: Markdown Files… (`.md`, `.markdown`), Markdown Folder… (one or more folders of Markdown files) and HTML Files… (`.html`, `.htm`). A notebook's context menu has the same three items in its Import submenu: the web view starts them with `import_pick(kind, bookId)` (Rust checks both), and the session's READY payload carries that notebook as `destination`, so the sheet skips choosing one (a folder's tree offers Import into it; picked files import at once). If the notebook is gone by then, the sheet asks as usual. A cancelled panel sends nothing.

- **Reading:** Rust shows the panel, scans what was picked and keeps it as an import session (`src-tauri/src/import.rs`); the web view never names a path outside it. A folder scan runs on its own thread and reports how many Markdown files and images it has found (`devot://import-scanning`, `devot://import-progress`, then `devot://import-ready` or `devot://import-failed`); closing the session (`import_finish`) cancels a scan still running. The UI reads files by session ID and relative path (`import_read`, `import_attach`, `import_finish`): relative to the folder for one folder, starting with each folder's name (made unique) for several, and for picked files their names (starting with their folder's name when they come from several folders). Hidden files and folders are skipped. Symbolic links are not walked (a target inside the folder is imported under its own path; a link to a folder or Markdown file that is hidden, outside it or missing is reported); an image link may go through a link, but never to a hidden file or out of the folder (for picked files, only an image file in the file's own folder or one folder below it, links followed, such as `img/shot.png` or a saved page's `Page_files/`: picking one file never opens the rest of a large folder to the import). Markdown files and images over 10 MB are left out and listed as skipped.
- **The sheet** (`src/renderer/src/ImportDialog.tsx`): a folder import is a wizard in one sheet: the scan with its progress; a tree of the folders found, each with its Markdown files, images and size and whether it becomes a notebook (`importTree`, `src/core/importTree.ts`), and the files that will be skipped; the destination (a notebook, or No Notebook; the open notebook to begin with); then the import's progress and its result: how many notes were imported, skipped and failed, and every file or image that was not imported, with the reason and its code (never note content). Picked files go straight to the destination. Cancel (or Escape) ends the session at any step before Import, and nothing is written to the database before Import is pressed. Imports picked while a sheet is up wait until it is closed; their scans go on meanwhile.
- **Notebooks:** notes go into the destination. One picked folder is not a notebook itself: its files go into the destination, and every folder inside it that holds an imported note (at any depth) becomes a notebook nested as on disk. When several folders are picked, each becomes a notebook too. Picked files all go into the destination. Folders with no imported notes under them, such as image folders, do not become notebooks. An empty folder imports nothing. The destination is shown afterwards (or the one top-level notebook made, with No Notebook).
- **Title:** Devot's own front matter `title` (see below), else the first level-one heading, else the file name without its extension (for HTML, the page's `<title>` comes before the heading). The body keeps its heading. File and folder names are composed (NFC) first, as macOS may give them decomposed and typed text, which searches compare by code point, is composed; CJK compatibility ideographs stay as they are. A note whose title is not composed so gets its title in the front matter on export.
- **Front matter:** only front matter that Markdown export added (its first line is the comment `# Devot metadata`) is read, as YAML with the `yaml` library (comments, quote escapes, block and multi-line scalars, lists over several lines; a key whose YAML is not valid is read from its line as far as that goes): its `title` (exactly, only cut to the limit), `tags` (a leading `#` kept; the escapes of double-quoted values read) and `status` become the note's, and it is left out of the note. Any other front matter is the note's own text: it stays in the body as written and nothing is read from it (its `title`, `tags` or `status` included). A key's line may hold a line or paragraph separator (U+2028, U+2029).
- **HTML:** an HTML file is sanitized (the default GitHub-style schema; scripts, styles, frames, objects and inline SVG or MathML are dropped with their content, event handlers, comments and `javascript:`/`data:` URLs go) and converted to Markdown (`src/core/htmlImport.ts`, with GFM tables, task lists, strikethrough and math; thematic breaks as `***`, so a converted page never starts with a front matter fence). From there it imports as a Markdown file does, so its local images become attachments. Before the page is sanitized, images embedded as `data:` URIs (PNG, JPEG, GIF, WebP, AVIF or HEIC in base64, as Export as HTML and page savers write them) are taken out and stored as attachments through `putFile` (checked as an upload is, `validate_upload` in Rust), their links pointing at them; a lazy-loaded image's `data-src` wins over its placeholder `src`; and MathML that carries its TeX (an `application/x-tex` annotation, which the preview's MathML keeps, so an exported page has it) becomes `$...$` or a `$$` block again. Whatever else the conversion leaves out (inline SVG such as a drawn diagram, MathML without TeX, frames, objects, media, other `data:` or local-file image URLs) is listed in the result as not imported (`E_IMPORT_HTML_CONTENT_DROPPED`, each kind once per file, the first 100 and then `+N` for the rest; an image listed so is left out of the note), and so is an embedded image that could not be stored (its link is left empty).
- **Images:** local images (`![](path)`, reference definitions that images use, and the `src` of an `<img>` in raw HTML, read as HTML reads it) resolve against the note's folder (a leading `/` means the import folder) and become attachments; Rust reads them from disk and checks their format by their bytes. Only their destinations change, to `devot://file/<id>` (a size preset stays: `img.png#half` becomes `devot://file/<id>#half`; any other fragment or query is dropped), and an image used twice in a note, at any size, is one attachment. Remote images stay as they are. A `\` in a destination or a file name is an ordinary name character (only `/` separates folders, in Rust's `resolve` too), so `C\C++ notes.md` imports and `![](shots\one.png)` names a file called `shots\one.png`. Missing or refused images and images outside the folder keep their original link and are listed as not imported, and so is an image whose link cannot be found in the text to rewrite. A destination is read as CommonMark reads one: it ends only at an ASCII space or control character (a screenshot's name may hold a narrow no-break space), its parentheses balance at any depth, and character references count (`Q&amp;A.png` names `Q&A.png`).
- **Parsing off the core worker:** each file is converted (HTML) and parsed for its title, front matter and image links in a worker of the import's own (`src/renderer/src/import.worker.ts`, started for each import and ended after it), so the saves queued in the core worker go on meanwhile however long a large page takes; the core worker only stores what comes back. A worker that cannot start or fails hands the files back to the core worker (logged as `W_IMPORT_WORKER_FAILED`). Reading, converting and parsing take time linear in the size of a page: library steps that looked each node up among its siblings, took the whitespace between blocks out one at a time, or read the rest of the page for each line's end, were quadratic in a parent's children or a page's lines, and are patched (`patches/`).
- **Bodies:** each body reaches its note as Yjs operations (`NoteService.setBody` applies a text diff), never by writing the snapshot. A file that fails part-way leaves nothing behind (its note is deleted with its attachments, and so are notebooks made only for it; tags are added last) and is listed as not imported.
- **Line breaks:** `\r\n` and a lone `\r` become `\n`. The editor counts a CRLF as one character and the Yjs text as two, so a body that kept `\r` would put every later edit in the wrong place.
- **Lossless:** apart from image destinations and line breaks the snapshot equals the source text byte for byte, so an export that writes the attachments back and restores their paths gives the original files (with `\n` line breaks).
- **Backups and quitting:** an import and the Backups dialog never overlap: Backups… chosen during an import opens once the import's sheet is closed, and a folder picked while Backups is open is imported once it closes, so a restore never mixes with an import. Quitting stops an import after the file it is on; only a file still unfinished when the quit allowance (2 s) runs out can be left as a note with an empty body.
- Notes get the import time as their creation and update time.

### Export and print

The note context menu has Export as HTML…, Copy as HTML, Copy as Simple HTML, Export as Markdown…, Export as PDF… and Print… (Shift+Cmd+P, anywhere in the window; Cmd+K is the palette); the palette lists them for the open note. With several notes selected, the menu keeps only Export Selected Notes as HTML… and as Markdown…, which write the notes side by side in one new folder (`Devot Export`), named after their titles and numbered on a clash; the others act on one note (Shift+Cmd+P does nothing then). The notebook context menu has an Export submenu (as Markdown…, as HTML…) for the notebook with its sub-notebooks. File > Export > All Notes as Markdown… and as HTML… (also in the palette) export every note into one new folder (`Devot Notes`): each top-level notebook a folder as in a notebook export, in sidebar order, the notes in no notebook (or in a deleted one) at the top, Templates and the Trash left out. All three use the notebook's folder panel and session.

- **Panels and files:** Rust shows the native save panel (a note) or folder panel (a notebook) and keeps the choice as an export session (`src-tauri/src/export.rs`): the folder, opened once when it was picked and never looked up by its path again (see Security). The web view writes by session ID and a relative path, which Rust checks (plain visible components, the session's extension). Every file is written to a new temporary file in its folder and renamed into place, never through a link (see Security), and the folders on its way are made one by one, each opened from the one before as a real folder, and the file is written in the folder so opened (a link in the way fails the file, never followed; one swapped in after the check is never reached). A notebook goes into a new folder named after it (`Work`, or `Work 2` when that exists), so nothing on disk is replaced; a note replaces only the file the save panel confirmed. Logs carry codes and IDs only. A failure shows what did not complete (an export, a print or a copy) with its code in a notice; notices stack in the window's bottom right corner, so a backup's and an export's never cover each other.
- **Markdown** (`src/core/export.ts`): a note is one `.md` file named after its title; a notebook is a folder, its sub-notebooks folders inside it, its notes files in their notebook's folder. Names are made file-safe (no `/`, `:`, control characters or leading dot; at most 200 bytes) and numbered when two would clash as macOS sees names, whatever their case or the form of their accents, or, to be safe, a compatibility form that macOS keeps apart, `x²` and `x2` (`nameKey`: `Plan.md`, `Plan 2.md`; a sub-notebook's folder never takes a note's file name or `attachments`). The body is written as it is stored, except: attachments (`devot://file/<id>` image destinations and `<img>` sources in raw HTML, whose ID is a UUIDv7, as Rust accepts; any other such link stays as written) are copied from the database into an `attachments` folder at the top of the export under their own names (a different file of that name already there is kept and the copy is numbered; the same bytes are reused), and their links become relative paths (`../attachments/board.png`, with spaces of any kind, parentheses, `&` (which would start a character reference), `|` (which would end a table cell) and the like percent-encoded, and in an `<img>` quotes too; an image shown at a size preset keeps it as the path's fragment, `../attachments/board.png#half`, which other tools ignore when they load the image and import reads back; each attachment is copied once, whatever sizes it is shown at; an image whose link cannot be found in the text keeps it and is listed as a problem, `E_EXPORT_IMAGE_UNLOCATED`); and the title, tags and status go into front matter where import would not read them back: import reads them only from Devot's own block, opened by the comment `# Devot metadata` (the marker), which it reads exactly and leaves out of the note again. So a note whose title is not its first heading or file name, or that has tags or a status, gets that block first; a note's own front matter is never changed (the block goes before it, and import keeps it in the body as it is), and a note whose own front matter would itself read as Devot's block (its first line is `# Devot metadata`) always gets the block. Values are single-quoted, or double-quoted with escapes when they hold what cannot be written on one line as it is (control characters, line and paragraph separators, a byte order mark). Note links (`devot://note/<id>`) stay as they are. So export then import gives the same notes (title, body, tags, status, notebook structure and images), checked on real files in `tests/core/export.test.ts`. Notebooks without notes under them do not come back (import makes notebooks for folders with notes), and names come back file-safe.
- **HTML** (`src/core/htmlExport.ts`, `src/renderer/src/exporter.ts`): a note's page is its sanitized preview tree serialized, in a document of its own: no scripts, and a `Content-Security-Policy` meta that allows only its own styles and images (`data:`, `https:`, `http:`; a page to print allows `data:` images only, see Print and PDF). Its styles are the design tokens (light, and dark on screens set to dark; print is always light), the preview's note content rules (`preview/content.css`, shared with the app) and the page's own (`preview/page.css`). Attachment images (a UUIDv7 ID; any other `devot://file/` image stays as written, so one stray link never fails the page) become `data:` URIs: the UI puts a token with a per-page random nonce in each image's `src` and Rust swaps in the bytes, so text in the note can never be mistaken for one. A size preset is the preview's class (`image-size-half`, sized by `content.css`), so exported and printed pages size images as the preview does. Mermaid diagrams are drawn by the UI (light) and cleaned again in the core; video embeds and click-to-load embeds become links; swatches get an inline colour; the preview's `data-*` attributes are dropped. A notebook gives one page per note, and links between its notes point at their pages. Copy as HTML copies the same page as text; Copy as Simple HTML copies the bare markup without any class, style or `data-*` attribute, front matter or drawing (diagrams show their source, alerts become block quotes with a bold title); a sized image gets no width there either (Half has no pixel width to give), so it shows at its own size, as in other Markdown tools. Both copy as plain text (the HTML source), with images as `data:` URIs.
- **Print and PDF:** Rust lays the note's page out in an offscreen `WKWebView` (scripts off) and runs an `NSPrintOperation` on it into a PDF on the paper and margins of the page setup (`native/macos.rs`), then draws that PDF's pages again with the header and footer (see Page setup): Print… prints that PDF through the system print panel as a sheet on the window (PDFKit, each page scaled down to the paper picked there if it does not fit); Export as PDF… asks where to save in a save panel, prints without a panel into a new private folder in the app's data (`<app data>/pdf`), and copies the PDF from there into place through a temporary file beside it, like any file, in the folder chosen, opened when the save panel closed. AppKit creates the PDF by its path, so the folder it prints in must be one nobody else can reach: a private folder in the chosen folder could be swapped for a link while the job runs by anyone who may remove names there (the owner of a folder the user saves into, say), and AppKit would print through it. One print job runs at a time. The job is named after the note's title (control characters as spaces, at most 1000 characters). A load failure (or the page's process ending) ends a job only before printing starts; once the print panel is up, the job ends when the operation reports back. AppKit reports back on the thread the operation printed on (a PDF's runs on a thread of its own), so the result is handed to the main thread, where every job ends and frees the print slot for the next. A cancelled print panel is no failure; a PDF has no panel to cancel, so one that was not written fails with `E_EXPORT_PDF_FAILED` (AppKit may show its own alert first).
- **Page setup:** Print… and Export as PDF… first show Page Setup (`PageSetupDialog.tsx`): the paper (A4, US Letter, A4 landscape, a 16:9 slide), the margins (narrow, normal, wide: half an inch, three quarters, an inch), a header and a footer with a left, centre and right slot each, whether the first page goes without them, and thin rules under the header and above the footer. Until the user picks a paper it starts from the system's: US Letter when macOS's default paper is as wide as Letter, A4 when it is A4, otherwise by the region (Letter in the United States, Canada, Mexico and the other Letter regions). It remembers the choices as editor settings (the `page*` keys, checked in TypeScript and Rust like the others: a slot is up to 100 characters, no control characters); Print or Export stores them first, and Rust reads them from the settings for the job (`src-tauri/src/page_setup.rs`). A slot's `{title}`, `{page}`, `{total}` and `{date}` (the note's title, the page number, the number of pages and today's date as the locale writes it) are filled in per page. WebKit's print path takes the paper and margins from the print info and honours `@page` margins, but ignores `@page` size and draws no margin boxes (`@top-left` and the like), and a fixed element prints on the first page only, so the header and footer cannot come from CSS: Rust draws each page of the laid-out PDF again into a new PDF (Core Graphics, the page as a form, so its text stays text) with the header and footer as text halfway into the top and bottom margins (the rules a quarter of a margin before the note), and keeps the page's links (web links and links to a heading on another page). The text and rules take the light theme's tertiary text and hairline colours and the smallest caption size, which the UI hands over from the design tokens (`look`).
- **Images from the web in the preview:** images in notes load as written, as in any Markdown tool: the production CSP allows `https:` images (besides `'self' data: blob: devot:`), so the preview renders `https` images (Markdown and allowed raw `<img>`) directly, with no placeholder and no click-to-load; the sanitizer is unchanged. Plain `http` images are not allowed by the policy and do not load. HTML export keeps the images and print shows links (see Nothing from the web in print). A production-CSP Playwright test checks that an `https` image loads with no violation reported.
- **Nothing from the web in print:** printing never loads an image from the web, so no server learns that a note was printed and no slow host holds a job up. Rust puts its print policy (`PRINT_POLICY`: only the page's own styles and `data:` images) in front of every page it prints, before anything of the page's, whatever the page's own policy says; the UI's pages to print carry the same policy (`PRINT_CSP`, kept equal by a policy test) and show each image from the web as a link to it, its alt text (else its URL) as the link's text (only the text inside another link), leaving out a `picture`'s other sources. Exported HTML keeps such images, to load where the file is opened.

### Command line

Settings > General > Command Line Tool installs the `devot` command: a symbolic link, `/usr/local/bin/devot`, to a shell script in the bundle (`src-tauri/cli/devot`, in the resources as `bin/devot`), which runs the app's binary with `--cli` and its arguments; `main` hands them to `src-tauri/src/cli.rs` before anything of the app starts. The row says whether the link is there (`cli_tool_status`, `cli_tool_install`, `cli_tool_uninstall`, granted to the Settings window alone and taking no arguments). The link is made beside its place and renamed over it; where `/usr/local/bin` cannot be written (or is not there), the system's authorization prompt does it (`osascript … with administrator privileges`, the paths passed as arguments, never in the script's text). Install refuses (`E_CLI_APP_NOT_IN_APPLICATIONS`, and the row asks to move Devot to Applications) while the app runs from a read-only volume, as a disk image is (`statvfs` reports it so), or a translocated copy (`…/AppTranslocation/…`), where the link would break once the image is ejected or the app moved; an app on a second disk, writable, installs the link. Install replaces only a missing file or a link, never a file; Uninstall removes only a link to this app's script; a cancelled prompt changes nothing (`src-tauri/src/cli_tool.rs`).

- **`devot`** brings Devot forward, or launches it.
- **`devot a.md b.md [--notebook NAME]`** checks that each file is a Markdown file there (paths taken from the folder the command ran in) and hands them over by absolute path: to a running Devot through the single-instance socket, in the format a second launch writes (only when the socket may be trusted, see One Devot), else by launching Devot (`open -a`, with no arguments) and sending them through the socket once it listens there, asking every 50 ms for up to 30 s (`E_CLI_LAUNCH_UNANSWERED` after that); then it returns. Devot ignores `open -a`'s arguments while it runs, even while another `devot` call is still launching it, so files never ride on a launch. A Devot started with them in its own arguments (the binary run by hand) still takes them, and Restart to Update restarts with none (`restart_env` in `src-tauri/src/exit.rs`), or every update would import them again. A running Devot that cannot be reached there (it holds the data folder, but nothing answers at the socket) fails the command instead: it prints `E_CLI_HANDOFF_UNREACHABLE` and exits with status 1. So does a hand-off the running Devot does not take within 5 s (`E_CLI_HANDOFF_UNANSWERED`) or closes unanswered, as it does while it quits (`E_CLI_HANDOFF_REFUSED`). It checks the data folder with a shared `flock` for an instant; a launch that meets it there tries once more 50 ms later. Devot scans them as Markdown Files… picks them and the main window gets a link of its own (`{kind: 'import', scan, notebook, first}`, which no URL makes; it waits like any link), imports them without a sheet into the notebook of that name (exactly, else in any case; made when there is none) or the default notebook, and opens the note the first file became (`src/renderer/src/cliOpen.ts`). A failure shows a notice.
- **`devot export <file.md|-> -o out.pdf|out.html [--simple]`** runs in its own process with nothing of the app's: no data folder, database, socket or Dock icon, so it runs beside an open Devot (`src-tauri/src/cli_export.rs`). The page is made by the exporter's own code, which needs a web view, so the process has one window that is never shown (`export.html`, private web data, its own capability granting `cli_export_source`, `cli_export_finish` and `cli_export_fail` and nothing else); Rust writes the HTML, or prints the PDF as Export as PDF… does (in a private folder in the app's caches, then copied into place). `-` reads standard input; at most 10 MB of UTF-8. `--simple` gives the bare markup (HTML only). Attachment images are not resolved (nothing reads the database), and an image given by a relative path stays a link beside the page, which the page's own CSP would not let load. It gives up after two minutes, and stops on SIGINT or SIGTERM; either way it removes its private PDF folder and the temporary file it was writing beside the output first. The output goes into place under the same lock such an exit takes, so it is either whole and the export exits 0 (a signal that comes after it is ignored), or never put there. Each PDF job, and every launch of the app, removes such folders more than ten minutes old left in `pdf/` (in the app's data and caches) by a job that never finished.
- Errors go to standard error as `devot: <message>`, with the code where there is one; the exit status is 0 when done, 1 when it failed and 2 when the command was not understood (`devot --help`).

### Markdown mirror

Settings > Markdown Mirror (and the palette's Choose Markdown Mirror Folder… and, while it is on, Turn Off Markdown Mirror) keeps a folder the user picked up to date with every note as a Markdown file, so other tools (editors, grep, Git, Spotlight, agents) read the notes without an export. It is off by default. The notes database stays the source of truth: the folder is written by Devot and never read back, which the section says.

- **Layout and files** (`src/core/mirror.ts`): an export of every notebook at once (see Export and print): a folder per notebook (sub-notebooks nested), a `.md` file per note named after its title with Devot's front matter where import would not read the title, tags or status back, one `attachments` folder at the top; notes in no notebook (or a deleted one) at the top. Templates and the Trash are left out. Importing the folder gives the same notes (title, body, tags, status, notebook structure and images) inside one notebook named after it, checked on real files in `tests/core/mirror-sync.test.ts`. Export reads a note's Markdown once (`markdownFacts` in `src/core/import.ts`), and not at all when it cannot hold an image (it has neither `![` nor an `<img` tag, in any case), front matter or a level-one heading; a property test checks that against the functions that always parse.
- **The manifest** (`.devot-mirror.json` in the folder) maps note, attachment and notebook IDs to the paths Devot wrote, with each file's SHA-256 and size, and for a note what its file was written from (`source`, a hash of its update time, body version, title, status, tags, path and attachment paths; the body version moves with every write of the note, which an older edit synced in is, though it leaves the update time as it is; the note list reads it from the list's index, migration 0023) and the attachments it shows. Devot moves or deletes only paths the manifest lists, and only while they hold what it wrote; nothing else in the folder is ever changed. A folder that is not empty and has no manifest is used only after a confirmation (which writes an empty manifest); an empty folder or one with a manifest this library wrote is used at once. The manifest names the library that wrote it (a random ID kept in the mirror setting), so a folder another library mirrors (app data lost, a second Mac set up on its own) also asks first and starts from an empty manifest: the files it lists can be taken back but are never removed. A copy of the whole app data (moved to a new Mac, or restored to a second one) is the same library by any ID it keeps, the database's included: if both copies stay in use and mirror to one folder, each takes the other's new notes for its own deleted ones. A manifest from before manifests named their library is taken as this library's own only in the folder the mirror already uses, and gets its name.
- **Edited outside Devot:** before a file is rewritten, moved or deleted, what is on disk is compared with the manifest's hash. A file changed outside Devot is renamed in its folder to `<name> (edited outside Devot).md` (numbered when that is taken; the suffix is `strings::MIRROR_EDITED_SUFFIX`, used only by Rust), leaves the manifest, so it is never touched again, and Devot writes its own version. This holds for note edits, renames, moves, the Trash, purges, attachments and reconciles, and the files kept are listed in one notice until it is dismissed (Rust names the first 20 and counts them all, so a tool that changed every file keeps the status small). A file that already holds exactly what Devot would write is taken as Devot's; one replaced by a folder or a link is only forgotten.
- **Files the manifest does not list:** a batch's files reach the disk before the manifest that lists them, so a crash, a power loss or a quit in between leaves them unlisted (as does a folder chosen again after its manifest was lost). The plan takes such a file back rather than writing the note again under a numbered name: a file at the note's place that holds exactly the text rendered for it there makes the place the note's, and the operation goes without its text (Rust adopts the file). An attachment's copy likewise, when its bytes' SHA-256 (`mirror_hashes`, asked only when a file is in the way of a copy) matches the file. So the folder still imports without duplicates.
- **Names stay:** a note keeps its file, and a notebook its folder, while the name still fits (its title's file-safe stem, or the stem numbered; a folder's in any case or form of its accents, since moving files to another name macOS takes for the same folder leaves them where they are), so a change touches only the files it affects. A new name is the first of `Plan.md`, `Plan 2.md`, ... free in its folder, names compared by the rule export numbers them by (`nameKey`: what macOS takes for one name, whatever its case or the form of its accents, and, to be safe, a compatibility form; a folder keeps its name only across what macOS itself folds, `fileKey`, so `x²` renamed `x2` moves): not held by a file of the manifest (one moving away keeps its name taken until the next pass), nor given in the pass, nor anything else on disk (a folder Devot did not make may be shared, a file never).
- **Plan and executor:** the core worker plans (`planMirror`, a pure function of the database, the manifest and what is known of the disk, unit-tested in `tests/core/mirror.test.ts`): it asks for what it needs as it goes (note bodies without their Yjs state, `mirror_bodies`; attachment names, `mirror_files`; the hashes of attachments' bytes, `mirror_hashes`; disk states, `mirror_check`) and renders files in the worker, handing its event loop back between steps. Rust (`src-tauri/src/mirror/`) holds the folder and the manifest and runs each operation (`mirror_apply`: keep, forget, remove, write or move a note, copy or name an attachment, record a notebook's folder) after checking it again: plain visible paths inside the folder (notes `.md` and never in `attachments`, attachments `attachments/<name>`), never a file it did not write unless it holds exactly that, never through a link (every folder on the way must be a real one), never making the chosen folder. Each call opens the chosen folder once, by the path resolved when it was chosen and never through a link anywhere on it (a link there now pauses the mirror as a missing folder does), and finds every path in it folder by folder from that handle, so a check and the step that acts on it work in the same folders (see Security). Every file, the manifest and the setting included, goes through the app's one writer (`atomic_file.rs`, see Security): a new temporary file of a hidden random name, never opened where something already is, put in place. A new note file, an attachment's copy, a note moved to a new name, a file kept aside and a folder's first manifest go only where nothing is yet, so a file or a link that appeared there after Rust looked is never replaced or written through (the plan learns it is in the way; see Security for volumes that cannot rename that way in one step), and a move is whole: a file never stays under its old name too (a folder it cannot leave, locked say, fails the move), and one whose new text then cannot be written stays listed where it went, with what it holds (the manifest is written back and the core reads it again), so the next pass rewrites it there; only Devot's own file, found holding what Devot wrote just before, is replaced. Files are not flushed one by one (the database is the source of truth, and a file a crash left short is caught by the next reconcile, kept aside and written again), while the manifest is flushed after each batch. Attachment bytes go from the database to disk in Rust, never across IPC. A link to an attachment ID Devot never made (any UUID) is a link to no attachment and stays as written. Something in the way of an operation (a file that appeared, one changed meanwhile) makes the plan learn what is there and try again, three times per entry in a pass at most; a note whose file is rendered for a new place again and again (ten times in a pass) is left as it is until the next pass, logged as `E_MIRROR_UNSETTLED`, so it never holds up the others; an operation planned from a manifest Rust has moved past waits for the next pass, which reads the manifest again. A path that reads as `other` (a link, or under something that is not a real folder) makes the plan ask about each folder on the way: a notebook's folder that is no longer a real folder (a link or a file in its place) is lost and the notebook gets a new folder; while `attachments` is not a real folder, only attachment names are kept, as with Include Attachments off.
- **When it runs** (`createMirrorRunner`, started by the main window once it has restored its view): every write the mirror follows (notes, their tags, notebooks, tags and attachments; `observeWrites` wraps the worker's storage, so edits, renames, moves, tags, statuses, notebook changes, the Trash, restores, purges, batch actions, duplicates, notes from a selection or a template all count) starts a pass a second after the last one (five seconds after the first at most), never per keystroke: a note is saved 300 ms after typing pauses. Passes run one at a time; each compares every note's `source` with the manifest and reads, renders and writes only notes that changed, so one edit writes one file and pinning writes none. A full reconcile, which also checks every manifest file on disk, runs when the mirror turns on, its folder or Include Attachments changes, it resumes, and two seconds after the window has restored at launch (also after a restore from a backup, which reloads the window). Notes devot-mcp writes are mirrored by the pass the window runs when it notices the database changed (`devot://db-changed`), or by the next launch's reconcile. A first mirror works in slices of 1,000 notes, written in batches of 200 operations (the manifest is written back after each batch that changed it); the 10,000-note benchmark (`tests/core/mirror.bench.test.ts`) keeps every stretch the worker computes under 200 ms and checks that an edit then writes one file. Quitting ends a running pass after its batch, so the manifest lists every file it wrote.
- **Include Attachments** (on by default): off, no attachment bytes are copied and the copies written before are removed (one changed outside Devot is kept); links still point at `attachments/<name>`, as in an export, and the manifest keeps those names. On again, the copies come back at the next reconcile under the same names, so no note's file changes.
- **Failures:** a folder that is missing (or has a link in its place) or cannot be written pauses the mirror with a code (Rust holds it; the main window shows a notice in the notice stack); a file or folder inside it that cannot be written (locked, say) only waits, logged, for a later pass. A manifest that could not be written back stays in memory and is written when the mirror resumes, never read again from the folder. A paused mirror checks its folder every 30 seconds and when the main window comes to the front (`mirror_open`) and resumes with a reconcile; Devot never makes the chosen folder itself. A manifest that cannot be read, or files without one, pause it too, until a folder is chosen again (or a missing manifest comes back), and the notice says so (`E_MIRROR_MANIFEST_MISSING`, `E_MIRROR_MANIFEST_INVALID`); so does a manifest another library wrote (`E_MIRROR_MANIFEST_FOREIGN`). Choosing that folder again asks first, then starts from an empty manifest, and the files that still hold what Devot would write are taken back (see above), so nothing is written twice. Logs carry codes and IDs only.
- **Setting and status:** the folder, Include Attachments and the library's ID live in `<app data>/mirror-settings.json`, a local preference like the editor settings (never synced, never in backups; read leniently). A file that cannot be read shows the mirror as off and is never written over: a change or a folder choice is refused with `E_MIRROR_SETTINGS_READ_FAILED`, the file is read again on the next call, and once a read works every window is told; a damaged file is copied to `mirror-settings.json.damaged` before the next change replaces it. After every change of the setting or of what the mirror shows (a pause, the size of the files in the manifest, the files kept) Rust sends `devot://mirror-changed` with the status and a revision to every window; the page's side shares `syncedStore.ts`. The size is unknown (null, and Settings shows none) until the folder's manifest has been read, and is sent once it is, even by a pass that writes nothing. `mirror_get`, `mirror_set`, `mirror_choose` (the folder panel over the calling window) and `mirror_confirm` are granted to the main and Settings windows; `mirror_open`, `mirror_check`, `mirror_apply`, `mirror_bodies`, `mirror_files` and `mirror_hashes` to the main window only. Turning the mirror off leaves its folder as it is; choosing that folder again later goes on from its manifest.

### Note templates

- **What a template is:** an ordinary note (synced, edited, trashed and restored like any other) filed in a reserved notebook, Templates. The sidebar lists them under Templates, above the Trash; New Note (or Cmd+N) there makes a new template, and the editor shows a line about front matter and variables in place of the notebook, status and tag pickers (a template's own status and tags are not used, so the status keys and the palette's Add Tag to Note are not offered for one).
- **The reserved notebook:** every device knows it by one fixed ID, `TEMPLATES_BOOK_ID` (`src/core/books.ts`): `00000000-0000-7000-8000-000000000001`, UUIDv7-shaped (version 7, variant 10, a zero timestamp no generated ID has), so Rust's ID checks accept it (a Rust test and a policy test keep the two sides in step) and no schema change was needed. Its row (named `Templates`) is written on first use (`TemplateService.create`); the copies two devices write merge field by field into one row. The notebook service never lists, renames, moves, deletes or shares it, and `settleOrder` leaves it alone. A Devot from before templates shows it as a plain notebook; if it deletes it there, templates keep working (the note service accepts the ID even without a live row).
- **Out of the library:** the note service's `list` and `search` leave templates out (`excludeTemplates` in `src/core/search.ts` adds one condition, or joins a notebook exclusion, so the longest query stays within the 12 conditions Rust accepts), and `book:Templates` names nothing. AI tools never count Templates as allowed, even with Allow AI Access set on its row by an older Devot, so devot-mcp lists, finds and reads no template. Counts, filters, the palette's notes and the `[[` popup follow from the note list. The Trash and the activity heatmap treat templates like any note.
- **A note from a template** (`src/core/templates.ts`): Cmd+T anywhere in the window (the registry's `note.newFromTemplate`, also New Note from Template… in the command palette) opens a picker: a filter, the templates used last on this device first (local storage, at most five, never synced), then the rest by title, and a preview of the note the selected one would make now: its title, notebook, tags and status, and its Markdown as plain text. Return, a double click or Create makes the note and opens it with the keyboard in its editor; when the view would not list it, its notebook (or All Notes) shows.
- **Front matter sets the defaults**, read by the import reader (`readFrontMatter`): `title` (else the template's own title), `notebook` (a name in any case, the first in sidebar order, or a path such as `Work/Meetings`; else, or when it names nothing, the notebook the window shows, as with New Note), `tags` (made when missing) and `status`. These four keys are then removed from the new note's front matter (all of it when nothing else is left), so the body holds only what is meant for the note; every other key stays.
- **Variables:** `{{date}}` (YYYY-MM-DD), `{{time}}` (HH:mm) and `{{datetime}}` (YYYY-MM-DD HH:mm) take a format after a colon (`{{date:dddd, D MMMM}}`; tokens YYYY YY MMMM MMM MM M DD D dddd ddd HH H hh h mm m ss s A a Z, text in brackets kept as written), `{{title}}` is the new note's title, and `{{uuid}}` is a random UUID v4 (one per note made, the same wherever it appears in that note). Names match in any case; anything else between double braces stays as written, and a title that holds a variable is not expanded again. Variables are filled in everywhere in the body, code included (a template can put today's date in a code block). Line breaks become `\n` first, as import does. The time is the page's clock at the moment the note is made, on the wall clock of the system's time zone; unit tests inject the zone (Los Angeles across both 2026 transitions, Shanghai, Kathmandu).
- **Instruction quotes:** a blockquote whose first line is a heading starting with `!` (`> # !Instructions`) is removed, with the blank line after it, from notes made from the template; it stays in the template. Quotes in code blocks and ordinary quotes are kept.
- **Starter templates:** Brainstorming, Debugging, Learning, Planning and Daily Report (`src/renderer/src/starterTemplates.ts`, text from the message catalog; core keeps only the `starter:` ID prefix and takes the list through `starters`) are not stored. They are read-only, listed under "Built-in" after the user's own templates (the picker and the Templates view), and editing one saves a copy as the user's own template (`TemplateService.save`). Applying a template to an existing note (`applyTo`) keeps the note's tags and status.
- **Writing it:** the note is made with `NoteService.create`, then it gets its own copies of the template's images (see Note links), then its body (showing the copies) is applied as Yjs operations (`setBody`), then its status and tags; a failure part-way purges the note. The template itself never changes.

## Search

Search covers live notes (never the Trash) through the FTS5 trigram index (`src/core/search.ts`, `notes_search`).

- **Syntax:** words and `"quoted phrases"` must all appear in the title or body (case-insensitive substrings). Qualifiers narrow the search: `title:` and `body:` (text in that part only), `book:` (the notebook and its sub-notebooks, like selecting it in the sidebar), `tag:`, `status:` (an ID such as `on_hold` or a name such as `"On Hold"`, in any case, with spaces, hyphens or underscores), `bookId:` and `tagId:` (the same by ID, a UUID; `bookId:` also includes sub-notebooks) and `pinned:` (`true`, `yes` or `1`; `false`, `no` or `0`; any case). A leading `-` excludes what any clause matches (`-draft`, `-tag:done`, `-pinned:true`, which is `pinned:false`). Phrases take `"…"` or `'…'`; a single quote opens a phrase only at the start of a clause or right after a qualifier, and only when a closing one follows (before a space or the end), so `don't` and `'tis` stay words. Clauses combine with AND, so repeating a qualifier narrows further. Names match in any case (accents count); a name with spaces is quoted (`book:"Weekly notes"`). A query keeps at most 10 clauses; a text value keeps at most 100 characters, and a `book:` or `tag:` name as many as a notebook or tag name can have (200 and 100).
- **Malformed input** never fails: an unknown qualifier, an empty value, an unknown status, an ID that is no UUID or a `pinned:` value that is no boolean is searched as the plain text typed; an unclosed double quote runs to the end, an unclosed single quote is literal. A `book:`, `bookId:`, `tag:` or `tagId:` naming nothing matches no note; excluding one excludes nothing. Two `pinned:` clauses that disagree, or one that disagrees with the view's Pinned filter, match nothing. The search field's "?" button lists the syntax.
- **Where it runs:** the core parses the query and turns notebook and tag names into IDs (`resolveSearch`; `NoteQuery.pinned` is true, false or null for either, in the core, the Rust store and the SQLite adapter); storage runs every condition in SQL before the result limit (200), so a qualifier never loses matches to the limit. Indexed text is matched in the FTS table first and ranked by bm25 (an excluded word uses the index too); text under three characters is scanned (it reads the bodies, of the ranked matches only when there are some), folding case with the SQL function `devot_fold` that both SQLite stores (Rust and `src/mcp/sqlite.ts`) register, the same character-for-character fold as the trigram index and the core, so "ém" finds "Émile" (shared cases in `tests/support/folds.json`). Live notes come from the note list's index (schema v14 `notes_list`, which covers what a search filters on and returns), never from their rows: a note's small columns come after its Markdown and its Yjs state in the row, so reading them there walks every overflow page of both, and a search would cost more the longer the notes are. A ranked search walks the whole list index even when one note matches (O(notes), about 2.5 ms for 50,000 notes): a deliberate trade-off, since letting the matches drive the join reads each match's row through its blobs and costs twice as much once a word is in many notes. Ties go to the newer note, then by ID, as in the note list. The Rust store, the better-sqlite3 adapter and the UI tests' memory adapter implement the same rules, and a property test checks SQLite against a plain model of them; tests check the query plans and that the results (rows and order) are those of the statements schema v14 replaced. A benchmark keeps 10,000 notes of a few KB each (with Yjs states larger than their text) under 50 ms for the lists and searches, excerpts included, and under 100 ms for a scan of every body (a missing two-character word). A word found in nearly every note together with a two-character word misses 50 ms at these sizes (about 65 ms: every body is read); the benchmark marks it as a known failure until #48 is fixed.
- **Two scopes:** Shift+Cmd+F (or `/` in the note list) searches the current view: the selected notebook and filter stay, and the field reads "Search in <view>". Shift+Opt+Cmd+F searches every note; while it does, nothing in the sidebar shows as selected (the notebook, All Notes or filter shows again once the search is cleared, and a row pressed meanwhile shows its own view: a notebook comes without the hidden filter, a filter covers every note rather than the hidden notebook). Escape or the clear button empties the field and returns to searching every note. Typing a search in the Trash shows All Notes.
- **Results:** in relevance order (see Note list order). Each row marks the words found in its title and in an excerpt of the body around the first word found there (about 160 characters), built from text nodes and `<mark>`, never from HTML. Storage cuts excerpts in code for the returned notes only, folding case one character for one like the trigram index. An excerpt is cut from the body's readable text (`src/core/readable.ts`, mirrored step for step in Rust with shared test cases): a leading front matter block is skipped and Markdown markers come out (heading, list, quote, task and alert markers, emphasis paired as in CommonMark, code fences and backticks, link and image syntax keeping the link text and alt text, defined link references, HTML tags and comments, table pipes; `[[target]]` and `[[target|label]]` from other tools show the label, else the target), while text that only looks like syntax stays as the preview shows it (an unpaired `*` or `_`, brackets that make no link, a `<` that opens no tag), so the marks land on the words as shown; a word found only in front matter or syntax shows no excerpt; an excerpt that would open inside a word starts at the next word instead (a cut with no space before the word found, as in Chinese text, stays where it falls). A body of more than 600 characters is not read whole, so a page of results costs the same however long the notes are (`EXCERPT_STRETCH`): a word is looked for as written (in any case), at most 8 places, after the front matter, and each place is read with 300 characters on each side as a body of its own (growing 300 at a time while the word shows too near an end of it for a whole excerpt). So in a long body a word that only markers cut apart (`te**rm**`) shows no excerpt, and a code fence or comment opened, or a link reference defined, outside that stretch is not known in it (`tests/support/excerpts.json` holds the cases both stores agree on).
- devot-mcp's `search_notes` uses the same syntax; `book:` and `bookId:` name only notebooks AI may see.

### Find in a note

- **Bar:** Cmd+F opens a find bar above the open note; Option+Cmd+F opens it with a replace row. Cmd+G and Shift+Cmd+G (or Return and Shift+Return in the field) go to the next and previous match, wrapping around; the bar shows "3 of 12". Option+Cmd+R toggles regular expressions and Option+Cmd+C case sensitivity (only while the bar is open). Escape in the bar or the searched pane closes it and returns the focus there (in the editor, its popups and the selection toolbar take Escape first). The shortcuts are the registry's `find.*` commands, in the `window` scope: they work window-wide while a note is open (`src/renderer/src/find/`), ahead of the editor's own Cmd+F and Cmd+G, and a held Cmd+G keeps stepping; the registry's clash test keeps them apart from every other key. F3 and Shift+F3 step through matches in the editor while the bar is open (editor-scope commands). The command palette lists Find in Note, Find and Replace and the match steps while a note is open, and the two toggles while the bar is open. A selection made by the user becomes the query when the bar opens; a selection the query already matches (the match left selected when the bar closed) does not. With the bar closed, Cmd+G and Shift+Cmd+G reopen it with the last query and go on to the next or previous match from the cursor. The bar's buttons use `aria-disabled` rather than `disabled`, so a button that runs out of matches (Replace All from the keyboard) keeps the focus and Escape still closes the bar.
- **Matching** (`src/core/find.ts`, shared by both panes): plain text by default, case-insensitive unless Match Case is on; a regular expression runs in Unicode mode with `^` and `$` per line (a pattern only the older syntax accepts, such as `\#` or `\-`, runs without Unicode mode), and an invalid one shows "Invalid regular expression" instead of failing. Empty matches (`^`) count and can be replaced, so replacing `^` with `> ` quotes every line. At most 10,000 matches are counted and marked ("More than 10,000 matches"); Replace All has no limit. Regular expression replacements expand `$&`, `$1`, `$<name>` and the rest as `String.prototype.replace` does (a property test checks this); plain replacements are inserted as typed.
- **Editor:** matches are CodeMirror decorations and the current match is the selection (it does not pop up the selection toolbar). F3 and Shift+F3 in the editor also step through matches; CodeMirror's own search panel and Go to Line dialog never open (`editor/settings.ts` keeps only its two searches that open nothing, Select Next Occurrence and Select All Matches, and a test checks that no built-in key opens a panel, also with Find Next moved to another key). Replace and Replace All are ordinary editor transactions, so they reach the Yjs document like typing; each is one undo step. `@codemirror/search` is not used: its marks only show with its own panel, and the preview needs the same rules outside the editor.
- **Preview:** Cmd+F in preview mode searches the rendered text (a line break between blocks and at a hard line break, so a match never runs across two paragraphs, but it does across bold or links; a soft line break inside a paragraph is a space, as shown) and paints matches with the CSS Custom Highlight API, so the preview's DOM is never changed and its patcher keeps owning every node; the marks follow re-renders. Rendered text cannot be edited, so the preview has no replace row; diagrams (islands) are not searched.
- **Split mode:** Cmd+F searches the pane that has the keyboard focus: the preview after a click in it, otherwise the editor. The bar stays on that pane until find opens again from the other one.

### Split mode

- **Synced scrolling:** in split mode, scrolling either pane brings the other to the same source line (`src/renderer/src/preview/scrollSync.ts`). The core marks every block of the preview with the line it starts on (`data-source-line`: paragraphs, headings, list items, table rows, code blocks, alerts, diagrams, math and embeds), in a last step after the renderers, which keep a replaced block's source position, and after sanitizing, so a note cannot set the attribute (the sanitizer drops the note's own `data-*` attributes). Both panes speak in fractional source lines: the editor reads CodeMirror's height map, the preview interpolates between its blocks, whose offsets it measures once per rendering, resize or loaded image, never on a scroll. The pane being scrolled leads, once per animation frame; the scroll it causes in the other pane is recognised by its offset and never sent back, and for half a second after a wheel or touch gesture in one pane, scrolling still running in the other does not pull it. A pane that cannot scroll (a short note in the editor) leads nothing. The tops line up with each other; over the leader's last screen the follower blends from the matching line to its own end, so both reach the bottom together without a jump. When a pane is laid out anew (the preview after each rendering, a loaded image or a diagram drawn later, a resize), it lines up with the other pane unless the user was last scrolling, clicking or typing in it, so typing in the editor keeps the preview with it while a place read in the preview stays put. Synced scrolling starts with the editor leading, or with the preview when the window comes from Preview mode, so the place being read is kept. It is on by default, an editor setting (`syncScroll`), turned off and on from View > Synced Scrolling (a check item: Rust stores the change itself and keeps the check mark in line with the setting however it changes), from the command palette (Turn Off/On Synced Scrolling) and from Settings > Preview.
- **Copy buttons:** each fenced code block in the preview (not front matter, inline code or diagrams) has a copy button in its top right corner, shown on hover and on keyboard focus (Option+Tab, as for every button in WebKit, or Tab with Full Keyboard Access). It copies the block's text as written in the note, without its final line break, through `clipboard_write_text` like every other copy (the command takes as much text as a note may hold, so any block fits), then reads Copied (or Could Not Copy) for a moment. The button is the page's own control, never part of the note's HTML: the core renders none, the preview adds it as a React portal marked `data-devot-ui`, which the patcher never reuses, replaces or removes, it has no text of its own (so find and selections do not see it), and printing hides it, so exports and printed or copied HTML never contain it.

## Editor settings

- **What:** Settings > Editing and Settings > Preview (the Settings window has a 200 px navigation column, `size.settings-nav-width`, under a capsule search field, with a row and a coloured tile per pane: General, Editing, Preview, Appearance, Keyboard, Mirror, Sync, AI, License, Integrations, Plugins and Usage; Back and Forward share one capsule in its toolbar; each pane's sections have a 13 px semibold title above a card, an optional footnote under it, and each setting a label, a grey description and its capsule control on the right). Editing has three sections. Interface: the selection toolbar (on), line numbers, highlighting the active line (off), line wrapping (Off, All lines, Prose only, which keeps code blocks and tables on one line each, or Unwrap at cursor, the default, which does that only for the code block or table under the caret and keeps the caret's line in place on screen; code in a quote or an alert wraps with it; a stored on/off from an older Devot reads as Unwrap at cursor/Off), inline image widgets, a readable line width (`size.reading-width`, 740 px), scrolling past the end (on) and the cursor scroll margin (pixels, 0). Markdown: the unordered list bullet (`*`, `-` or `+`), the indent unit (2 or 4 spaces or a tab), tab size, how a lone pasted URL goes in (as copied, `<url>` or `[](url)`; see Pasting URLs) and spell checking (on). Text Appearance: font size (10 to 32 px; also Cmd+=, Cmd+- and Cmd+0 in the main window, the registry's `view.font*` commands), font family (System, SF Mono, Menlo, Monaco or Courier New), font weight (normal or 300 to 700), line height (1.2 to 2.0 offered, 1.0 to 2.5 accepted; 1.5 by default), showing invisible characters and highlighting trailing whitespace (`color.trailing-space`). Preview holds the preview's font size (10 to 32 px, 15 by default) and synced scrolling in split mode (see Split mode). General holds the default notebook for new notes. The same store also holds Settings > Appearance's sidebar material (see Native look). The roomy defaults (line height 1.5, tab size 2, `*` bullets, links for pasted URLs, spell checking on, no active-line highlight) apply only to settings the user never set: Rust writes only the values the user set, so a default that changes later still reaches everything else.
- **Default notebook:** an ID (or none) in the same store, applied by the main window when a note is made while the view shows no notebook (`notebookForNewNote`: the notebook shown, else the default when it still exists, else none). The Settings window cannot reach the core, so the main window keeps the notebook names (never note content) in local storage (`notebookChoices.ts`), which the Settings window reads and follows through `storage` events.
- **Store:** a local preference, not note data: Rust keeps it in `<app data>/editor-settings.json` (`src-tauri/src/editor_settings.rs`), outside the notes database, so it never syncs and backups never include it. A change is written to a temporary file, flushed to disk and renamed over the old one. `editor_settings_get` is granted to every window that draws with the settings (main, note windows, quick capture and Settings), and `editor_settings_set` (a partial change) to the main and Settings windows only; Rust checks every value (booleans, whole-number ranges, fixed lists for the font, weight, indent unit and marker, a short notebook ID or null) and refuses a change with an unknown key or a bad value as a whole. Reading the file is lenient: a missing, out-of-range or damaged value takes its default and the rest are kept; the file holds only the values the user set, merged with each change. A file that cannot be read (anything but a missing one, such as a permission or I/O error) is never written over, since a change would drop the values it holds: the defaults show, a change is refused with `E_EDITOR_SETTINGS_READ_FAILED`, and the file is read again on the next read or change. A damaged file (not a JSON object) is copied to `editor-settings.json.damaged` before the next change replaces it. `src/core/editorSettings.ts` holds the same lists, ranges and defaults for the UI.
- **Editor font:** SF Mono by default, nothing bundled. Font Family also offers an installed font (`fontFamily: 'installed'`, the family in `installedFont`, listed by AppKit through `fonts_installed`) or an imported file (`'imported'`, the file name in `importedFont`). `font_import` (Settings window) asks for a TTF, OTF, WOFF or WOFF2 file in a native panel, checks its extension against its first bytes and its size (50 MB at most), and copies it into `<app data>/fonts/` (a stored file is never replaced: a different file under a taken name is stored as `Name 2.ttf`, so a window never keeps stale glyphs), which never syncs and backups never include; `fonts_list` lists that folder. `font_read` returns a stored file's bytes, checked again, and the window loads them as a `FontFace` under one family name of its own (`src/renderer/src/fonts.ts`), so no path or URL reaches the web view. Names are checked on both sides (no quotes or backslashes) before they go into the CSS font list, and every list ends with SF Mono, so a font that is missing, invalid or still loading shows SF Mono.
- **Live in every window:** after each change Rust sends `devot://editor-settings-changed` with the full settings and a revision to every window (the Settings window may listen to events for this). The revision goes up by one with each stored change, so a window ignores an answer or event older than one it has seen (two changes can announce themselves out of order). The page re-sends the event as `devot:editor-settings-changed`, which the UI tests send too. A window applies its own changes at once, keeps them on top of what Rust reports until Rust answers (a failed change is dropped), and sends them one at a time, in order. Cmd+= and Cmd+- step from the stored size once it has been read. The font size field stores a typed size once typing pauses or the field is left. Rust was chosen over the webview's local storage because a `storage` event between two WKWebViews is not guaranteed, and a file in Rust gives one validated source of truth.
- **In the editor:** font, size, weight and line height are CSS variables on the root element (`--editor-font-size`, `--editor-font-weight`, `--editor-line-height`, `--editor-font-family`), set through CSSOM, which the CSP allows; the editor's theme reads them, and `--preview-scale` (the preview's font size over the type scale's preview size) scales the preview's text, headings and notes (exported and printed pages leave the variable unset: scale 1). Everything else lives in CodeMirror compartments (`src/renderer/src/editor/settings.ts`, the basic setup with those parts split out): a change reconfigures only the parts it touches, so the open editor keeps its text, selection, undo history and focus. The gutter (line numbers and folding) goes with Line Numbers; the selection toolbar is off through a facet the toolbar checks (`toolbarOff`); Scroll Past End pads half a screen under the last line (the host element scrolls, not CodeMirror's scroller); the cursor scroll margin is a `scrollMargins` extension; invisible characters and trailing whitespace use CodeMirror's `highlightWhitespace` and `highlightTrailingWhitespace`; the readable width applies only to wrapped lines (the Settings window disables it, with a hint, while lines do not wrap) and not in split mode, where the editor and the preview take half the note area each; popups in the editor keep the UI's font size. The list marker is the bullet a new list item gets (the bulleted and task list formats, and a numbered item turned into a bullet); items that have a bullet keep it, and a new item continued with Return keeps its list's marker, since another marker would start a new list.
- **Images under their lines** (`src/renderer/src/editor/images.ts`): each line that shows images (attachments and `https` images) gets a block below it with those images, from a state field (only decorations from the state may change the editor's vertical layout). The block has one fixed height (`size.inline-image-height`), known before the images load, so nothing moves as they load or fail. An attachment that has not arrived (sync) shows a placeholder box there instead (`src/renderer/src/missingImages.ts`). CodeMirror draws only the visible part of a note, so only visible images load; finding images scans the text for `![` and asks the syntax tree only there, so long notes stay cheap. Plain `http` images do not show, as the CSP blocks them. Double-click opens the viewer; right-click opens the image menu.

## Usage events

- **Catalog:** `track(name, properties)` (`src/core/usage.ts`) takes only events declared in `USAGE_EVENTS`, and every property is an enum of fixed lowercase tokens, a count or a duration (whole milliseconds), all required. The types reject anything else; `checkUsageEvent` rejects it again at run time (an undeclared or missing property, a string that is not a declared value, a negative, fractional or unsafe number) and copies only the declared keys. A policy test scans the catalog for property names that would describe content (title, name, ID, path, query and the like). Result counts that could fingerprint a library go in as buckets (`0`, `1`, `2-5`, `6-20`, `21-100`, `101+`).
- **Events today:** `note.created` (from New Note, the `[[` popup, Duplicate, New Note from Selection or a template), `search.run` (once results have shown for a second after typing; the scope, the number of clauses and a result bucket; reruns after edits and the same query again do not count) and `import.finished` (counts of notes, notebooks, images and problems, and the duration). Adding one: declare it in the catalog, label it in the i18n catalog (`usage.event.<name>`) and call `track`.
- **Store:** Rust keeps events in their own database, `<app data>/usage.sqlite` (`src-tauri/src/usage.rs`), not in the notes database: they carry no HLC and never sync, backups never include them (restoring one cannot bring back cleared events) and devot-mcp never opens the file. Each write and each listing drops events older than 90 days and keeps the newest 10,000. Deleted rows are zeroed in the file (`secure_delete`) and clearing empties the write-ahead log too; the file uses WAL with `synchronous = NORMAL`, since a crash may cost the latest events but never notes. The command checks the shape again (a dotted lowercase name, at most 16 properties whose values are short lowercase tokens or whole numbers). Recording failures are logged by code and never reach the user.
- **Access:** only the main window may record (`usage_record`); only the Settings window may read and clear (`usage_list`, `usage_clear`, `src-tauri/capabilities/settings.json`). Settings > Usage Data shows how many events are stored and of each kind (in cards), lists them on request (newest first, at most 500 shown, keys and values as stored) and clears them after a confirmation.
- **Upload (later):** `UsageTransport` is the seam for sending events off the device. Nothing implements it. It ships with accounts, behind an opt-in switch, and only then reads the stored events.

## Security

- **Commands are least-privilege.** `src-tauri/build.rs` declares every app command, so none is reachable until a capability file (`src-tauri/capabilities/`) grants it to a window. Every command validates its arguments in Rust and returns error codes, never content.
- **CSP** in `src-tauri/tauri.conf.json`: `script-src 'self'`, no `'unsafe-inline'`, no `eval`; connections only to the app and Tauri's IPC; images also from https; iframes from https, the app itself (the diagram frame) and `devot-plugin:` (plugins' sandboxed frames, see Extensions). `freezePrototype` is on. A test checks the policy. Styles are never inline: CodeMirror runs in a shadow root, where it adds its styles as constructed stylesheets, which the policy allows.
- External links: `https:` opens in the browser; any other scheme needs an allowlist entry and a confirmation.
- Untrusted URLs (for example, link titles) are fetched by Rust, never by the UI.
- Secrets live in the OS keychain (AI provider keys: see AI > Providers).
- **Files written whole, never through a link** (`src-tauri/src/atomic_file.rs`): everything Rust writes outside the databases (exported notes and attachments, Save Image As, PDFs, diagnostics, the settings files, backups, crash reports, the Markdown mirror's files and manifest) goes to a temporary file in the target's folder, flushed to disk (the mirror's many files are not, see Markdown mirror) and renamed into place; there is no other writer (a policy test, `tests/policy/one-writer.test.ts`, refuses a file created or written by path anywhere else but the log, which appends to its own file in the app's data folder). A temporary file is only ever created new (O_CREAT | O_EXCL) under a hidden random name (`.devot-<32 hex digits>.tmp`; a crash report's is its random event ID), so a file or a link already at that name is passed over, never opened: a link planted at a name that could be guessed, in a shared or downloaded folder, would take the bytes wherever it pointed. A writer that creates its file by path itself (AppKit's PDF, SQLite's backup) writes inside a new private folder (mode 0700) made the same way in the app's data, which nobody else can reach (the mode keeps others out of the folder, not from swapping it for a link where it sits), and its file is renamed out of it or, for a PDF, copied to the chosen file. A file that must not replace anything (a notebook export's files and attachments, diagnostics, the mirror's new files) goes in place only where nothing is yet, and so does a file the mirror moves to a new name or keeps aside: in one step where the file system can (a rename that fails on any name already there, a link included, on APFS and HFS+); elsewhere (FAT, exFAT, many network shares) a new empty file claims the name first, which fails the same way, and the rename goes over it, so only something put over that claim in the instant between could be replaced. Either way a move is whole: a file never stays under both names. Every write works in a folder opened once, by a handle, never by its path again (`atomic_file::Folder`, safe system calls through `rustix`): a folder the user chose is resolved when it is opened (a link the user picked is followed then, once), and the temporary file, the rename into place, a removal and every folder below are named relative to that handle, one plain name at a time, each folder below opened from its parent and never through a link (`O_NOFOLLOW`; for search alone, `O_SEARCH`, so a folder others may only drop files into still works). So a local process that may rename entries in a folder Devot writes to (a shared or synced folder) cannot swap a folder on the way for a link between Devot's checks and its write, move or removal: an export session keeps its folder open from the panel to its last file, a PDF's folder is opened when the save panel closes, Save Image As and diagnostics open theirs once per file, and the Markdown mirror opens its folder once per call, by the path resolved when it was chosen, refusing a link anywhere on it.

### URL scheme

Devot registers `devot://` with macOS (`plugins.deep-link` in `tauri.conf.json`, which the bundler writes into the Info.plist as `CFBundleURLTypes`), so a link opened in another app reaches it (`src-tauri/src/deep_link.rs`, `src/renderer/src/deepLink.ts`).

- **What a URL can do:** `devot://license?key=<key>` offers a license (see below). `devot://note/<id>` brings Devot forward (launching it if needed) and opens the note: where it is listed, otherwise in All Notes (Templates for a template), and in the Trash if it is trashed; a note that does not exist shows a notice. `devot://command/<id>` runs one of ten commands that only show something (none makes, changes or removes anything): `palette.open`, `view.allNotes`, `view.trash`, `view.focus`, `view.togglePreview`, `view.split`, `view.edit`, `view.preview`, `app.backups` and `app.checkForUpdates`. Rust and the window keep the same list, and a test checks that they agree and that every one is a registry command; a command without a handler at that moment (Edit Mode with no note open) shows a notice.
- **Checked in Rust, whole:** a URL is accepted only as `<scheme>://note/<UUIDv7>` (the canonical lowercase form) or `<scheme>://command/<listed id>`, exactly: no query, fragment, escapes, trailing slash, other case or other host, and at most 96 bytes; or as `<scheme>://license?key=<key>`, with nothing after the key, whose characters may be percent-encoded, up to 3,104 bytes. Anything else is dropped and logged as `W_DEEP_LINK_REFUSED <code>`, never with its text. The window gets the checked link (`{kind, id}`, event `devot://open-url`), never the URL, and reads it again before acting. The deep-link plugin's own commands are granted to no window.
- **License links:** Rust verifies the key before the window sees it and sends `{kind: 'license', key, offer}` (the license ID, licensee and the state it would have) or, for a key that fails, `{kind: 'license', code}` alone; it logs `W_DEEP_LINK_LICENCE_REFUSED <code>`, never the URL, and `Debug` never shows the key. The main window adds a license to a device that holds none and says so, says nothing changed for the license it holds already, and otherwise asks first (Replace the license on this device?, naming both licensees and license IDs). It reads the license from Rust again before it decides.
- **Attachments keep their protocol:** `devot://file/<id>` is the web view's own protocol for attachments (`register_asynchronous_uri_scheme_protocol`); it never reaches LaunchServices, and the URL handler refuses such a URL from another app.
- **Debug builds** answer to `devot-dev://` instead, so a development bundle never takes the links meant for an installed Devot: `pnpm build:debug` builds with `src-tauri/tauri.debug.conf.json`, which registers that scheme, and a debug binary accepts only it. Copy Note URI still writes `devot://` (the links notes hold). Deep links need a bundle: `tauri dev` cannot receive them on macOS.
- **Timing:** links wait in Rust until a main window has restored its view and asked for them (`deep_link_take`, granted to the main windows; a reload of a page makes its window wait again until it asks) and then go to the frontmost main window that has asked (see Several main windows), and while the Settings window is open (Settings comes forward; the links follow, in order, once it closes). At most 16 links wait, and apart from them up to 64 sets of files from the `devot` command; more links are dropped, and files past that are refused at the hand-off, so the command fails (`E_CLI_HANDOFF_REFUSED`) instead of losing them. Files already released to the page wait in its queue, which Rust cannot see, so the hand-off counts imports still open there too (`Imports::open`: scanning or scanned, not yet `import_finish`) and refuses once those plus the ones Rust holds reach 64, rather than looking at its own queue alone. The window listens from the moment its page loads and holds what comes until its view is ready; there too at most 16 links and 64 sets of files wait (files dropped there end their import session), and a link the same as the one before, within a second of it, is dropped (a page that opens a link over and over). In the window, links run one at a time, each after the window has rendered what the one before did (so a link after `view.trash` sees the Trash), and a link that comes while a sheet (`<dialog>`) is up waits until none is. A note the window's lists do not hold yet (another writer made it a moment ago) is looked up in the core before the notice shows.
- **One Devot:** the single-instance plugin (`src-tauri/src/single_instance.rs`) runs first, so a second launch of the binary hands its arguments to the running Devot (which comes forward and takes any URL of its scheme among them) and exits, with status 0 and no alert, before it opens the data folder. Its socket is in a folder of the user's own, `devot-<uid>` in the user's temporary folder (`DARWIN_USER_TEMP_DIR`, whatever `TMPDIR` says), made with mode 0700 and refused unless it is a folder owned by the process's effective user; the socket is named after the folder identifier, so a debug build and the release app never meet, and a launch with HOME elsewhere still meets a running Devot of the same kind. A file at the socket's place that is not a socket of that user is never written to (`W_SINGLE_INSTANCE_SOCKET_FOREIGN`); the data-folder lock is the safety net either way. A hand-off is done only once the running Devot answers it with one byte. It answers as it takes the message, before it comes forward and finds the files (which can take longer than a sender waits); one that is quitting takes none and closes it unanswered (`W_SINGLE_INSTANCE_QUITTING`), and a message over 1 MiB is dropped whole, never cut. Only the process that holds an exclusive `flock` on `<identifier>.lock` beside the socket (for its whole life, let go at exit) removes or binds the socket, so of two launches at once the one that goes on to fail (the data-folder lock) never takes the other's socket away, and a full backlog never makes a launch remove a live one; a launch that finds the lock held waits for it on a thread of its own and binds the socket should it outlive the holder. At exit Devot removes the socket only if it is still the one it bound (by device and inode).

### Private macOS APIs

Window transparency and the 120 Hz unlock use private APIs, so Devot cannot ship on the Mac App Store.

- All Objective-C and private API code lives in `src-tauri/src/native/macos.rs`, and the iPhone app's UIKit code (public APIs only) in `src-tauri/src/native/ios.rs`: the only modules allowed to use `unsafe`. Every block carries a `SAFETY` comment.
- Every private call is guarded by `respondsToSelector:`, and so is every message to an object a private call returns, whose answers are checked for their class before use (the 60 fps lookup skips a `_WKFeature` that no longer answers `key`). Private calls run inside `guarded`, which catches an Objective-C exception (`objc2::exception::catch`) as well as a Rust panic: `catch_unwind` alone cannot stop an Objective-C exception, which aborts the app when it unwinds into Rust. When an API is missing or throws, the app falls back (60 fps, or an opaque window) and logs a code; it never crashes.
- `src-tauri/tests/main_thread.rs` checks on the main thread that the 60 fps preference can be found and toggled, that the lookup gives no feature (and no crash) for objects that do not answer `key` or a list that is not one, that an Objective-C exception inside a guarded call gives the fallback, and that the system accent reads.

### HTML and embeds in notes

Notes are not only written by the user: imports, sync and AI also write them. So the preview treats note content as untrusted.

1. **Devot's own page:** HTML is sanitized with a tag and attribute allowlist (`rehype-sanitize`). Scripts, event-handler attributes and `javascript:` URLs are removed. Safe tags such as `sub`, `sup`, `kbd`, `mark`, `details` and `summary` stay.
2. **`<iframe>`:** any `https:` source is allowed. Devot rewrites its attributes: a forced `sandbox` without top navigation, `allow` limited to fullscreen, picture-in-picture and encrypted media, a strict `referrerpolicy`, and lazy loading. Pop-ups open in the system browser.
3. **Loading:** well-known video providers (YouTube via `youtube-nocookie.com`, Vimeo, Bilibili) load directly. Other origins show a placeholder ("Embedded content from example.com · Load") and load on click. This list controls convenience only, not whether an embed is allowed.
4. **Pipeline:** the core worker parses Markdown, parses raw HTML, sanitizes, then runs the preview renderers (`src/core/preview`), which add Devot's own structure (alerts, swatches, embeds, front matter) to the already-sanitized tree. The worker returns a hast tree; the UI patches only the DOM nodes that changed, building them with DOM APIs, never HTML strings. Colour swatches get their colour through the CSSOM, so the CSP needs no inline styles.
5. **Links:** clicks in the preview never navigate the app page. `devot://note/<id>` opens the note; `https:` goes to the `open_external` command, which accepts only plain https URLs and opens them in the browser through `/usr/bin/open` (the app never waits for it, but a thread of its own reaps it, so no defunct `open` stays behind until quit). New-window requests from embeds are routed the same way by the main window's new-window handler and never create app windows. The paste chooser's page titles and GitHub snippets (`link_title`, `github_snippet` in `src-tauri/src/link_info.rs`) are fetched in Rust, never by the page, so the CSP stays as it is; they run only once the user highlights or picks a format that needs them. Every outbound request goes through `src-tauri/src/net.rs`: https only and public hosts only on every redirect hop (at most 5), by name and by the addresses the name resolves to, one 10 s cap for the whole call, a cap on the bytes read, and errors as codes, never URLs. GitHub is called without authentication, so only public repositories work. A blob link leaves the `/` of a branch name unencoded, so a snippet tries the ref as one segment after `blob`, then longer (up to 4), while the answer is not found, all within the one 10 s cap.
6. **Extension point:** preview renderers register through a versioned registry (`PREVIEW_API_VERSION`); the built-in features use the same API. A renderer may be async and load its library only when the note needs it (math loads temml, emoji loads the shortcode table). Content that needs the page's layout engine is an _island_: the worker marks it, the patcher leaves its children alone, and a UI-side island registry (same API version) renders it.
7. **Math, Mermaid, emoji:** math renders to MathML with temml (no fonts or inline styles; the web view lays it out) and passes a MathML allowlist. Inline `$` next to a space stays text, so prices are not math. Mermaid is an island. It runs in a hidden same-origin frame (`mermaid.html`), created on the first diagram, because Mermaid and its libraries assign to prototypes, which fails in the main window where `freezePrototype` freezes `Object.prototype` (Tauri freezes the main frame only). The frame talks to the preview only through a private `MessagePort`; the preview rebuilds the returned SVG node by node so the strict CSP holds: its `<style>` becomes a constructed stylesheet and `style` attributes go through the CSSOM. The preview sends one request at a time (Mermaid's settings are global) and the frame draws each in a container of its own; a failure says why: an error in the source stays until the source changes, and so does a returned drawing that cannot be read (logged with its code); a failure that may pass (a drawing that broke, no answer in time: the limit starts when the request is sent, and loading the frame has a longer limit of its own, so a slow start is not a failure) is logged with its code and drawn again at the next mount, and only its message says it is tried again. A drawing's stylesheet is freed when the drawing is replaced or removed and when the preview closes. The CSP's `frame-src` allows `'self'` for this frame; notes can still only embed https.
8. **Code blocks:** the fence's info string (` ```js `, ` ```js:app.js `, ` ```js title="app.js" `) is read from the note's Markdown at the block's position. A block with a language or a title gets a header with the language's name and mark (an SVG path from a fixed table, `design/icons/languages.json`) and its title as text; the page's copy button sits in that header. Highlighting is lowlight with a fixed set of highlight.js grammars, loaded only for notes that need one; its output is `span.hljs-*` and text, coloured by the syntax tokens. Blocks over 20,000 characters stay plain.
9. **Task lists and front matter:** a task's checkbox carries where its mark is in the Markdown (`data-task-at`); a click in the preview ticks it through the editor, which checks the text is still that box. Exported pages disable every box. Front matter that is a map of keys shows as a compact properties block (lists as chips); other YAML shows as code. The main window's live preview also gets the note's own title, status and tags and the library's tag colours (`note` in the preview options; only the first piece, which holds the front matter, renders again when they change). There the `tags` row shows the tags as the import reader reads them (`readFrontMatter`), each chip in its tag's colour with the header's chip classes and tokens (plain when no tag of that name has a colour), and the `title`, `status` and `tags` rows that differ from the note show the note's value in a quiet badge ("Note: Active") and an Apply button (`data-frontmatter-apply`, handled in the preview's click like a task box): it sets the field through the same services as the title field and the header pickers, so undo, sync and saving are theirs (status read as import reads it; tags made when missing, as templates make them, and the note's other tags taken off; the title cut to the title limit on one line). Status text that names no status shows the badge without Apply, and a read-only window shows no Apply. Front matter stays text in the body: nothing is read from it on save. HTML export, Copy as HTML, print and PDF, templates and the note window's preview get no note fields and show front matter as written.
10. _Later hardening:_ render the preview in a script-less sandboxed iframe, with math and Mermaid pre-rendered to SVG in the worker.

## Sync and encryption (phase 2)

- **Protocol first:** a versioned message format over WebSocket, with no dependency on any one host.
- **Relay** (`relay/`, docs/sync-relay.md): plain TypeScript logic over a storage interface (the host's SQLite) with two implementations: a Cloudflare Worker in front of one Durable Object per vault on SQLite storage, and Node + SQLite (a file per vault) for a server. One test suite runs against both, the Durable Object locally in workerd through Miniflare. The relay URL is a client setting. The app never imports the relay; the relay takes from the app only the wire format (`src/core/sync/protocol.ts`).
- **Protocol (version 1):** JSON envelopes `{v, type}`; a message with chunks travels as one binary frame (header length, JSON header, raw chunks). `pull(since)` in pages, `push(id, base, kind, chunks)` as one SQLite transaction with compare-and-swap on the version, `changed(seq)` to the vault's other connections; `welcome` on connecting gives the relay's time and the vault epoch. Devices enroll by presenting an enrollment secret derived from the vault key (the relay stores only its verifier) and get a device token, of which the relay keeps only the hash; the front checks the token's MAC (keyed from the relay's own secret) before anything reaches the vault. Device list and revoke go over the socket. Pairing has HTTP routes of its own under `/v1/pairings/` (docs/sync-relay.md); a relay from before them answers `E_SYNC_NOT_FOUND`, which the client reports as `E_SYNC_RELAY_OUTDATED`.
- The relay is not a source of truth. Every device holds the full data, so moving to another relay means pointing clients at a new URL; they re-upload.
- The relay only sees ciphertext. It stores the latest encrypted state of each record, and clients merge on a rejected push (docs/adr/0002-sync-latest-state-per-record.md).
- **First deployment:** a dedicated Cloudflare account on the Workers Free plan. When a free limit is exceeded, requests fail instead of being billed; the worst case is that sync pauses until the daily reset, while local data is unaffected.
- **Cost guards (required on any host):** the WebSocket Hibernation API only; client reconnects with exponential backoff, jitter and a rate cap; a changed record pushed after 3 s without edits, and at most every 10 s while typing; server-side per-device rate and message-size limits; a client circuit breaker that stops sync when it detects abnormal send rates; a self-imposed cap at 80% of every free limit the relay can count (on by default on Node too, `RELAY_QUOTA=off` turns it off there; docs/sync-relay.md, Quota).
- **Attachments** (docs/adr/0003-sync-attachments-as-records.md, #327): one encrypted record of kind `file` per attachment on the same relay, downloaded by every device, within a 3 GB share of the relay's storage.
  - **Record** (`src/core/sync/records.ts`, `FileState`): `format byte || header length || JSON fields || image bytes`; the fields are the ID, name, MIME type, size, `noteId` with `noteHlc` (the clock of its last change; '' for a file never passed on), `createdAt` and `purged`. A purged file is a tombstone with only its ID and `purged`, kept forever. Migration 0022 adds `files.note_hlc`, lets `sync_records` hold `file` and puts triggers on `files`, so an attachment is pending like a note; a purged one has no row, only its entry, which the engine reads as the tombstone.
  - **Merge:** the bytes are written once, so only the owner merges: the higher `noteHlc` wins (equal clocks: the greater note ID); a purge wins over everything. `HAND_OVER_FILES_SQL` dates the new owner with the purge's HLC, so every device settles on the same note.
  - **Upload order:** before the first push of a note, the engine pushes the attachments its body links (up to 500, not yet synced). The bytes cross to Rust as base64 only when the record is pushed (`sync_file_data`).
  - **Checked on both sides:** `src-tauri/src/sync/file_record.rs` checks a file record as a paste is checked (`validate_upload`: a known raster image of at most 10 MiB, SVG refused, the type and size the header names) on the way out before it is sealed, and on the way in before the web view sees it; the core checks again (`decodeRecord`), and `sync_file_put` once more before the row is written. A record that fails is logged by code and ID (`W_SYNC_FILE_REFUSED`, `W_SYNC_RECORD_SKIPPED`) and left out. An existing row never takes new bytes.
  - **The share:** the relay refuses a push past 3 GB of file records with `E_SYNC_ATTACHMENTS_FULL` (`PushResult` `full`). The attachment stays local and is counted as unsynced; notes keep syncing. The engine does not offer a larger image once a smaller one was refused, tries again after a purge (pushed or pulled) frees room, and on the next launch. A relay that does not say `attachments` in its `welcome` is sent no image (`E_SYNC_RELAY_OUTDATED`; docs/sync-relay.md, Update the relay). Settings > Sync shows how many images are not synced and why (`unsyncedFiles` in the status Rust keeps).
  - **A link whose image has not arrived** shows a placeholder at `size.inline-image-height` in the editor and the preview (`src/renderer/src/missingImages.ts`): an `<img>` that fails to load from `devot://file/<id>` is marked `image-missing` (an empty alt keeps the web view's broken-image icon away), and loaded again whenever the database changes, which is how a pulled image arrives.
- **Encryption:** AES-256-GCM, done in Rust. Keys come from device pairing: the first device generates the key, new devices pair by a one-time code (QR code or text), and keys live in each device's keychain. A recovery key is shown for printing or safe storage until the owner says it was saved.
- **Vault** (`src-tauri/src/sync/`): a random vault ID (a UUIDv4) and a 256-bit vault key from the OS random source, made on the first device that turns sync on. Both live in one keychain item (a generic password, service `<folder identifier>.sync`, so a debug build's `.dev` never reads the installed app's vault; never synced through iCloud; on iOS readable after the first unlock and kept off backups), never in files, settings or logs. Making or restoring a vault adds the item only when the keychain holds none (`SecItemAdd`, which refuses a duplicate in one step, so two windows or processes at once cannot both add), so a key that may be the only copy is never replaced. No command returns the key or a secret derived from it, and only `sync_recovery_key` returns the recovery key, until this device says it was saved: the core hands plaintext records to Rust and gets plaintext back, and Debug output and errors show the vault ID at most.
- **Records:** each record is sealed under a record key derived from the vault key (HKDF-SHA256, salt the vault ID, its own label) and cut into chunks of at most 1.9 MB (1,900,000 bytes, nonce and tag included), each `format byte || 96-bit random nonce || ciphertext || tag`. The additional data is a label, the vault ID, the record ID, the record version, the chunk's index and the chunk count, so a swapped, replayed, reordered, truncated or extended chunk set fails to open (`E_SYNC_CHUNK_AUTH`). A record holds at most 80 MiB of plaintext (a note's Yjs state may take 64 MiB); record IDs are 1 to 64 ASCII letters, digits and hyphens. Rejecting an older version the relay replays under its old number is the client's job (it remembers the versions it has seen).
- **Enrollment:** any holder of the vault key derives the enrollment secret (HKDF-SHA256, its own label) and presents it to the relay, which keeps only its verifier, SHA-256 over a label and the secret (`enrollmentVerifier`, the same in Rust).
- **Client engine** (`src/core/sync/engine.ts`, in the main window's core worker; docs/adr/0002-sync-latest-state-per-record.md, Client): the core builds and merges records, Rust seals them and holds the socket. A record is a note (with its tag memberships), a notebook or a tag under its own ID (`src/core/sync/records.ts`): `format byte || header length || JSON fields || Yjs state`. Allow AI Access is not in it (each device decides what devot-mcp may read), nor are revisions; an attachment travels as its own `file` record (#327).
  - **What changed:** every write of a note row, its tag rows, a notebook or a tag moves its `sync_records.edits` on (triggers in `migrations/0019_sync.sql`, so writes from devot-mcp count too); the engine looks at a record while `edits` differs from `synced` and pushes it only when its fingerprint (the fields, and the body's state vector and delete set, so equal content gives an equal print whatever the bytes) differs from the one the relay's version stands for here (`fingerprint`). The engine's own writes of another device's state set that print, so they are never pushed back.
  - **Push timing:** after 3 s without writes, at most 10 s after the first of a run of writes (`PUSH_IDLE_MS`, `PUSH_EVERY_MS`). A push is based on the version this device last saw; the relay's compare-and-swap rejects it when another device wrote first, and the engine pulls (which merges), then pushes again, at most 5 times with backoff and jitter; past that the record waits for the next `changed`. One record pushed more than 30 times in a minute is a loop, not typing: sync stops with `E_SYNC_CIRCUIT_OPEN`.
  - **Pull and merge:** pulls page from the cursor in `sync_state` (`since`); a version not above the one already seen is a replay and is skipped. Body: both Yjs states in one document. Metadata: per field the higher HLC (dates as storage merges them, tag memberships each by their own HLC); notebooks and tags the same, sort keys at equal HLCs the greater key. The merged note is written through `putNote`'s compare-and-swap, so a local save meanwhile is merged in, not lost, and the note service then takes it in as it does another process's writes. A note open in a note window gets it through the main window's core (`mergeStored`): a note that core holds relays what it took in, title included, as its own changes; one it does not hold, but another window spoke of, is relayed its stored state, once for each write. A record that does not open or read is logged by code and ID and skipped; a storage failure stops the pull, to retry.
  - **Trash and purge:** the Trash is the note's `deletedHlc` field, the higher HLC winning. Each record also carries `bodyHlc`, stamped when the engine finds the body changed here (not while the note is in the Trash); a body or title change after the move to the Trash brings the note back on every device, the same way (`deletedHlc` becomes that edit's HLC). A purge is a tombstone (ID, `purged`, deletion; no body) that wins over everything, and is kept forever.
  - **Clock and epoch:** the engine refuses to sync while this device's clock is more than 5 minutes off the relay's (the `welcome` time; `E_SYNC_CLOCK_SKEW`, checked again every 5 minutes). A `welcome` with another vault epoch than the one stored (a relay that lost its data, or a new relay) resets every record to version 0 and uploads everything again.
  - **Stops and notices:** `E_SYNC_REVOKED`, an unknown device, a missing vault key or token stop sync until the user acts; the window says so in a notice, and a revoked device keeps its credentials marked so it never enrolls again on its own. A relay without the vault (`E_SYNC_NO_VAULT`, for example after it lost its data) makes the device drop its token, so Settings > Sync asks for the relay secret again to create the vault there under a new epoch. A record past the relay's limits (16 chunks, found before anything is sent: `E_SYNC_TOO_LARGE`) stays on this device; the notice and Settings say how many. Network failures retry with exponential backoff and jitter (1 s to 5 minutes); the relay's `E_SYNC_RATE` is waited out in Rust.
  - **Quota cap** (docs/sync-relay.md, Quota): the relay refuses pushes past 80% of a Workers Free limit it counts (rows written and requests a day, stored bytes in total) with `E_SYNC_QUOTA` and `until`, its next 00:00 UTC; pulls stay allowed. The engine closes the socket, reports `paused` with that time (the notice and Settings > Sync say "Sync paused until" it, in local time), and connects again once, at a random moment in the minute after it (measured on the relay's clock from the `welcome`, checked at least hourly, since a timer falls behind while the machine sleeps); a refusal without `until` (a relay that did not say) waits for the next 00:00 UTC. A refusal for `storedBytes` lasts past the reset, so the pass goes on with the records that fit (smaller ones, purges) and pauses after it. A pass the socket closed in the middle of stops there, so the upload keeps its place. Local work goes on. A backlog of at least 100 records (a first upload, a new epoch) reports its progress, records sent of the total; the total is kept in `sync_state` (`uploadTotal`) and what is left is the pending count, so a restart keeps its place and a large vault uploads over several days. A `welcome` without `quota` comes from a relay older than the cap: sync goes on, and Settings > Sync says to update the relay.
- **Transport** (`src-tauri/src/sync/client.rs`, `service.rs`): vault creation and enrollment over HTTP (ureq: no redirects, no proxy), the socket over tungstenite on a thread of its own, both over the system TLS stack; https only, or http to this machine. The device token lives in the keychain beside the vault (account `device`, with the relay's URL and the vault ID it belongs to), never in a file or the web view. A token the relay's front refuses (its secret changed) makes a device that holds the vault key enroll again; a device the vault does not know (revoked) does not. A device with the vault key and no token for the relay enrolls on its own; joining (below) enrolls at once.
- **Settings > Sync:** the relay's URL, Join With a Code and Join With Recovery Key on a device that is not in a vault, then Set Up a New Vault for the first device only, which asks for the relay's secret (once, sent in that one request and never stored), the recovery key (offered from the first time the vault is ready on a relay until I Saved It, across pane switches and closed windows; Copy puts it on this Mac's clipboard only, marked concealed and transient, and clears it after 90 seconds unless something else was copied: `clipboard_write_secret`), Add a Device (a pairing code with its QR code, countdown and Cancel) and Devices (this one marked; Remove asks first, then revokes the other's token) on one that is, sync on or off, and the status the engine reports through Rust (state, last sync, code, records kept here, when a quota pause ends, an upload's progress, a relay to update). Settings live in `<app data>/sync-settings.json`, with the vault whose recovery key was saved (`recoveryShown`, a vault ID). Pairing and joining need the license (`E_LICENCE_REQUIRED`); listing and removing devices do not.
- **Pairing** (docs/adr/0008-sync-device-pairing.md, `src-tauri/src/sync/pairing.rs`): a device that syncs makes a 128-bit pairing secret and shows it as a pairing code (32 Crockford base32 characters with a version and a checksum, in groups of four) and as a QR code of `devot://pair?relay=…&code=…`. Both devices derive from the secret, with HKDF-SHA256, the pairing ID the relay files it under and a key the relay never sees. The showing device seals the offer (the vault ID and key and its expiry) under that key and leaves it on the relay for 10 minutes; the joining device takes it once, opens it, enrolls on its own, and only then keeps the token, the vault (never replacing another one: `E_SYNC_VAULT_EXISTS`, checked before the offer is taken) and sync on, and returns its device ID sealed under the same key, which the showing device opens before it reports the pairing. The showing device polls every 2 seconds, through an unreachable relay too, and closes the pairing then, on Cancel, when the Settings window is destroyed (`sync::on_window_event`), when polling fails otherwise, and at the expiry, or, when the offer was taken, after the relay's minute of grace; a taken offer never confirmed ends as `unconfirmed`, which Settings warns about. An offer or confirmation that does not open (`E_SYNC_PAIRING_AUTH`) leaves nothing behind; an offer past its sealed expiry by more than 5 minutes is refused (`E_SYNC_PAIRING_EXPIRED`). The new device never learns another device's token. Rust joins only through the relay set in Settings: a link for another relay is refused (`E_SYNC_PAIRING_RELAY`), and Settings asks, naming the host, before it sets the relay a link names. A removed device keeps a revoked mark per vault and never enrolls again on its own, under any relay address; it still holds the vault key, so it can join again on purpose until key rotation exists. The page sees the code and the QR code's modules (drawn in `color.qr.*`) while the code is on show, and the outcome; Rust keeps the secret and the key.
- **Recovery key:** the vault ID and key with a version byte and a 4-byte checksum (SHA-256 over a label and the rest), as 85 characters of Crockford base32 in groups of five. Reading it ignores case, spaces and hyphens and takes O for zero and I or L for one; a mistyped key fails its checksum (`E_SYNC_RECOVERY_CHECKSUM`) before anything uses it. Entered with the relay's URL on a new device, it restores the vault into the keychain (or finds it there already), enrolls the device and turns sync on; it needs nothing a relay from before pairing lacks.

## Updates

- **The updater** (`src-tauri/src/updates.rs`, `docs/releasing.md`): Tauri's updater reads a channel feed in the repository's `updater` release (`beta.json` for a prerelease build, `stable.json` otherwise) 30 seconds after launch, then daily (hourly on the beta channel) and on Check for Updates. A build without the updater's public key has no updater. Rust holds the status and sends `devot://update-status` (with a revision) to every window; with `autoDownloadUpdates` on (the default) a found update downloads in the background and Restart to Update installs it.
- **Revocations:** the same scheduler thread fetches `<license site>/revoked` once a day, 30 seconds after launch and then when due, also in a build without the updater key, as long as the build gates and a license that verifies is held. It downloads the list whole through `net::get` (https, public hosts only, a time cap and a size cap of 1 MiB; the system TLS stack and the proxy settings the web client reads from the environment) with no query, cookie or license-specific header, so the Worker never learns which license a device holds. `License::apply_revocations` verifies it and ignores one older than the list kept. A failure is logged as `W_LICENCE_REVOCATIONS_FETCH_FAILED <code>` (or `W_LICENCE_REVOCATIONS_REFUSED <code>` when the list does not verify) and changes nothing; a successful fetch waits a day, while a failed one is tried again at the scheduler's next 15-minute wake.
- **Tests:** Rust unit tests for the status the page reads and the revocation fetch (against a server on this machine, and with a fake transport for the failures); `tests/ui/updates.spec.ts` for the notices. A license plays no part in what the updater offers: a valid license unlocks every version.

## Licences

- **The app** (`src-tauri/src/licence/`, docs/licensing.md, The app): Rust parses and verifies a key exactly as docs/licensing.md (Formats) says, with `ed25519-dalek` (`verify_strict`), against the public keys the build holds by `kid` (`licence/keys.rs`: a committed table of production keys (kid `2026-10` since v1.0.5-beta1); the test vectors' `test` key in test and debug builds only). The key lives in the keychain (a generic password under the app's identifier, account `license`, beside the AI keys), read once per run; a read the keychain refuses (a denied access prompt, say) shows `E_LICENCE_KEYCHAIN`, leaves the item as it is and is tried again at the next tick rather than at each write, each of which would prompt again. The state is none, valid (in every version: nothing in a key ends), revoked (the ID is in the last verified revocation list, kept in `<app data>/license-revocations.txt` and verified again on every read; an older list never replaces a newer one) or invalid (with `E_LICENCE_MALFORMED`, `E_LICENCE_UNKNOWN_KID` or `E_LICENCE_SIGNATURE`). Until the build holds a production key nothing is gated, the trial never starts and the keychain is not even read to say so.
  - **The trial** (`licence/trial.rs`): the first launch of a build with a production key begins a 72-hour trial, also on a device that used an ungated build before. Its start and the latest time seen are one keychain item beside the license (account `trial`, JSON `{start, seen, ended}` in milliseconds), which outlives a reinstall. It runs while `start <= now < start + 72 h` and `now` is not more than an hour before the latest time seen. A clock set back further ends it for good (`ended`, written at once, `W_TRIAL_CLOCK_SET_BACK`). The latest time seen is written at launch and every 10 minutes (not while a license is valid; a write the keychain refuses waits the 10 minutes too, as each may bring back its prompt) by a thread that looks at the trial every minute (`License::tick`) and sends `devot://license-changed` when what the windows show changed (the trial ended); it is not written on writes. An item the keychain cannot give, or one that does not parse, counts as ended (`W_TRIAL_UNREADABLE <code>`, read again at the next tick); a damaged item never begins a new trial. A valid license overrides the trial.
  - **Commands:** `licence_get` (main, note, quick capture and Settings windows: gated, state, code, license ID, licensee, plan, and the trial's state, end and code; never the key), `licence_set(key)` (main and Settings: drops the spaces and line breaks a mail client wrapped the key in, verifies it and refuses one that fails with its code, changing nothing), `licence_remove` (Settings only) and `settings_open_licence` (main and note windows: Settings at its License pane, `settings.html?pane=license`, or `devot://settings-pane` to an open one). Every change goes to every window as `devot://license-changed`.
  - **Enforcement:** with gating on, no valid license and the trial over, `SyncService` refuses to create a vault and to connect, and `Ai::generate` (the one path every AI request takes: edit proposals, next edit suggestions, every provider) refuses before it reads a key, all with `E_LICENCE_REQUIRED`. A device that already syncs stops at its next connect: the engine treats the code as one that stops sync, and the main window starts the engine again when the license changes.
  - **Read-only:** every write of user content refuses with `E_LICENCE_REQUIRED` too. The database hands its store out shared for reads (`Db::call`) and exclusively only through `Db::write(kind, …)`, after the gate `License::require_write` (set at launch, `Db::guard`), so no write reaches SQLite another way: note bodies and metadata, revisions and their deletion and compaction, notebooks, tags, attachments and their copies, the Trash and purges, sync's incoming changes and purges, and restoring a backup. Imports, templates, quick capture, the local HTTP API and plugins all write through those commands. Kind `Body` (`note_put`, `revision_put`) is still taken for five minutes after a trial ran out (not one the clock ended), so a save in flight lands; kind `Bookkeeping` (sync's own state and reset, rebuilding the search index) is never refused. Quick capture (`quick_capture_save`) and the local HTTP API (its write routes, 403) refuse before the main window is asked, since the core keeps an edit it could not save pending. Settings, window state, the license and the trial, making backups, exports and the Markdown mirror keep working. The devot-mcp CLI writes the database itself and is not covered (it is not shipped).
  - **Windows:** while editing is not allowed (`useEditing`, `entitlements.has('editing')`, which also turns at the trial's end by the window's own clock), the editor is read-only (`EditorState.readOnly` and a change filter that lets only Yjs changes from other replicas through; no paste or drop; no format, table or image bars), the title, notebook, status and tags are read-only, the commands that change notes (`changesNotes` in the registry: formats, inserts, table edits and every command that makes, moves, tags or deletes) leave the window's shortcuts, menus and palette, context menu items that change notes are hidden (`edits` on a menu entry), rows are not dragged, New Note and New Notebook are disabled, the Trash's, a selection's, a version's and a backup's restore and delete are disabled, and quick capture keeps its draft and saves nothing. When the trial ends during a session the windows save what was typed (`flush`) as they turn read-only. One bar in the main and note windows says the trial has ended and notes are read-only, with Buy a License and Add License; nothing dismisses it. Once, when less than 24 hours are left, a notice says the trial ends today or tomorrow at its time, with the same buttons; Dismiss is kept (`devot.trial.reminded` in local storage, by the trial's end) and it never comes back.
  - **Logs** carry codes and the license ID (`I_LICENCE_SET license=<id>`, `I_LICENCE_REMOVED`, `W_LICENCE_REFUSED <code>`, `I_LICENCE_REVOCATIONS issued=<at> count=<n>`); the key and the licensee never reach a log, an error or a `Debug` line, and a test checks it.
  - **Settings > License:** the state in a sentence, the trial's end and time left while it runs (or that it ended), licensed to and license ID; a field to add or replace a key, Remove License… (asks first), and Buy a License, which opens `https://licence.devot.online/buy` in the browser through `open_external` (the address is one constant, `LICENCE_SITE` in `src/renderer/src/license.ts`). Settings > Sync and Settings > AI show a locked row with Buy while their feature is locked, saying the trial has ended when that is why; Edit with AI is not offered once the trial is over, and a refusal from Rust says a license is needed; a Suggest Next Edit key press says so in a notice (a pause asks nothing); the main window's sync notice says sync stopped for want of a license (the trial having ended), with Buy.
  - **Tests:** the Rust tests read `licence/test-vectors.json` and check every entry (valid keys, each invalid key's code, the list and its tampered copies), the malformed shapes, the states, gating both ways, the stored list, and AI and sync refusing with nothing sent (the sync test against the Node relay); the trial's states (fresh, running, ended, the clock set back, a later launch, a license over it, an ungated build, an unreadable item, the ten-minute write) and the write gate (`storage::db`, the HTTP API's writes, the grace). `tests/core/entitlements.test.ts`, `tests/core/sync-license.test.ts`, `src/renderer/src/licenceView.test.ts`, the registry's and the menus' tests, `tests/ui/license.spec.ts` (Settings > License, the locked features, the link) and `tests/ui/trial.spec.ts` (read-only mode, the bar, the reminder, the trial in Settings > License, quick capture) cover the windows.
- **License Worker** (`licence/`, docs/licensing.md, ADR 0006): a Cloudflare Worker on the owner's account with a D1 database, the one hosted service. It creates Stripe Checkout Sessions (Managed Payments, or Stripe Tax when a variable says so), issues one Ed25519-signed license key per paid session from the webhook or from the success page, whichever comes first, mails keys through Resend's HTTP API (a `fetch` call with an idempotency key; runs on Workers Free), mails them again on request (`/resend`, the same answer whatever the address, rate-limited) and serves the signed list of licences revoked by a full refund or a lost dispute (`/revoked`). Its pages and email look like devot.online in light and dark, with the stylesheet and Copy script on fixed routes under a strict CSP (no inline script or style), `no-store`, `no-referrer` and no framing. D1 holds licences, purchases (Checkout Session, Customer and PaymentIntent IDs), refunded PaymentIntent IDs and rate-limit counters; no email address, no key and no notes. Stripe is a small `fetch` client with a pinned API version, the mailer and the store are interfaces, and the tests run every route on a real D1 database in workerd through Miniflare with Stripe and the mailer faked. The key and list formats, and the test vectors the app's Rust check reads (`licence/test-vectors.json`), are in docs/licensing.md. The app never imports the Worker.

## Local HTTP API

Other tools (launchers, scripts, editor integrations) can read and write notes while Devot runs, through a local HTTP API (`src-tauri/src/http_api/`, desktop only). Settings > Integrations > Local HTTP API turns it on (off by default), sets its port and shows its token. Every request passes these guards before anything reaches the notes:

- **Where it listens:** `127.0.0.1` only, on the port in Settings (27484 by default; 1024 to 65535), never on another interface. The settings are `<app data>/http-api.json` (`enabled`, `port`, `scope`): on this device only, never synced, never in backups. A port another program holds leaves it on but not listening, and Settings says why (`E_HTTP_API_PORT_IN_USE`); the next change, or the next launch, tries again. It starts at launch when on (off the launch's thread, since it reads the keychain) and stops when turned off; a request already being answered finishes.
- **Reading a request:** HTTP/1.1 (or 1.0), one request a connection (`Connection: close`), read by hand to small limits: a head of at most 16 KiB and 64 headers (`E_HTTP_HEADERS_TOO_LARGE`, 431), the whole request within 10 s (`E_HTTP_TIMEOUT`, 408), at most 8 connections at once (`E_HTTP_API_BUSY`, 503). A header that must be single and comes twice is refused (`E_HTTP_BAD_REQUEST`).
- **DNS rebinding and browsers:** the `Host` header must be `127.0.0.1:<port>` or `localhost:<port>` (`E_HTTP_HOST_REFUSED`, 403); a request with an `Origin` header, whatever its value (`E_HTTP_ORIGIN_REFUSED`), or a `Sec-Fetch-Site` or `Sec-Fetch-Dest` header (`E_HTTP_BROWSER_REFUSED`) is refused, since only a browser sends them and no page script can set them. `Sec-Fetch-Mode` alone is no sign of a browser (Node's `fetch` sends it) and passes. No response ever carries a CORS header, so a web page can never read one; every response is `application/json` with `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`.
- **Token:** every request carries the per-install token as `Authorization: Bearer <token>` (`E_HTTP_TOKEN_MISSING`, `E_HTTP_TOKEN_INVALID`, 401 with `WWW-Authenticate: Bearer`), compared in constant time. The token (`dvt_` and 32 random bytes in base64url) is a generic password in the keychain (service the app identifier, account `http-api-token`), never in a file or a log; it is made the first time the API is turned on. Settings reads it only when asked to show or copy it (`http_api_token_reveal`, the Settings window only); its status line otherwise says only whether one is stored. New Token, or choosing another access, makes a new one: the old one stops working at once, without a restart. A build without a keychain cannot turn the API on.
- **Scope:** the token grants read or read and write (`scope`, Read Only by default), chosen when it is made: changing the access in Settings makes a new token. A write with a read-only token is refused (`E_HTTP_READ_ONLY`, 403).
- **Rate limit:** 30 requests at once and 10 a second after that, for the token (`E_HTTP_RATE_LIMITED`, 429, with `Retry-After`). Refused requests do not use it up, so a page flooding the port cannot lock a tool out.
- **JSON only, size limits, validation in Rust:** a call that takes a body needs `Content-Type: application/json` (`E_HTTP_JSON_REQUIRED`, 415) and a `Content-Length` (no chunked bodies: `E_HTTP_LENGTH_REQUIRED`, 411) of at most 2 MiB (`E_HTTP_BODY_TOO_LARGE`, 413, refused before the body is read); one that takes none is refused with a body (`E_HTTP_BODY_UNEXPECTED`). Rust parses the body as an object of exactly the fields the call has (`E_HTTP_BODY_INVALID`) and checks them to devot-mcp's limits (`routes.rs`: Markdown at most 1 MB, `MAX_AI_BODY_BYTES`, else `E_NOTE_BODY_TOO_LARGE`; 1 to 50 patches; at most 50 tags; a query of 1 to 1,000 characters and a limit of 1 to 50, `E_HTTP_QUERY_INVALID`). A path that names no note ID answers like an unknown note (`E_NOTE_NOT_FOUND`). The core checks everything again to its own limits.
- **Errors and logs:** an error is `{"error": "<code>"}`, never content; the status follows the code (`E_NOTE_NOT_FOUND` and `E_BOOK_NOT_FOUND` 404, `E_BOOK_NAME_TAKEN`, `E_BOOK_AMBIGUOUS` and the patch codes 409, other codes of the core 400, `E_STORAGE_BUSY` 503). Each request is logged by its call, status, code and note ID (`I_HTTP_API_REQUEST notes.update 200 <id>`, `W_HTTP_API_REQUEST …`; a note made is logged by its new ID); requests refused before they name a call are logged as `W_HTTP_API_REFUSED <status> <code>`, at most 20 at once and one a second after that, so a flood cannot fill the log.

**Calls** (the contract with the core is `tests/support/http-api-calls.json`, which both the Rust router and the core's handler are tested against):

| Request                                                                               | Call                                    | Answer                                                                          |
| ------------------------------------------------------------------------------------- | --------------------------------------- | ------------------------------------------------------------------------------- |
| `GET /v1/notebooks`                                                                   | `notebooks.list`                        | `{ notebooks: [{ id, name, notes }] }`, in the sidebar's order                  |
| `POST /v1/notebooks` `{ name, parent? }`                                              | `notebooks.create` (write)              | 201 `{ id, name }`                                                              |
| `GET /v1/tags`                                                                        | `tags.list`                             | `{ tags: [{ name, notes }] }`                                                   |
| `GET /v1/notes?q=<query>&limit=<1-50>`                                                | `notes.search` (the app's query syntax) | `{ results: [{ id, title, notebook, updatedAt, snippet }] }`                    |
| `POST /v1/notes` `{ title, markdown, notebook }`                                      | `notes.create` (write)                  | 201 `{ id, title, notebook }`                                                   |
| `GET /v1/notes/<id>`                                                                  | `notes.read`                            | `{ id, title, notebook, status, pinned, tags, createdAt, updatedAt, markdown }` |
| `PATCH /v1/notes/<id>` `{ title?, markdown? \| patches?, notebook?, tags?, status? }` | `notes.update` (write)                  | the note as `GET` answers it                                                    |
| `DELETE /v1/notes/<id>`                                                               | `notes.trash` (write; never purges)     | `{ id, title, trashed: true }`                                                  |

Times are ISO strings; a notebook is named by ID or exact name. The calls and their rules are devot-mcp's tools (see AI): the same core service answers both.

- **Through the core:** Rust writes and reads no notes itself. A checked call goes to the main window as an event (`devot://http-api`, `{ id, op, note, args }`) and Rust waits up to 15 s for the answer (`http_api_done`, main window only: the JSON, or a code; anything else becomes `E_HTTP_API_FAILED`). No answer in time answers `E_HTTP_API_TIMEOUT` (504); a write the window finishes after that still lands. Tauri sends an event no window listens for without an error, so a call made while the main window is not listening (still starting, or reloading) also waits the 15 s and times out (`E_HTTP_API_UNAVAILABLE`, 503, is only for an event that could not be sent). The window runs calls one at a time (`src/renderer/src/httpApiHost.ts`); its core first saves pending edits, so a call reads and changes what the editor shows, then runs it through the AI service (`src/core/httpApi.ts`, `createAiService` in the worker with its own note service on the window's storage, and the AI queries made of the plain storage calls, `aiStorageOver`). So access follows Allow AI Access exactly as for devot-mcp (see Access control: a note in a notebook without it answers `E_NOTE_NOT_FOUND`, a notebook `E_BOOK_NOT_FOUND`), bodies go in as Yjs operations of the text difference, metadata by HLC under this install's node, and the body as it was is kept in History first. After a write the window takes it in as a change from outside (`devot:db-changed`, see Picking up changes): notes in memory merge the stored copy, the open editor takes it without an undo step (see Merging and history), and the lists reload. The Markdown mirror follows the writes like any other. Unlike devot-mcp's, a call's steps are not one storage transaction: the window's storage commits each Rust storage call on its own and has no transaction across calls. So a failure between two steps (`E_STORAGE_BUSY`, say) can leave part of a call written: `POST /v1/notes` an empty note with its title (a retry makes a second one), `PATCH` the body written and not the tags or the notebook. `tests/core/lineage.test.ts` checks that an API write while the editor types merges with another device's edit, each change once.
- **Tests:** `src-tauri/src/http_api/tests.rs` runs each guard over a real socket (no token or a wrong one, a wrong `Host`, any `Origin`, oversize heads and bodies, the rate limit, a read-only token, non-JSON, slow and surplus connections), checks that no response has a CORS header, that the log holds no content or token, and that every request of the contract routes to its call; `tests/core/http-api.test.ts` runs every call of the contract on real SQLite through storage without AI queries, as the app's, and checks what a hidden notebook leaves unseen; `tests/ui/http-api-settings.spec.ts` covers Settings.

## Menu bar mode

Settings > General > Keep in Menu Bar (`menuBar` in the editor settings, off by default; `src-tauri/src/menu_bar.rs`, desktop only) keeps Devot running in the menu bar.

- **While it is on:** a menu bar icon shows, a template image of the dove (`design/app-icon/menu-bar.svg`, drawn by `pnpm app-icon` into `src-tauri/icons/menu-bar/template.png`, 36 px for the 18 pt status item, compiled in with `include_image!`), so macOS tints it for the menu bar's appearance. A click on it opens quick capture; its menu (right click or Control-click) has New Quick Note, Open Devot and Quit Devot. Control-Option-Command-N opens quick capture from any app (`QUICK_CAPTURE_SHORTCUT`, registered in Rust through the global shortcut plugin, no window is granted the plugin's commands; the registry reserves the key as `QUICK_CAPTURE_KEY` so no command takes it, and a policy test keeps the two alike). Turning the setting on or off applies at once, on the main thread; an icon that cannot be shown leaves the mode off (`W_MENU_BAR_ICON_FAILED`), and a shortcut another app holds is logged (`W_QUICK_CAPTURE_SHORTCUT_FAILED`) with the icon still working.
- **Closing the last main window shown hides it** rather than quitting (`exit::on_window_event`; with several main windows see Several main windows): its core keeps running with every unsaved edit, the page saves as it does when it goes out of sight (`visibilitychange`), and a quit from anywhere (the app menu, the icon's Quit Devot) runs the save handshake as before (see Saving and quitting). A window that cannot be hidden quits as before. Open Devot (the frontmost main window), a click on the Dock icon (`RunEvent::Reopen`), a `devot://` link (behind Settings when Settings is open, which holds links until it closes) and Settings > General > Show Backups bring it back; turning the mode off shows it if it is hidden, and so does a quit the UI calls off (`app_exit_cancel`), since the notice that says why is in the main window. The Dock icon stays.
- **Quick capture** (`quick-capture.html`, `src/renderer/src/quickCapture/`): a small window with a title, a body, a notebook (the notebooks the main window publishes for Settings, `notebookChoices.ts`; the default notebook first, see Editor settings) and Save (Command-Return) and Cancel (Escape, which keeps the text). While a save is on its way the fields are read-only and Cancel and Escape do nothing, so no text is typed after what was sent and no draft outlives a note that was made. Return in the title goes to the body. It starts no core and is granted no note command (`capabilities/quick-capture.json`): it hands the note to Rust (`quick_capture_save`, title, body and notebook checked against `note_put`'s limits), which emits it to the main window (`devot://quick-capture`) with a request ID and waits up to 15 s for the answer (`quick_capture_done`, main window only, a code or nothing). The main window claims the request (`quick_capture_claim`) before its core writes anything: one Rust gave up on cannot be claimed, so a timed-out capture is never made (`E_QUICK_CAPTURE_TIMEOUT`, try again), while a claimed one that times out may still appear (`E_QUICK_CAPTURE_LATE`, the window says to look for it before saving again). The main window's core makes the note (`captureNote`, `src/core/capture.ts`: refuses an empty capture and a notebook that is gone, then saves before it answers; a save that fails after the note is made leaves it pending in the core like any unsaved edit, so the capture is never sent twice), records `note.created` from `quick_capture` and refreshes its lists. On success the window empties and closes (`quick_capture_close`); on failure it keeps the text and shows the code. What is typed is kept as a draft in the webview's local storage on every change (`devot.quickCapture.draft`, cleared once the note is saved), so closing the window or quitting first loses nothing.

## AI

- **MCP first.** `devot-mcp` (`src/mcp`) is a standalone CLI that Claude Code and Claude Desktop launch over stdio (`@modelcontextprotocol/sdk`). It runs the core library with the better-sqlite3 adapter (`src/mcp/sqlite.ts`, which the tests use too) and works when Devot is closed. `pnpm mcp:build` bundles it with Vite into one Node ES module, `dist-mcp/devot-mcp.mjs` (everything but the native better-sqlite3, which loads from `node_modules`); it is not part of the app bundle. Tools: `list_notebooks` (in the sidebar's order), `search_notes` (full text, the app's query rules, a snippet per hit), `read_note` (Markdown snapshot and metadata), `list_tags` (the tags on visible notes, with counts), `create_note` (title, Markdown, a notebook by ID or exact name), `update_note`, `trash_note` and `create_notebook` (see Writes). stdout carries MCP messages only; logs go to stderr as codes and IDs (`I_MCP_NOTE_CREATED|UPDATED|TRASHED <id>`, `I_MCP_NOTEBOOK_CREATED <id>`). `pnpm mcp:build` also writes the npm package's manifest, README and license beside the bundle (`src/mcp/npmPackage.ts`), so `dist-mcp/` is the `devot-mcp` package as it would be published; it is not published yet, and clients run the checkout's bundle with Node.
- **Database:** the release app's file by default (`~/Library/Application Support/io.github.jma49.devot/devot.sqlite`; a debug build's is in `io.github.jma49.devot.dev`, see App data folder), or `--db`, opened on the first tool call with the app's pragmas (WAL, 5 s busy timeout). devot-mcp never creates the file and never migrates: a schema older or newer than its own is refused with a code (`E_STORAGE_SCHEMA_TOO_OLD` asks to open Devot first), and the version is checked again before every call, so an app upgrade while it runs is noticed.
- **Picking up changes:** Rust polls `PRAGMA data_version` on the app's own connection every second (`src-tauri/src/watch.rs`); it changes only when another connection commits, so the app's own saves are ignored. A change emits `devot://db-changed`. The window first has the note service take in what was written (`mergeStored` in `src/core/notes.ts`): every note it holds in memory reads its stored copy back, its Yjs document takes the stored state in and each metadata field keeps the newer HLC, so the next save keeps the other's changes instead of writing its own copy over them, and a note whose stored copy lost edits of its own is saved again; a note deleted for good is dropped. The others stay in memory: letting one go there could lose an edit that had just loaded it (a pin from a batch change, say), so each outside change reads back every note held. The open editor takes in the merged state (nobody's undo step) and the title field a rename. Then the window saves pending edits and reloads its lists. The window hears of a change within a second; a note saved in that second does not go over the change either: storage refuses the write, since the note's body version moved on, and the note takes the stored copy in and is written again (see Body versions in Data model), so the editor's replica gets what the other wrote when the window then hears of it, and the title field a rename the note took in that way (`mergeStored` reports it as one it took in itself).
- **Access control:** each notebook has an "Allow AI access" switch (`books.ai_access`, schema v8; a synced field merged by HLC like the others), off by default and set from the notebook context menu. MCP, the local HTTP API and every other AI feature only see notebooks with the switch on (`src/core/ai.ts`). The switch is not inherited: a sub-notebook needs its own. AI sees only live notes filed directly in such a notebook; notes in the Trash, in no notebook or in a deleted notebook never show, and reading any other ID fails exactly like an unknown one (`E_NOTE_NOT_FOUND`).
- **Creating notes:** `create_note` goes through the note service with its own HLC node ID (`mcp…`, random per process): the body is applied to the new note's Yjs document as operations, never written as a snapshot, and the note and its body are written in one transaction, so the app never sees a half-made note. It never compacts history (`compact: false` on its note service): a sweep would run inside that transaction, holding the write lock from the app, bucket days in its own process's time zone and thin notes AI may not see. The app compacts.
- **Writes:** MCP writes directly; nothing waits for acceptance. Every write goes through the core (`src/core/ai.ts`) in one storage transaction, so the app never sees half of it, and needs the note (and any notebook it names) to be visible as above: a hidden note answers `E_NOTE_NOT_FOUND`, a hidden notebook `E_BOOK_NOT_FOUND`.
  - `update_note` changes the title, the body, the notebook (only to one that allows AI access), the tags and the status, any of them at once. The body is the whole new Markdown or a list of exact passages to replace in turn (each must occur exactly once in the body as the ones before left it: `E_AI_PATCH_NOT_FOUND`, `E_AI_PATCH_AMBIGUOUS`). It goes in as the text difference applied as Yjs operations, never as a snapshot, so it merges with the app's copy of the note like any outside write (see the Body versions item and Undo: the open editor takes it without moving the caret or the selection and without entering the undo history). Before the change, the body as stored is kept as a version unless the history already ends with it (`keepBaseline`), so each edit leaves the text it replaced in Revision History; title, notebook and status changes are recorded as events as usual. Tags are the note's whole list by name: a name no tag has yet becomes a tag, tags left out are taken off. Tag names are unique, so a name an existing tag has (in any case) puts that tag on the note, wherever else it is used. A whole body AI sends, or all patches of a call together, may be at most 1 MB (`MAX_AI_BODY_BYTES`); a patched note may be as large as any note.
  - `trash_note` moves a note to the Trash (never purges), keeping its history; the owner restores or empties it.
  - `create_notebook` makes a notebook at the top level or inside an allowed one, with Allow AI Access on, so AI can use what it made; a name an allowed notebook already has is refused (`E_BOOK_NAME_TAKEN`), since tools name notebooks by exact name.
  - `list_tags` lists only tags on visible notes, so a tag used only in hidden notebooks is never revealed.
  - Edits from the app's own AI features are proposals the user accepts first (see Edit with AI); only MCP writes directly.
- **Authorship** (#372, ADR 0007; see Data model): devot-mcp, the local HTTP API and an accepted Edit with AI proposal record each write with its writer: devot-mcp as the client named itself in `initialize`, one session per connection (`clientWriter` in `src/mcp/server.ts`), the HTTP API as `http`, one session per start of the main window's core, and each Edit with AI sheet as `aiEdit`. Logs carry codes, note IDs, write IDs and kinds (`I_AUTHORSHIP_WRITE`, `I_AUTHORSHIP_UNDONE`, `I_AUTHORSHIP_CLEARED`, `W_AUTHORSHIP_RECORD_INVALID`), never a client name or text; the app's go to the local log from the core worker (as info lines) and the page, and `log_write` takes write IDs, kinds and counts only under these codes. The UI always names a writer with its kind ("Claude Code (MCP)", "HTTP API", "Edit with AI"; `authorshipLabels.ts`).
  - **Gutter** (View > Show Authorship, the `authorship` setting, on by default; a check item in Rust's menu): the editor marks the lines agents wrote, one mark per run of lines with the same writes, read from the replica's own document (`editor/authorship.ts`). The text is attributed once per change to the document and only the marks in the viewport are drawn. The marks are buttons in a group of their own beside the text, outside CodeMirror's gutters (hidden from assistive technology): each is named "Written by <writers>, <time>", shows that on hover or focus, selects the agents' text on its lines when chosen, and the arrow keys move between them. They show in Edit and Split; the history bar's overlay covers them with the panes.
  - **Review notice** (`AuthorshipNotice.tsx`): above the panes, so the history bar's overlay never covers it (inert while a version shows), when the open note has unseen writes: how many and by whom, Review Changes, one Undo All per writer and Dismiss. Review Changes steps through the unseen writes' places in document order (`reviewSteps`: an inserted run, a deletion point, or both), selects and scrolls to each, with Previous, Next (also the arrow keys) and Done; Keep and a per-step Undo (ADR 0007) are not built yet. Undo All runs `NoteService.undoAgentWrites` as an owner edit over every write of that writer on the note, seen ones too, so its button gives the count when that is more than the notice names; the editor takes it as one undo step, and a notice says when deleted text was too old to put back. Undo All is off once the trial is over without a license; Review Changes and Dismiss are not. When Done, Dismiss or Undo All takes away the control with the keyboard, the editor gets it. Note windows show the gutter but no notice, and do not mark writes seen.
  - **List and sidebar** (`agentWrites.ts`): a row or board card of a note with an unseen write shows a mark and "changed by <writer>" (the newest). The sidebar's Agents section lists the MCP clients and the HTTP API of this device's rows, newest first, each with its unseen count; choosing one filters the list to the notes it changed (a filter like Status and Tags, not kept across launches; search in that view keeps to them).
  - **Clear Authorship** (the note context menu and the More menu, for a note with records, after a confirmation): `NoteService.clearAuthorship` in one transaction, which the open editor takes in; a write another device made that the clear had not seen counts as cleared until its session writes again (see ADR 0007).
- **Setup helper:** Settings > Integrations shows copy-ready configs for Claude Code (`claude mcp add --scope user devot -- node <checkout>/dist-mcp/devot-mcp.mjs`), Codex (`~/.codex/config.toml`) and a generic `mcpServers` JSON. Rust's `settings_mcp_setup` (no arguments) says where the bundle is in the checkout the app was built from, when it exists there, and the database a debug build uses (passed with `--db`); otherwise the pane shows a path to replace.
- **Models:** embeddings run locally (vectors stored with `sqlite-vec`), so semantic search works offline and keeps content local; the runtime (in the UI worker or in Rust) is chosen in phase 2. Generation goes through a provider interface (below). Nothing is sent to a cloud model unless the user triggers it, and only text from notebooks that allow AI access.
- **Providers:** `src-tauri/src/ai` defines the `Provider` interface: a provider turns one provider-agnostic request (an optional system prompt, messages that start with the user, a token cap) into its own HTTP request, and its response into text, a stop reason (`end`, `maxTokens`, `other`) and token counts. Two implementations ship. `anthropic` (the default) is the Anthropic Messages API (`POST {endpoint}/v1/messages`, `x-api-key`; default endpoint `https://api.anthropic.com`, default model `claude-sonnet-5-5`). `openai` is OpenAI-compatible chat completions (`POST {endpoint}/chat/completions`, bearer key, `max_completion_tokens`; default endpoint `https://api.openai.com/v1`, no default model: the user names one). Both are non-streaming: Edit with AI waits for the whole reply. A refusal, a missing text or a shape the provider does not keep answers with a code.
  - **Where things live:** Rust holds everything that must not reach the web view. The endpoint and model of each provider, the active provider and whether suggestions are also asked for on a pause (`suggestOnIdle`) are in `<app data>/ai-settings.json` (`settings.rs`): on this device only, never synced, never in backups. The key is a macOS keychain item per provider (`keychain.rs`: the app identifier as service, `ai-key-<provider>` as account; a build without a keychain refuses with `E_AI_KEYCHAIN_UNAVAILABLE` and keeps no key elsewhere). The page can set or remove a key (`ai_key_set`, `ai_key_clear`) but never read it: `ai_settings_get` says only `set`, `unset`, `unknown` (the keychain could not be read, so Save Key and Remove Key stay usable) or `unavailable` (no keychain in this build). Whether a key exists is checked without reading it, so Settings never loads a secret or triggers an access prompt; only a request reads it. Requests ignore proxy environment variables, so a key goes only to the endpoint the user set. A key is checked as a header value (visible ASCII, no spaces, at most 512 characters).
  - **Endpoints:** https, or http to this Mac only (a model server on `localhost`, `127.0.0.1` or `::1`), with no credentials, query or fragment, so a key never travels over plain http to another machine. Only the Settings window can change an endpoint, so the web view cannot send a key anywhere else. The request goes out from Rust (`transport.rs`, the system TLS stack, 180 s, responses capped at 8 MiB), redirects are never followed (a key goes only to the endpoint set), and the endpoint is not restricted to public hosts, since the user chose it. The CSP is unchanged: the web view makes no request to a provider.
  - **Commands:** `ai_generate` (main window), `ai_settings_get` (main and Settings windows: the main window reads it for Suggest Next Edit), `ai_settings_set`, `ai_key_set` and `ai_key_clear` (Settings window). `ai_generate` names no endpoint, key or model: Rust reads them. It validates the request (1 to 100 messages starting with the user, none empty, at most 2 MiB of text in all, 1 to 32,000 output tokens) before it reads the key, so a bad request sends nothing; with no key it answers `E_AI_KEY_MISSING` and sends nothing. Before all of that, a build that gates AI answers `E_LICENCE_REQUIRED` without a valid license (see Licences).
  - **Errors and logs** are codes: `E_AI_AUTH_FAILED` (401, 403), `E_AI_RATE_LIMITED` (429), `E_AI_REQUEST_REJECTED` (400, 413, 422), `E_AI_NOT_FOUND` (404), `E_AI_PROVIDER_UNAVAILABLE` (5xx), `E_AI_HTTP` (other statuses, redirects included), `E_AI_NETWORK_FAILED`, `E_AI_TIMEOUT`, `E_AI_RESPONSE_INVALID`, `E_AI_RESPONSE_TOO_LARGE`, `E_AI_REFUSED`, `E_AI_MODEL_MISSING`. The log line holds the provider and the status, never a prompt, an answer, a header or a key; an error never quotes the response body, which can echo the prompt.
  - **The access rule** is in the core (`src/core/aiProvider.ts`, `createAiGenerator`), so every AI feature has the same one in front of it, whichever provider is active. A request needs a trigger `{ by: 'user', books }`: anything else (a timer, a sync, a note's own content) is refused with `E_AI_NOT_TRIGGERED`, and every notebook the text comes from must have Allow AI Access on (Templates and sub-notebooks of an allowed notebook do not count), or the request is refused with `E_AI_ACCESS_DENIED` before it reaches Rust. The renderer's transport is `src/renderer/src/ai.ts`.
  - **Settings > AI** (the AI pane): the active provider, the Suggest When I Pause switch (see Next edit suggestions), and for each provider its endpoint, model and key (a password field that is cleared once the key is saved, with Save Key and Remove Key). Endpoint and model are stored when the field is left or on Return; Rust refuses a bad value with its code and the field shows the stored value again.
  - **Tests:** `src-tauri/src/ai/tests.rs` runs one contract per implementation against a mock HTTP provider on a loopback port (the request each provider sends, its answer and stop reason, every failure status, a response of the wrong shape, a refusal, redirects, no key, a bad request, timeouts, the response cap, and that the key is never in a body, a path, a settings file or an error); `tests/core/ai-provider.test.ts` covers the access rule on real SQLite; `tests/ui/ai-settings.spec.ts` the pane. The keychain itself is checked by an ignored test run by hand (`cargo test -- --ignored keychain`), since it writes to the login keychain.
- **Edit with AI** (#158, first half; `src/core/aiEdit.ts`, `src/renderer/src/AiEditSheet.tsx`, `editor/aiMenu.ts`): with text selected, the selection toolbar's AI button (SF Symbol `sparkles`, its own group at the end) and the editor menu's Edit with AI submenu offer the presets Improve Writing, Proofread, Reformat, Summarise, Make Bullet List, Make Task List, Make Table, Add Headings and Create Mermaid Diagram, then Custom Instruction… (a field in the sheet; nothing is sent until Send or Return).
  - **What is sent:** picking a preset is the request; the sheet opens and asks at once. One request through `createAiGenerator`, so the access rule above applies: the trigger is the user's, and its notebook is the open note's as the core holds it now (`read`), which must have Allow AI Access on; a note in no notebook or in Templates is refused (`E_AI_ACCESS_DENIED`) before anything reaches Rust. Only the selected text goes, between `<selection>` tags after the preset's instruction (or the user's), with a system prompt that asks for the Markdown alone and says the selection is content, never instructions. A selection is at most 20,000 characters (`MAX_AI_EDIT_CHARS`, `E_AI_SELECTION_TOO_LARGE`), an instruction 2,000, the reply 8,192 tokens; a reply cut off at that cap is refused (`E_AI_REPLY_CUT_OFF`) rather than shown half.
  - **The reply** (`cleanAiReply`): a fence around the whole reply comes off (unless the selection was a fenced block), line feeds only, and the selection's own blank lines at either end are kept. Summarise and Create Mermaid Diagram add their result after the selection (a blank line between; a diagram is always one ` ```mermaid ` block); the other presets and a custom instruction replace it.
  - **Review:** the sheet shows the proposal as a line diff of the selection (`proposalParts`: runs of shared lines and changes; unchanged runs folded to two lines around each change). With more than one change, each has an "Apply this change" check box; Accept (Accept Selected when some are unchecked) takes the checked ones (`proposalText`), Discard drops the proposal, Try Again asks again. Escape, Cancel and Discard leave the note as it was; an answer that comes after Cancel is dropped. Proposals are not kept: closing the sheet forgets it.
  - **Applying:** `NoteService.applyAiEdit` finds the selection at its start, or wherever edits since moved it when it is there exactly once (else `E_AI_PROPOSAL_STALE`), takes a version of unversioned typing, applies the difference as Yjs operations (`textEdits`, as `setBody`), then takes a version marked `ai` (see Revision history). The core returns the update, which the editor applies as one undo step, as a restore is: Cmd+Z takes back the whole edit.
  - **Unavailable:** the sheet says why, with the code: no Allow AI Access on the note's notebook (and how to turn it on), no key or no model (Settings > AI), a refused key, a rate limit, no connection, a reply cut off, a selection too long or changed meanwhile. Try Again shows only where asking again may help.
  - **Tests:** `src/core/aiEdit.test.ts` (prompts, replies, diffs), `tests/core/ai-edit.test.ts` (applying on real SQLite: one update, the versions, merging with typing, a moved or changed selection, compaction), `tests/ui/ai-edit.spec.ts` (the toolbar and the editor menu, review per change, undo, history, nothing sent without access, failures, with `ai_generate` faked).
- **Next edit suggestions** (#158, second half; `src/core/aiSuggest.ts`, `src/renderer/src/editor/ghostText.ts`): a continuation of the note at the caret, shown as ghost text after it. Tab accepts it, Escape or any typing, caret move or change of the note drops it.
  - **Triggers:** the command Suggest Next Edit (`ai.suggest`, Option+\ by default, also in the palette; the user can rebind it) and, only if the user turned on Settings > AI > Suggest When I Pause (`suggestOnIdle` in `ai-settings.json`, off by default, device only), a pause of 1.5 s in typing with the caret at the end of a line. Nothing else asks: not opening a note, not a timer with the setting off, not sync. The pause timer starts only after typing the user did (`input.type`), is dropped by the next change, and the setting is read afresh from Rust at the moment of the request, so turning it off stops the next one.
  - **When it is off:** `createSuggester` sends nothing unless the note's notebook (as the core holds it now) is one `createAiGenerator` accepts (Allow AI Access on; a note in no notebook or in Templates never), and the active provider has a key stored and a model (`providerReady`; a key state of `unknown` or `unavailable` counts as missing). The key trigger then fails with the code (`E_AI_ACCESS_DENIED`, `E_AI_KEY_MISSING`, `E_AI_MODEL_MISSING`) shown in a notice; a pause request fails silently. The Trash has no suggester. The central access rule is untouched: the request is a user trigger (`by: 'user'`) with the note's notebook, and the idle setting is checked before it in the suggester.
  - **What is sent:** at most 2,000 characters before the caret and 500 after it (`SUGGEST_BEFORE_CHARS`, `SUGGEST_AFTER_CHARS`; never splitting a surrogate pair), between `<before>` and `<after>` tags, with a system prompt that asks for the text to insert only and says the note is content, never instructions. Nothing else from the note goes out; Settings > AI states the sizes. The reply is capped at 256 tokens and 1,500 characters; a reply cut off at the cap loses its unfinished last word. Rust gives up after 20 s (`timeoutSecs` on the request, never longer than its own limit).
  - **Never in the note until accepted:** the suggestion is a decoration (a CodeMirror state field), not part of the document, so it is not in the Yjs text, the saved body, the preview or sync. Accepting dispatches one transaction (`input.complete`, history isolated before and after), so Cmd+Z takes back exactly the accepted text.
  - **One request at a time, cancelled by typing:** a change or caret move, Escape, leaving the note (the editor's plugin is destroyed) or a newer request makes the answer of a request on its way stale, and it is dropped when it arrives. Rust cannot abort an HTTP call, so the call itself runs to its end (or its 20 s limit) and the suggester sends the next one only after it: a request never leaves while an earlier one is still on its way, and one cancelled while it waited is never sent.
  - **Tests:** `src/core/aiSuggest.test.ts` (context, prompt, reply, ordering and cancelling), `tests/core/ai-suggest.test.ts` (on real SQLite: nothing is sent with the pause setting off, for a notebook without AI access, for a note in no notebook or in Templates, or without a provider; only the text near the caret goes), `src/renderer/src/editor/ghostText.test.ts` (the field and accepting as one undo step), `tests/ui/ai-suggest.spec.ts` (the key, Tab, Escape, typing, the pause setting, a late answer after typing or switching notes, every refusal, with `ai_generate` faked), the Rust settings and time limit tests, and `tests/ui/ai-settings.spec.ts` for the switch.
  - **Not done:** note windows (a note opened in its own window) have no suggester yet; the suggestion is one text, not several to cycle through.

## Extensions

- An internal, versioned extension API. Built-in preview renderers (and their islands) register through it (`PREVIEW_API_VERSION`; see the preview section's Extension point); commands and keymaps have their own registry (`src/renderer/src/commands/`). Built-in features written against it so far: math, Mermaid, emoji, alerts, embeds and the other preview renderers. Import, export and themes are built-in code.
- **Third-party plugins** (ADR 0005, `PLUGIN_API_VERSION` 1) contribute commands, menu items, keymaps, preview renderers and import and export formats, each with a permission the user approves on install. No permission reaches the network, other notes, storage or Tauri.
  - **Package:** a folder with `devot-plugin.json` (ID, name, version, API version, main script, permissions, contributions), or a `.zip` of one, at most 256 files and 20 MiB. Rust reads it whole and checks it (`src-tauri/src/plugins/`), the page checks the manifest again (`src/core/plugins/manifest.ts`); both run `tests/fixtures/plugins/manifests.json`.
  - **Install:** Settings > Plugins > Install from Folder or Install from Archive picks a package in a native panel; the sheet lists what it asks for, and Install approves it all (Cancel, which has the keyboard, installs nothing). Rust writes it to a new folder and renames it into `<app data>/plugins/<id>/`, replacing an older version whole, and records it as on with those permissions in `plugins.json` (granted permissions the manifest on disk no longer asks for do not count). The pane turns plugins on and off, lists their permissions and removes them. Nothing is downloaded; plugins never sync and backups leave them out.
  - **Sandbox:** only the main window runs plugins. Each enabled plugin gets a hidden `<iframe sandbox="allow-scripts">` on `devot-plugin://localhost/<id>/`, which Rust serves for enabled plugins only: Devot's container page (`src-tauri/plugin-frame/`), which frames the plugin's page in another sandboxed frame and lets that one page load, so the plugin can never navigate. The plugin's page runs Devot's runtime, then the plugin's script, under `default-src 'none'` with scripts, styles, images, fonts and media from its own folder and every connection, frame, worker and form refused; WebRTC is off in every main window's web view (WebKit's `PeerConnectionEnabled` preference), as are resource hints (preconnect, preload, prefetch and DNS-prefetch), which would otherwise reach the network outside the policy; the runtime removes WebRTC too and refuses child frames and hint links (also through the `document.body` and table `caption`/`tHead`/`tFoot` setters), through DOM methods it keeps before the plugin's script runs. A preconnect connects synchronously on insertion, so the native preference is the guarantee and the runtime guard is defence in depth. Both frames have opaque origins, so a plugin shares no storage, cookies or DOM with the app or another plugin, and Tauri's IPC and invoke key are in the main frame only. The main window's policy only gains `devot-plugin:` in `frame-src`.
  - **Protocol** (`src/core/plugins/protocol.ts`, version 1): the main window hands each frame a `MessagePort` and binds it to that plugin (`src/renderer/src/plugins/host.ts`). Plugins call `note.read`, `note.replace` (the text read and the new text; refused when the note changed since), `ui.show` and `ui.hide`; the host calls `command.run`, `preview.render`, `import.convert` and `export.convert`. Every call is checked for its shape, a known method, its permission and, for the note and panel calls, that one of the plugin's commands is running or its panel is open; refusals and failures are answered and logged as codes with the plugin's ID. At most 64 calls wait per plugin; a plugin answers within 5 s (a drawing), 30 s (a conversion) or 60 s (a command).
  - **Edits** go through the core as Yjs diffs (`NoteService.applyPluginEdit`, `textEdits`), with the text before kept as a version, and the editor applies the update as one undo step.
  - **Contributions:** commands in the palette under the plugin's name; a keymap's key works in the whole window when it is a valid shortcut with Command or Control that no app command, reserved key or earlier plugin (by ID) uses, and is dropped and logged otherwise; menu items in the Plugins menu, which Rust builds from the manifests (with Plugin Settings… last) and whose picks reach the window as `devot://plugin-action`; preview renderers draw fenced blocks of their language as Markdown the preview renders and sanitizes like note text, without plugin renderers (a block without an answer stays code; exported and printed pages show it as code); import formats (File > Import and the palette) turn the files Rust reads from a native panel (UTF-8, 5 MiB each, 20 at a time) into notes in the notebook shown; export formats (File > Export and the palette) turn the open note into text Rust writes whole where the save panel says.
  - **UI:** a plugin shows its frame only from one of its commands (`ui.show`), in a sheet titled with its name, with Close; the frames stay in that sheet while it is closed, so showing one never reloads it. Closing tells the plugin (`ui.hidden`).
  - **Tests:** `tests/ui/plugins-sandbox.spec.ts` (a hostile plugin cannot reach Tauri, the main window, another plugin, the network or a note without permission), `tests/ui/plugins.spec.ts` (each contribution point), `tests/ui/plugin-settings.spec.ts`, `tests/ui-csp/csp.spec.ts` (a plugin under the production policy), `src/renderer/src/plugins/host.test.ts`, `src/core/plugins/protocol.test.ts`, `tests/core/plugin-*.test.ts`, and Rust's `plugins` tests (packages, install, serving, menus). The UI tests serve the same pages from `src-tauri/plugin-frame/` (`tests/ui/plugins.ts`).

## Localisation

- English is the source locale and the only one shipped now.
- No UI text is written inline: every string comes from a typed message catalog by key, so adding a locale means adding a catalog, with English as the fallback for missing keys. The locale follows the macOS preferred languages.
- Placeholders (`{title}`) are filled with `format` in one pass, never with `String.replace`, whose replacement patterns (`$$`, `$&`, `$'`) would garble a title holding them; a policy test refuses `.replace('{`. A sentence is never built from pieces in code: each variant (with or without a count, a key or a scope) is its own catalog entry.
- Dates, numbers and lists use `Intl`. When a second locale arrives, the catalogs move to ICU message syntax for plurals and placeholders, and native menu labels in Rust get the same catalog.
- Code contains no CJK characters at all; test data that needs them uses `\u` escapes. A test enforces this over every tracked file.

## Design system

- Direction: native macOS structure with cool neutrals, a blue accent and distinct Markdown colours in the editor. Details in `design/README.md`.
- Assets live in `design/`, to the standard of an open-source asset library:
  - Design tokens in W3C Design Tokens (DTCG) JSON: `design/tokens/`. A build step generates CSS custom properties and TypeScript constants.
  - Icons are SF Symbols rendered at runtime; `design/icons/symbols.json` maps Devot icon names to symbol names. No symbol artwork is stored in the repository (license finding: `docs/adr/0001-sf-symbols-rendered-at-runtime.md`).
  - Fonts are the system's (SF Pro, SF Mono) and are not bundled. Any bundled font must have an open license (such as OFL).
- Every asset comes from a source that can be open-sourced. Devot's app icon and logo must be original artwork: the dove in `design/app-icon/` (`dove.svg` the mark, `source.svg` the flat app icon, `AppIcon.icon` the layered one; `design/README.md`, App icon). `pnpm app-icon` makes `src-tauri/icons/` from them.
- The bundle lists the layered icon, which Tauri compiles with `actool` into `Assets.car` (named by `CFBundleIconName`; what macOS 26 shows), and keeps `icon.icns` as `CFBundleIconFile`, the fallback. Without `actool` from Xcode 26 or later (the Command Line Tools alone have none) the bundler only logs and leaves `Assets.car` out, so the release workflow checks that the bundle has it. Under the Node CLI the bundler starts `actool` with stdin closed, and `actool` then crashes (tauri-apps/tauri#15315): `pnpm tauri` (and so `pnpm build` and the release workflow) puts `scripts/shims/` first on PATH, whose `actool` runs the real one with an empty stdin. Remove the shim once the bundler does that itself (tauri-apps/tauri#15991). A crashed `actool` can leave an `ibtoold` behind that fails the next runs too; `killall ibtoold` clears it.

### Native look

- The window is transparent with the `underWindowBackground` window effect behind all of it, always active (also while the window is inactive); the page's root is transparent and each region paints a wash over the material: the sidebar `color.surface.sidebar`, the list `color.surface.list-wash`, the editor pane `color.surface.editor-wash` (CodeMirror's own background is transparent). The toolbar has no wash of its own; pop-ups and menus stay opaque (`color.surface.popover`).
- **Interface style** (Settings > Appearance > Interface style: Glass, the default, or Classic, an opaque window; stored as `sidebarMaterial`, true for Glass): with Classic, the main window drops its effect, the page's root behind every pane paints `color.surface.window` and the regions their opaque surfaces (`color.surface.sidebar-opaque`, `color.surface.list`, `color.surface.editor`), so nothing in the window is see-through. With Glass, Settings > Appearance > Glass Transparency (`windowTransparency`, a whole number from -100 to 100, default 0: the design washes) reaches the page as `--window-transparency`; app.css works each wash's alpha out from it (`color(from ...)`, 1 - (1 - a) x (1 + level / 100), clamped: -100 opaque, 100 twice as clear), so the tokens keep the design alphas. The slider is shown only for Glass, with its value beside it (0 is the design washes). The slider stores its value at most every 100 ms while it is dragged, and the last value when it stops (`settings/draggedNumber.ts`). The choice is stored with the editor settings (`sidebarMaterial` in `editor-settings.json`, same validation, same `devot://editor-settings-changed` event), so it follows a change in every window at once; the main window's root element carries `data-sidebar-material="on|off"` (`src/renderer/src/sidebarMaterial.ts`). Rust builds the main window with the configured effect only when the material is on, and hands the page the settings it was built with in an initialization script (`window.devotInitialEditorSettings`, which the CSP does not govern), so the first paint matches the window (the editor's font too). That script carries the settings read at launch into every load, so the page also keeps the newest snapshot it has confirmed in `sessionStorage` and, after a reload (a backup restore reloads it), starts from that one when it is newer. After a change the page calls `sidebar_material_sync` (main window only, no arguments), which removes or restores the effect to match the stored setting through Tauri's `set_effects` (AppKit work on the main thread) and answers once the main thread has applied it (`src-tauri/src/sidebar_material.rs`). The order keeps the desktop from showing through a bare wash: turning it off paints opaque first and asks Rust once that has been painted; turning it on asks Rust first and turns translucent only after Rust answers that the window shows the material (on a failed answer, or when Rust has stored a later change to off already, the regions stay opaque). Rust applies stored revisions in order and leaves the effect alone when another setting changed. The window itself stays transparent (that is fixed when it is built): an opaque window removes the material view, which is what costs GPU time, and paints every pixel.
- Overlay title bar: traffic lights in the sidebar's top bar, a unified toolbar over the list and editor.
- macOS type scale: body 13 pt, captions 11 pt, sidebar rows 28 px.
- The menu bar and context menus are native (Tauri menus). Settings live in the app menu.
- Context menus are tables of entries (`src/renderer/src/contextMenu.ts`): each entry has an action, a catalog label (fixed or chosen per target), an optional accelerator, and optionally a `shown` or `checked` rule. Each menu is built once per window with every item it can show; before it pops up, the same native menu shows, hides, relabels and checks its items for the right-clicked target, and a picked item acts on that target, never on the open note (the note menu's target is every selected note when the right-clicked row is one of them; see Multiple selection).
- The note context menu (`src/renderer/src/noteMenu.ts`): its shortcuts work only while the note list has focus and act on the row that has the keyboard (a right-click focuses its row, a filter can hide the open note): on every selected note while several are selected (see Multiple selection), otherwise on that row's note alone. When the row that has the keyboard leaves the list while the view stays the same (Move to Trash from the keys, the menu or the palette, Delete Permanently or Restore in the Trash, a move out of the notebook, a change the filter hides), the open note's row takes the keyboard if it is still listed; otherwise the next row (the previous one at the end) takes it and opens (unless another note, hidden by the filter, is open), and an empty list keeps it itself (arrow keys and `/` work there), so the list's keys go on working. A row whose focus went elsewhere first (a click on a toolbar button or on blank space) hands nothing on, and switching views opens no note. Copy items write through the `clipboard_write_text` command, because WebKit lets a page write the clipboard only during a gesture in the page, and a native menu click is not one.
- The note context menu also opens Revision History… (Option+Cmd+Y, also in the View menu).
- **Multiple selection** (`src/renderer/src/listSelection.ts`, `SelectionSummary.tsx`, `src/core/batch.ts`): in any note list (the library, search results, Templates, the Trash) Cmd-click adds a note to the selection or takes it out (the clicked note becomes the anchor), Shift-click selects the notes from the anchor to the clicked one, Shift+Up and Shift+Down move the far end of that range, Cmd+A selects every note listed (the registry's `list.*` commands; in the editor Cmd+A stays Select All for the text) and Escape goes back to the open note alone. The listbox is `aria-multiselectable` and each selected row `aria-selected`. The open note stays open while it is selected (when it leaves the selection, the anchor opens); a plain click, an arrow key, opening a note from anywhere, Next, Previous, Back, Forward or Return on a row show one note again, from the open note, and another view starts without a selection. With two or more selected, the editor pane shows a summary instead of the editor: how many, their titles (eight, then a count), and buttons for every batch action: Move to Notebook… (the Move dialog), Pin or Unpin (Unpin when all are pinned), the status pop-up (Mixed while they differ), the tags any of them has (removing a chip takes it off all; Add Tag puts it on all), Copy Note Links and Move to Trash. In Templates the summary has no status or tags (a template's own are not used); in the Trash it offers Restore and Delete Permanently (which asks first, with the count). The same actions come from the list keys (M, P, Cmd+C, Cmd+Delete), the status keys, the palette (the note commands relabelled for the selection, plus Add Tag to Selected Notes… and Remove Tag from Selected Notes…, which open a tag picker) and the note context menu: on a selected row it acts on the whole selection, with plural labels, a Status submenu (checked when all share one) and the tag items, and without the items for one note (Revision History, Duplicate, Copy Note URI and ID, and the export and print items); on any other row it acts on that note only and leaves the selection alone. Copy Note Links writes one link per line through `clipboard_write_text`, which takes as much text as a note may hold (`src/renderer/src/clipboard.ts`: longer text goes through the page's clipboard API, which only a click or a key in the page allows); a copy that fails (links, a URI or an ID) shows a notice with its code.
- **Batch changes** (`applyBatch` in `src/core/batch.ts`): one change (notebook, status, pin, add or remove a tag, trash, restore, purge) is applied note by note through the note and tag services, each note written before the next, so every note gets its own HLC and its own history event, never one SQL update for all. Every note named gets the write, even one that seems to have the value already (the lists may not have caught up with a change just made). A note that fails (deleted meanwhile, its write refused) does not stop the rest; the window logs `W_BATCH_FAILED` with the count and the first code, and a notice in the notice stack, with the other notices (not above the editor), says how many notes could not be changed.
- **Dragging notes:** a row drags the whole selection when it is selected, else itself (the payload is the note IDs, one per line). Dropped on a notebook they move there, on a tag they get it, on a status they get it, on the Trash they move to the Trash; the row under them shows as a drop target. Templates drop only on notebooks and the Trash; the Trash's rows do not drag.
- The tag context menu (`src/renderer/src/tagMenu.ts`): Tag Settings… (name and colour), Colour (a submenu of check items: None and the palette), Filter by Tag (a check item; toggles the filter), Copy Tag ID (through `clipboard_write_text`) and Delete Tag (Delete or Backspace on the focused row; it asks first, since the tag leaves every note; hidden in a workspace). Renaming in place is F2 on the row, and the keyboard goes back to the row afterwards. A coloured tag shows a dot in place of its sidebar icon and on its chips; the dot is named after its colour for assistive tech. A context menu entry may hold a submenu, whose items are relabelled and checked per target like the rest.
- The image context menu (`src/renderer/src/imageMenu.ts`), for an image in the preview or under its line in the editor: Copy Image and Save Image As… (attachments only) and a Size submenu of check items (Auto, Small, Half Width, Full Width; shown when the size can be set). Copy Image calls `image_copy`, which reads the attachment by ID and puts it on the general pasteboard as PNG and TIFF data (decoded off the main thread by `native::macos::pasteboard_image`, a PNG keeping its own bytes; only the pasteboard write runs on the main thread). The decode runs in an autorelease pool of its own, so AppKit's temporaries (decoded copies of the image) are freed when it returns, not when its blocking-pool thread ends seconds later (`tests/main_thread.rs` checks that the thread's exit frees nothing more). An image whose header gives it more than 100 megapixels (`MAX_COPY_PIXELS`, twice a 48-megapixel photo) is refused with `E_IMAGE_TOO_LARGE` before anything is decoded: its decoded copies would take gigabytes, and a file of a few MB can ask for that. Save Image As… writes the bytes as they are, at any size: it calls `image_save`, which shows the system save panel over the window (the attachment's name with the extension for its type) and writes the bytes beside the chosen path before renaming them over it. The path is written as chosen: the panel asked before replacing a file there, so Rust never adds an extension that could replace another file. The page names attachments by ID only, never a path. The same actions are registry commands (`image.copy`, `image.save`, `image.size*`), which the palette offers while the cursor is on a line with an image.
- Status shortcuts (`src/renderer/src/statusKeys.ts`): Control+Command+1 to 5 set the open note's status (none, active, on hold, completed, dropped) anywhere in the window, also while typing, but not over a sheet. They are the registry's `status.*` commands (`window` scope), so the palette lists them while a note is open and Settings > Keyboard Shortcuts can change them. Unit tests check that they take no key another command, a context menu, the menu bar or macOS already uses.
- Notebook drag and drop (`src/renderer/src/Sidebar.tsx`): dropping a notebook on the top quarter of another puts it before that one, on the bottom quarter after it (after an open notebook's sub-notebooks too; the top quarter of a first sub-notebook puts it first inside), in the middle inside it; a line on the row's edge shows where it will go (after an open notebook: under its last visible sub-notebook, at its indent). A drag that ends anywhere, dropped or cancelled, clears the drop marks. A notebook never drops on itself or among its own sub-notebooks. The Notebooks header puts it first at the top level. A note dropped anywhere on a row goes into that notebook.
- The notebook context menu (`src/renderer/src/bookMenu.ts`): New Notebook Inside, Rename (Return or F2), Move Up and Move Down (Option+Up and Option+Down; when there is a sibling that way; the way to reorder without a drag), Move to Top Level (nested notebooks only), Allow AI Access (a check item) and Delete Notebook (Delete). The right-clicked notebook is outlined while its menu is open and stays unselected. A notebook with AI access on shows a small sparkle before its count while its row is under the pointer, has the keyboard, is selected or has its menu open; at rest the sparkle takes no room, so the name gets it, and its accessible name stays. Every action of a notebook or tag row has a keyboard route: Shift+F10, the menu key or Control+Return (the registry's `sidebar.rowMenu`, scope `sidebar`) opens the focused row's native menu under the row, where the arrow keys and Return pick (Allow AI Access, the exports, New Notebook Inside, the tag Colour submenu and the rest); Rename, Move Up and Move Down and Delete also have keys of their own. The menu key is a named key (`ContextMenu`) of the shortcut notation, so Settings > Keyboard Shortcuts can record it.
- **Sidebar sections and footer** (`Sidebar.tsx`, `sidebarSections.ts`, `SidebarFooter.tsx`): Notebooks, Status, Tags and Agents have one header shape: the title on the left; on the right the section's own actions (search, add) and then its disclosure chevron, shown while the header is under the pointer or has the keyboard inside it. A collapsed section keeps its chevron shown, so its state shows. Each section folds, and each window remembers which are folded in local storage (`devot.sidebarCollapsed.<window label>`); naming a notebook opens a folded Notebooks section. The footer is one button that opens the backup and mirror status: it reads the last save time ("Saved at 11:37:02") once a note was saved in this window, else the panel's name.
- **Row time** (`relativeTime` and `rowDate` in `src/renderer/src/format.ts`): with Note List Dates set to Relative, a list row and a board card say how long ago the note changed, "Just now" under a minute, then "7 min ago", "3 hr ago", "3 days ago" (the locale's short units in the catalog's `time.ago`), and the date after 30 days; the time is secondary text, and its tooltip is the full date and time.
- **Untitled notes in lists** (`headline` in `src/core/extract.ts`, `src/renderer/src/headlines.ts`): a note with no title shows the first line of its body as its row title (and in the multiple selection's list), so a list of new notes can be told apart. The line is the first one with readable text after front matter, as the preview shows it (heading, list, quote and task markers and link syntax out; a line with only an image is skipped), cut to 120 characters. It is a display fallback only: the title stays empty (the title field shows its placeholder, links, exports and the Markdown mirror still name the note Untitled), and it is never written to storage. The list does not read bodies: the rows that render ask the core (`NoteService.headlines`, which reads pending edits too and works for Trash notes) for the notes they show with no title, only the start of each body is read, and the answer is kept until the note's `updatedAt` changes (at most 2000 are kept). A note with no text shows Untitled. Return in the title field moves to the body (not the Return that picks an input method's candidate).
- **Duplicate** (`duplicateNote` in `src/core/duplicate.ts`): the copy has the original's body (as Yjs state), notebook, status and tags, and the title "<title> copy" (the suffix comes from the message catalog; an untitled note's copy stays untitled, and a title is cut to the title limit). It is not pinned: a pin is a place in the list, and two pinned twins would crowd it. A tag that cannot be put on the copy is left off and logged by code; the copy is still made.
- Note list order (`src/core/sort.ts`, `src/renderer/src/noteSort.ts`): a sort button in the list header opens a native pop-up under it with six check items (title A to Z or Z to A; date updated or date created, newest or oldest first) and Use as Default. The order is a view preference kept in the webview's local storage, never in the database, so it does not sync. Each library view keeps its own order: All Notes, each notebook, and each filter (a filter is keyed by itself, whatever notebook narrows it). Views without their own order follow the default (newest updated first until the user picks Use as Default, which makes the current view's order the default and checks the item while a view follows it). Pinned notes keep their own section, sorted the same way. Titles compare with `Intl.Collator` (numbers by value, case and accents ignored) in the macOS preferred languages, then the UI locale, so Chinese titles sort by pinyin for a Chinese-language system; untitled notes come last and equal titles put the newest updated first. Search results stay in relevance order, with Relevance as a seventh item, until the user picks another order (remembered for search results only; Use as Default is not offered there). The Trash keeps its deletion order and has no sort button.
- Focus mode (the toolbar button or Shift+Cmd+D) hides the sidebar and the note list; each window remembers it. Turning it on with the keyboard in a hidden area moves the keyboard to the editor (see Keeping the keyboard on the page).
- **Board layout** (`src/renderer/src/NoteBoard.tsx`, `board.ts`): a List / Board control at the end of the list's filter row (and Show as Board or Show as List in the palette, `view.toggleBoard`) shows All Notes, a notebook (a workspace too), Pinned or a tag as five columns, one per status (No Status, Active, On Hold, Completed, Dropped), each with its count; a status filter is one column already, and search results, Templates and the Trash have no board. The choice is kept per view (the list's view key: filter and notebook) in the window's last state; nothing else is stored. Every column shows, empty ones too, and takes drops; Settings > General > Dropped Column on Boards (`boardDropped`, an editor setting, on by default) turned off leaves the column and its notes off boards. A card shows the title (an untitled note's first line), the date and a dot per tag (the tag names are in the card's accessible name, as hidden text); clicking one opens it, and the cards of a column keep the view's order (pinned first). There is no manual order, so a drop within a column changes nothing. Each column is a listbox; the selection is the list's (`listSelection.ts`, the cards column by column as its order), so Cmd-click, Shift-click, Shift+Up and Down, Cmd+A and Escape work as in the list, and the note keys, the context menu and Return act as there. The arrow keys move up and down a column and sideways to the same place in the nearest column with cards. A card drags the selection when it is selected, else itself, with the list's payload (so the sidebar's notebooks, tags, statuses and Trash take it too); dropped on a column, the notes get its status. Control+Command+Right and Left (`status.next` and `status.previous`, in Settings > Keyboard Shortcuts, the palette, and the note menu on a board) move each selected card, or the focused one, to the next or previous column; a card in the last column stays. Status changes go through the note service as a batch (`applyBatch`), so sync, history and devot-mcp see ordinary status events; a moved card shows in its new column at once. Each move (a drop or a key press) is one step of the board's own undo history (`createMoveHistory`, the last 50 moves of each board view, kept in memory for the last 20 boards shown, so it lasts across a visit to another view): Cmd+Z and Shift+Cmd+Z while a card or column has the keyboard take the last move back or make it again, each note whose status changed since left alone. A move whose write failed keeps only the notes that were written, and a step that changes nothing any more is passed over. A view with no notes shows the list's empty message and tip in place of the columns. A board of more than 200 cards renders, in each column, only the cards near the part that shows, as a long list does (`columnWindow`, with `listWindow.ts`), so headlines are read for those cards only. The board has its own width (`size.board-default-width`, room for the five columns at their narrowest, dragged from `size.board-min-width` to `size.board-max-width`); in a narrow window it gives way before the editor, and its columns keep `size.board-column-min-width` and scroll sideways, a focused card scrolling into view. While a board shows, the editor keeps `size.board-editor-min-width` (380 px, the least at which its toolbar, title and metadata row are not clipped) in place of the usual two panes' width, so at laptop widths the board scrolls rather than the editor being squeezed.
- **Restoring the last state** (`src/renderer/src/lastState.ts`): a window opens where it was left. It restores the library view (All Notes, a notebook or Templates) with its filter, the library views shown as a board (see Board layout; at most the 100 switched last), the view mode (edit, split or preview), the open note, the note's selection, and its scroll position: in edit and split mode the editor's, kept as the line at the top and an offset into it so it finds the same line at another width or font size (in split mode only the editor's: the editor leads), in preview mode the preview's (applied again while images and diagrams load, until it is reached or the user scrolls); an editor restored hidden in preview mode goes to its place when it shows. The editor takes the keyboard again if it had it, but only while the keyboard is nobody's: a search typed or focus put anywhere since launch (`keyboardIsFree` in `focus.ts`), checked when the restore starts and again when the editor has loaded, keeps the keyboard where the user put it. Like focus mode it is a view preference of one window: a JSON value in the webview's local storage (`devot.lastState.<window label>`, versioned; a window File > New Window opened keeps it in session storage instead, see Several main windows), never in the database and never synced; every part is checked when read and a part that is not valid falls back on its own. What is gone since is skipped quietly: a notebook shows All Notes, a filter on a deleted tag shows no filter, and a note deleted, in the Trash or purged leaves the view with no note open. The Trash and search results are not restored: while the Trash shows, the state from before it is kept, and a search leaves the view under it. It is saved at once when the view, filter, note or mode changes, 400 ms after the selection or a scroll position stops changing (never per keystroke; the editor measures its top line only when it scrolls, and moves it with edits made above it), and when the page goes away or out of sight and at the start of the quit handshake. Nothing is saved until the window has restored, so a window that is still loading never overwrites it, and a view or note picked while it loads is kept rather than replaced. The restored note opens like any other, as the first entry of Back and Forward's trail.
- **Keyboard navigation** (`src/core/navigation.ts`, `src/renderer/src/areas.ts`, `src/renderer/src/Sidebar.tsx`):
  - **Back and Forward:** each window keeps the trail of notes it opened (up to 100, in memory): opening a note from anywhere (the list, the palette, a link, Next or Previous) drops the entries ahead and adds it; Cmd+[ and Cmd+], and the Back and Forward buttons (SF Symbols `arrow.left` and `arrow.right`) after the focus mode button at the start of the editor's toolbar, move along it. They skip notes deleted since and the open note itself, and are disabled (the keys do nothing, the palette does not offer them) with nowhere to go. Notes opened in the Trash are not entries; Back from the Trash leaves it for the last note opened. Each press steps on at once, so quick presses each go one note further. A key pressed in the editor leaves the keyboard in the editor of the note it opens.
  - **Next and Previous:** Shift+Cmd+] and Shift+Cmd+[ open the note after or before the open one in the list shown (pinned section first; search results; the Trash's list), from anywhere; with no note open, the first or last. They stop at the ends. A list row with the keyboard follows; from the editor the new note's editor takes the keyboard.
  - **Window keys over the editor's:** the window's keys are window-wide, so CodeMirror's own bindings for them are left out of the editor (Cmd+[ and Cmd+] indent and outdent, Cmd+/ toggle comment, and the search keys that find takes; `editor/settings.ts` drops every built-in binding a `window` command takes, but an arrow key, which moves the caret in text). In the editor Tab and Shift+Tab indent and outdent (a table's Tab and Shift+Tab come first and move between cells). A held window key runs its command once, and its repeats are stopped, so they reach no native menu item either.
  - **Areas:** Tab and Shift+Tab on a sidebar row or in the note list (`panes` scope) move the keyboard to the next or previous area: sidebar, list, editor, and round again, skipping one that is hidden or has nothing to focus. The sidebar's area is its tab stop row; the list's its open note's (or first) row, else the list itself; the editor's the note's text, else the rendered note (Preview mode and the Trash: the preview is a scrolling region with `tabIndex=0`, an accessible name and a focus ring for the keyboard, so the arrow keys, Page Up and Page Down, Home and End read a long note), else its title, else the first button of the note. Control+Tab and Control+Shift+Tab do the same from anywhere, the editor and its title too (the macOS key for leaving a control that uses Tab itself). Escape then Tab (or Shift+Tab) leaves the editor as well: CodeMirror leaves the Tab after Escape alone for two seconds, and it moves on like a pane's. As in macOS's own panes, the toolbar buttons are not in this loop: each has a key or a palette command (the list's sort pop-up is Sort Notes… in the palette), and the editor's are still reached with Shift+Tab from the title.
  - **Keeping the keyboard on the page** (`src/renderer/src/focusRescue.ts`): when the element that has the keyboard is removed, hidden or disabled (a row deleted, a button that goes away with its action, Focus Mode hiding an area, a sheet that closes), the web view drops focus on `<body>` and keys stop reaching the window. A hook in the window watches for that (focus events and a mutation observer, checked a frame later, so components that move the keyboard themselves go first) and moves the keyboard: on a sidebar row to the same row if it is still there (moved or renamed), else the next row of its kind (notebook, status, tag), the one before it at the end, else any other row; elsewhere to the note list, else the editor area, else the sidebar. It leaves alone focus the user moved on purpose (a click on blank space) and any window with a sheet open; a sheet that closes without giving the keyboard back (the hook remembers what had it before the sheet) hands it back. The note list keeps its own recovery (next row, open note's row); Backups and Import open in a layout effect on their Done button (so Return dismisses them and never takes a backup) and `close()` on unmount so the keyboard returns to what had it. Buttons that turn off while the keyboard is on them (Empty Trash, Clear Usage Data, the Backups buttons while busy) use `aria-disabled` and a guarded handler, not `disabled`, so they keep it; a tag chip's remove button hands the keyboard to the tag field when pressed from the keyboard. The note list always keeps a Tab stop: the open note's row, else the first row (the open note may not be listed).
  - **The list:** Return on a row edits the open note's title (caret at its end), Cmd+Return its body (showing the editor in preview mode); with no note open, the row's note opens first. Not in the Trash's list.
  - **The sidebar:** it is one tab stop, the row of the view shown (its filter, else its notebook, the Trash or All Notes). Up and Down (Home and End) move through every row in order (All Notes, Pinned, the notebooks shown, the statuses, the tags, Templates, the Trash), and the view follows: All Notes or a notebook shows without a filter (a click on one keeps it; the keyboard shows the row it is on), the Trash shows, and a filter row turns its filter on (narrowing the notebook shown, as a click does). On a notebook Left closes it (or goes to its parent) and Right opens it (or goes to its first sub-notebook).
  - **Hiding the sidebar:** Cmd+/, View > Hide Sidebar (which reads Show Sidebar while it is hidden; the page relabels it through `sidebar_menu_set`, main window only), or the button in the sidebar's title bar hide it; the button that shows it again sits at the start of the list's toolbar. Each window remembers it in local storage (`devot.sidebarHidden.<window label>`, like focus mode). In focus mode the sidebar is hidden anyway: Cmd+/ leaves focus mode and shows it. Hiding it with the keyboard in it gives the keyboard to the list. The key reaches the page first, which runs it and stops it; the menu item runs it only when the page did not (so a picked item or a key the page never saw still works), and the first menu toggle within half a second of the key's is dropped as an echo. Shown again from its Show Sidebar button, the sidebar takes the keyboard.
- **Commands and shortcuts** (`src/renderer/src/commands/`): every app command is declared once in the registry (`registry.ts`) with an ID, a catalog label, a group (note, notebook, tag, view, search, find, format, table, image, app), a scope and its default keys. Keys use one platform-neutral notation (`keys.ts`): modifiers `Mod` (Command on macOS), `Ctrl`, `Alt`, `Shift`, then a letter, digit, punctuation mark or named key (`Mod+Shift+D`, `Mod+Backspace`, `Enter`); the registry writes them in canonical order, and `keys.ts` turns them into what macOS shows (`⇧⌘D`), native menu accelerators (`Shift+CmdOrCtrl+D`) and CodeMirror key names. A key press matches by the character it types, as the menu bar matches key equivalents, so Cmd+Q is Q on a French keyboard (where Q is on the A key) and Cmd+Z is Z on a Dvorak one (`pressedKey`); the recorder and the reserved keys read presses the same way. A press whose character is not the key's own (Option, or Shift on a digit or punctuation key) is read from the character that physical key was seen to type (`rememberKey`, fed by every key press of a window), else from its US position; the page cannot ask the system for the layout, so a layout map from `UCKeyTranslate` was not added. The keypad matches by its keys, whatever the layout (`=`, `-`, `.`, `/`, `+` as `=`, digits). Exactly the modifiers named must be held; auto-repeat never runs a command. A scope says where a command's keys work, and scopes nest: `window` (anywhere, also in the editor) holds `editor` and `outsideEditor`; `outsideEditor` holds `panes` (the sidebar's rows and the note list, not toolbars or fields); `panes` holds `sidebar` (a sidebar row, which holds `notebookRow` and `tagRow`) and `list` (any note list); `list` holds `noteList` (the library's or search results' list) and `trashList` (the Trash's). Two commands may share a key only where their scopes never overlap, that is unless one scope lies within the other (so Cmd+Delete is Move to Trash in `noteList` and Delete Permanently in `trashList`, and Delete deletes a notebook or a tag by the row it is on); a unit test checks the whole registry, and keys macOS keeps (Cmd+Q, Cmd+H, Cmd+M, Cmd+W, Cmd+Comma, ...) are refused. Window keys are dispatched by `useWindowCommands` (none while a sheet is open, none that the list or editor already handled); the note list, the Trash's list, notebook rows and tag rows match their own keys through the registry (`noteShortcut`, `trashShortcut`, `bookShortcut`, `tagShortcut`, `commandMatches`), including `/` in a list (search the view it shows); no key is handled outside it; a held key with Command or Control that is a command's key does nothing after its first press and is stopped (`heldCommandKey`) in the list and the sidebar's rows, as in `useWindowCommands`, so it never repeats into the Edit menu (Select All, Copy); the context menus (note, notebook, tag, and the toolbar's Alert pop-up) take their labels and accelerators from it; the editor's format, table, Paste as Plain Text and New Note from Selection keymaps and its F3 find keys are generated from it; find (`findShortcut`) and the status keys read it too. The window binds a handler to each command it can run at the moment (a note, status or find command only while a note is open, a format or alert only while the editor shows), and only those are offered. Native menu items that run a command (View > Revision History…, Command Palette…, Hide Sidebar and Synced Scrolling, and Devot > Backups…) are built in Rust with the command's default key (`tests/policy/native-menu-keys.test.ts` checks each against the registry and keeps the menu's own keys, Quit and Settings, clear of every command) and get the keys in effect from the main window (`command_menu_set`, below). Rust sends such an item's event to the main window whichever window has the keyboard, so the main window ignores it while it does not (`document.hasFocus()` is false: Settings or a native panel is the window the user is in): Cmd+K in Settings opens nothing behind it. The editor's own keymaps (format, table, find) are matched by CodeMirror, which reads the character like the menu bar for letters and falls back to US key positions with Option or Shift. The Format menu takes its keys from the registry at run time (below). Every reader takes a command's keys through `commandKeys`: the registry'sdefaults with the user's changes (see Keyboard shortcuts).

- **Format menu** (`src-tauri/src/format_menu.rs`, `src/renderer/src/commands/formatMenu.ts`): the menu bar has a Format menu between Edit and View with every format command: the inline formats (Bold, Italic, Strikethrough, Highlight, Inline Code, Link), a Heading submenu (1 to 6), the block formats (Code Block, Bulleted, Numbered and Task List, Quote), an Alert submenu (Note to Caution) and Horizontal Rule. It exists for the keys: in the app Command-I reached neither the page nor the menu bar. AppKit offers a key equivalent to the key window's views before the menu bar, and the web view took Command-I without passing it on. So on macOS a local key-down monitor (`native::macos::give_format_menu_keys_priority`, installed with the main window) runs before both: a key with Command or Control in the main window, while it is the key window, is offered to the Format menu alone (`performKeyEquivalent:` on the menu bar's Format submenu, found by its title on every key, since muda keeps a separate NSMenu per attachment), and a key the menu takes is dropped, so the web view and the other menus never see it; every other key goes its usual way. While an input method composes in the window (its first responder, the web view, has marked text: `hasMarkedText`, asked only for keys with Command or Control) no key is offered: the web view hands it to the input method first, which may use Control keys, and a format would end the composition (see Input methods). The decision is a pure function (`native::offers_to_format_menu`, unit-tested); the AppKit part is checked on a throwaway menu bar, and the marked text on an offscreen window (a text view, and that the web view answers the same question), by the main-thread test (`tests/main_thread.rs`). Debug builds log `I_FORMAT_KEY_MENU` each time the menu takes a key, and `I_FORMAT_KEY_SEEN` for every key with Command or Control: the outcome (`TAKEN`; `REFUSED`, the menu said no; `NOT_OFFERED`, the window check failed or an input method composes; `NO_MENU`), the event's window and the key window (0 none, 1 main, 2 other), whether the main window has marked text, the modifier bits, the key code, auto-repeat and whether a menu item has that key (0 none, 1 enabled, 2 disabled). `format_menu_set` runs one call at a time and takes a turn-off only from the main window that turned the menu on (or once that window is gone), since the blur of the window left can land after the focus of the window entered. It takes every key off the menu (natively, on the main thread) before it sets the planned ones: the menu library cannot remove an accelerator (setting none keeps the old one), and AppKit lets a disabled item with a key take that key without running it, so a greyed-out Format menu would otherwise swallow Option+Cmd+K outside the editor. Rust holds the items (labels from `strings.rs`) but no keys: while the editor has the keyboard the UI sends the registry's keys for them (`format_menu_set`, which accepts only format commands and accelerators with Command or Control that none of the menu bar's own items has, `MENU_BAR_KEYS`) and the items are enabled; when the keyboard is anywhere else, or another window (Settings) is the key window, it takes the keys away and the items are greyed out, so a format key never shadows what that key does elsewhere (Shift+Cmd+C copies a note's URI on a note list row). Keys the user changed (Settings > Keyboard Shortcuts) reach the menu through the same call, at once. A picked item, by mouse or key, sends `devot://format` with the command ID to the main window, which runs it only when it is a format command and the editor has the keyboard; while an input method composes in the editor the format does nothing (`formatCommand`). A format runs once per key press: when the menu has the key, the page never sees it (the monitor drops it); when the page sees it, the editor's keymap (kept for Linux CI, which has no monitor, and in case the menu does not match a key) runs the format and stops the key; and should the same key reach the menu as well, its event is dropped once as an echo when the keymap ran that format within the last half second. Like any menu key equivalent, a held format key repeats. A format's key is offered only where the format does something: the editor reports the formats that would do nothing at the caret after a pause of 150 ms (`inertFormats`, `editor/formatKeys.ts`; every inline format in code, Strikethrough on an empty line start; nothing is reported for a selection over 5000 characters or while the parser has not reached it), and `format_menu_set` is sent without their keys, so the key reaches the editor's other bindings (Cmd+I selects the parent syntax in code). The policy test checks that the menu lists exactly the registry's format commands, with the app's labels and no keys of its own, and that the registry's format keys are ones `format_menu_set` accepts: each has Command or Control and none is in `MENU_BAR_KEYS`, and they equal `src-tauri/tests/fixtures/format-menu-keys.json`, the key map Rust's tests run through the same checks (a refused map would leave the menu without keys and Cmd+I lost again).
- **Keyboard shortcuts** (Settings > Keyboard Shortcuts; `src/renderer/src/commands/keymap.ts`, `shortcutSettings.ts`, `src/renderer/src/settings/KeyboardSection.tsx`, `src-tauri/src/keyboard_shortcuts.rs`): every registry command can take other keys or none.
  - **Model:** the user's changes are a map from command ID to that command's whole list of keys (an empty list: no key; at most four), layered over the registry's defaults; a command not in the map has its defaults. `effectiveKeymap` merges the two in one place and hands the result to the registry (`setCommandKeys`), so the window's keys, the note list, Trash, notebook and tag row keys, find and status keys, the editor's keymaps, the Format menu, the View menu's command items, context menu accelerators, the palette's key hints, button tooltips (`commands/titles.ts`) and the font size hint all read the keys in effect. A key a command may not take, or an unknown command, in the stored map is ignored. If the stored map still holds a clash (edited by hand, or a later default), a key the user set wins over a default, and between two the user set the command declared first keeps it.
  - **What a command may take** (`keyProblem`): a key in the registry's notation, never one of `RESERVED_KEYS` (Cmd+Q, Cmd+H, Option+Cmd+H, Cmd+M, Cmd+W, Cmd+Comma, Cmd+Tab, Cmd+Space, Control+Cmd+F, Control+Cmd+Space, Control+Cmd+Q, Control+Cmd+D) nor Escape (it closes and cancels everywhere), nor an arrow key, Home, End, Page Up or Page Down (the lists, the sidebar and text move on them whatever the modifiers). In the `window`, `outsideEditor`, `editor` and `panes` scopes, where text is typed (the panes' Tab also leaves the editor's text after Escape), a key needs Command or Control (a key without them types text) and may not be an Edit menu key (Undo, Redo, Cut, Copy, Paste, Select All). On list and sidebar rows (the scopes within `panes`) any other key goes, as the defaults there use M, P, Delete and Cmd+C. A command's own default keys stay allowed (the table keys Tab, Return and Option+Up, F3). A stored list none of whose keys a command may take is ignored (the command keeps its defaults); an empty list means no key.
  - **Clashes:** a key another command has where both apply (their scopes overlap, as the registry's clash test defines) is shown with that command's name, and taken from it only when the user agrees (Reassign); Reset does the same when a default key now belongs to another command. Recording replaces the command's keys with the one recorded (Reset brings back a second default key).
  - **Pane:** a card per command group (App, Notes, Notebooks, Tags, View, Search, Find, Edit, Format, Tables, Images; `GROUP_ORDER`), each row the command's name (and where it works) with its keys in a field at the right, under a filter field that matches names, group names and keys (as shown, as written, or typed with cmd, ctrl, opt, alt and shift: `cmd+k` finds the commands bound to Mod+K alone; `shortcutSearch.ts`). Left of the field, Reset shows while the command is changed, Copy and Clear while the row is under the pointer or has the keyboard; Reset All Shortcuts… is in the toolbar's More menu (an in-page menu: arrow keys, Home and End move, Escape closes).
  - **Recorder:** each command's shortcut is a button named "<command> shortcut: <keys>". Pressed, it captures the next key combination, read as the character the key types (`shortcutOfPress`, as `keyMatches` reads it): modifiers alone wait for a key, keys an input method is composing are left to it, Escape cancels, and leaving the button cancels; Backspace and Delete are recorded like any key (some row commands use them), so removing a key is the row's Clear button. Reset gives a command its defaults back; Reset All Shortcuts… asks first. Clear, Reset and Reset All use `aria-disabled` rather than `disabled` when there is nothing to do, so the one just pressed from the keyboard keeps the focus. A unit test (`commands/bindings.test.ts`) checks that every command the page lists runs from a key set for it. What happened (the new keys, a refusal and why, a cancel) is announced through a live region, and a refusal also shows under the row.
  - **Store:** a local preference like the editor settings: Rust keeps the changes in `<app data>/keyboard-shortcuts.json` (outside the database: never synced, never in backups), written through a temporary file and a rename. `keyboard_shortcuts_get` is granted to the main, note and Settings windows, `keyboard_shortcuts_set` (a patch: new keys, or null for the defaults) to the Settings window only. Rust checks command IDs (dotted camelCase words), the notation in canonical order, the reserved keys and Escape, four keys at most, each once, 256 commands at most, and refuses a bad patch as a whole; reading the file drops only a bad entry. A file that cannot be read is never written over, as with the editor settings: the defaults apply, a change is refused with `E_KEYBOARD_SHORTCUTS_READ_FAILED` until a read works again, and a damaged file is copied to `keyboard-shortcuts.json.damaged` before the next change replaces it. What only the registry knows (which commands exist, scopes, clashes) the UI checks. After each change Rust sends `devot://keyboard-shortcuts-changed` with all changes and a revision to every window (re-sent in the page as `devot:keyboard-shortcuts-changed`), which applies the newest revision. The page side shares its revision and in-flight handling with the editor settings (`src/renderer/src/syncedStore.ts`), and the atomic write with them in Rust (`atomic_file.rs`).
  - **Live everywhere:** the editor's registry keymaps (format, table, find, Paste as Plain Text, New Note from Selection, and CodeMirror's own bindings less every key a window command has and every key the user gave an editor command, compared as key presses however CodeMirror spells them, `codeMirrorKey`; an editor command's default keys, such as Tab in a table, fall through to CodeMirror's binding where the command does not apply) sit in compartments (`editor/registryKeys.ts`) and are rebuilt in the open editor in one transaction; context menus are built again on their next use; the Format menu gets its keys again; and the main window sends the View menu's command items their keys through `command_menu_set` (in one queue with `format_menu_set`, the command items first, so a key moved between the two menus is never on both; a failed call is sent again when the window comes to the front) (main window only; command ID to accelerator or null; Rust accepts only those three commands and accelerators with Command or Control that the menu bar's own items do not have, takes every key off them natively, `native::macos::clear_item_key_equivalents`, since the menu library cannot remove one, and sets the planned ones).
- **Window shortcuts:** Cmd+N New Note (in the Trash it opens All Notes first and creates the note there; in Templates it makes a template), Cmd+T New Note from Template, Shift+Cmd+F and Shift+Opt+Cmd+F search, Shift+Cmd+D focus mode, Opt+Cmd+Y Revision History, Cmd+K the command palette, Cmd+P split view, Cmd+F and the other find keys, Control+Command+1 to 5 the note status, Cmd+= (also Shift+Cmd+=) and Cmd+- the editor's font size and Cmd+0 its default size, Cmd+[ and Cmd+] (also Cmd+Left and Cmd+Right while no text field has the focus) Back and Forward, the editor too, Shift+Cmd+] and Shift+Cmd+[ the next and previous note, Cmd+/ the sidebar, Control+Tab and Control+Shift+Tab the next and previous area (see Keyboard navigation). Shift+Cmd+P prints the open note.
- **Editor line keys** (`src/renderer/src/editor/lineCommands.ts`, the `edit.*` commands): Shift+Return starts a plain line, Cmd+Return a blank line below (caret moves to it), Shift+Cmd+Return one above, Cmd+D deletes the line, Cmd+L selects it, Option+Up and Option+Down move it, Shift+Option+Up and Shift+Option+Down copy it, Tab and Shift+Tab indent and outdent (Indent and Outdent have no keys of their own, so Cmd+[ and Cmd+] stay Back and Forward), Control+Shift+O opens the link or note link under the caret, F5 and Shift+F5 sort the selected lines ignoring case (Control+F5 and Control+Shift+F5 case-sensitively), Control+J joins lines. Return on an empty quote line continues the quote; Shift+Return or Backspace on the empty `> ` leaves it. A backtick typed over a selection wraps it in backticks. In a table the alignment keys are Option+Cmd+Left, Right, Up and Down (left, right, centre, none) and a row moves on Shift+Option+Cmd+Up and Down (Shift+Option+Up and Down copy the line, so the row keys add Cmd and no other command shares them). Full screen is the system's Control+Cmd+F. The keys are registry commands, so the Keyboard settings table lists them and a stored override keeps working when a default changes.
- **Input methods** (`src/renderer/src/ime.ts`): the keys an input method composes with (pinyin, kana, dead keys) are its own, so the Return that picks a candidate never also submits a field or starts a line, and the Escape that cancels a composition never also closes or clears anything. `isImeKey` tells them apart as WebKit sends them: during a composition (`isComposing`); with key code 229 when the input method took the key (the Return or Escape that ends a composition arrives after `compositionend`, with `isComposing` false); and as the first key down within 100 ms after `compositionend`, whatever its code (`watchCompositions`, started in each window before any key handler). Every key handler asks it first: the window shortcuts (`useWindowCommands`), the find keys and the find bar's Escape, the panes' Tab, and the Return, Escape and arrow keys of every field (Move to Notebook, the find bar, the tag field, renaming a notebook or tag, the search field, the template and tag pickers, the palette, the shortcut recorder). In the editor (`editor/imeKeys.ts`) keys typed into a composition stop before the editor's handlers but are never prevented, so keys the input method passes on (Command-Q, Command-V) still reach the menu bar; the key that ended a composition stops ahead of every keymap once CodeMirror has seen it (CodeMirror itself ignores it only for a moment after the composition ends). Nothing changes the editor's text while it composes: a format (from the Format menu, the toolbar or a key) does nothing then (`formatCommand`), and the Format menu's key monitor offers no key while the web view has marked text (see Format menu).
- **Command palette** (`src/renderer/src/palette/`): Cmd+K anywhere, the editor too (Link is Option+Cmd+K), or View > Command Palette…. One field finds commands, notebooks, tags and notes by fuzzy match (`src/core/fuzzy.ts`: the query's letters in order, case, accents and spaces ignored, word starts and runs scoring higher). Results are grouped by kind, each group best match first and the group with the best match first (ties keep the order commands, notebooks, tags, notes); matched letters are bold, commands show their key. With nothing typed it lists every command it can run and the first five notebooks, tags and recently edited notes; a query shows up to 20 of each kind (50 commands). Return runs a command, opens a notebook (as clicking it in the sidebar), filters by a tag, or opens a note (leaving the Trash; the open note stays as it is). In the Trash the commands include Restore from Trash and Delete Permanently for the open note, and Empty Trash whenever the Trash has notes; notebook and tag row commands act on a row and are not listed. Option+Return (or Option-click) is the second action: move the open note to that notebook, or add that tag to it; it is offered only when it would change something, and a line under the results names both actions for the selected result. Arrow keys move, Escape or a click outside closes; keys that end an input method's composition are left to it. Closing gives the keyboard back where it was (into the editor with its selection), then runs the picked action. Once the action has finished (it may wait on the worker: opening a note, Move to Trash, Duplicate) and the window has rendered, if the place that had the keyboard is gone or hidden (Show Preview, focus mode, a replaced editor), the open note's row (or the list's first row), its editor, its title, or else a toolbar button takes it. A note an action opens while the palette came from the editor takes the keyboard into its own editor once it has loaded. The field is a combobox over a listbox of groups (`aria-activedescendant`). Notes come from the window's note list in memory, never from a search request.
- 120 Hz: the WebKit 60 fps preference is turned off when the main window is created.
- Icons: the `symbol_png` command renders an SF Symbol through AppKit, or UIKit on iOS (`native/ios.rs`), in black at two pixels a point for the UI to tint. UIKit lays the symbol out for a display scale of 1, on whole points as AppKit does: its PNG is then within a pixel of the Mac's in size and in where the symbol sits, 8 bits a channel in sRGB like AppKit's (laid out for the screen's scale, UIKit sizes it in thirds of a point and it sits higher). It is an async command whose render runs on a blocking thread, one render at a time (AppKit uses an image on one thread at a time) in an autorelease pool of its own, never on the main thread: Tauri runs a synchronous command there, and at launch the main thread also routes the page's first IPC, which the first paint's 22 icons held up for about 115 ms (80 of them on the first, when AppKit loads the symbols). The UI caches results per name, size and appearance, and re-requests them when the appearance changes.
- Icon placement (`src/renderer/src/icons/symbols.ts`): every symbol shown at one icon size is asked for at one point size (`boxPoints`, from the size's box alone) and weight, so icons of a size share their optical size and stroke whatever their shape. The UI never scales a symbol on its own: it measures the PNG's ink and copies it pixel for pixel onto a square canvas, the ink centred on whole device pixels (`placeInCanvas`); the canvas is the icon's box, grown evenly where the symbol is larger, so a wide symbol (the sidebar toggle, the eye) overhangs its box rather than shrink. A disabled button only fades (`opacity.disabled`).

### Theming

- **Default theme:** Devot's palette in the appearance chosen in Settings > Appearance: Light, Dark or Auto (the default, CSS `prefers-color-scheme`). A chosen appearance is `data-appearance` on the root element, which the generated tokens read, and Rust gives every window that theme (`editor_settings::announce`). The accent is Devot's blue unless "Use the System Accent Color" is on: then Rust reads the accent from AppKit for both appearances and pushes changes from `AppleColorPreferencesChangedNotification`, and the UI sets `--system-accent-fill-<appearance>`, `--system-accent-text-<appearance>`, `--system-accent-selection-<appearance>` and `--system-accent-selection-inactive-<appearance>` (solid tints of the fill that stand 1.3:1 from the editor and the active line, behind selected editor text) (`src/renderer/src/theme/accent.ts`). The system colour is used raw for neither: yellow or green under white text would be 1.6:1 to 2.4:1, so each role takes the system colour moved toward black or white only as far as WCAG AA (4.5:1) needs (`contrast.ts`; a colour that already passes is left alone): the fill under the on-fill colour, the text and links on the surfaces, the fills drawn over them and the editor selection. Multicolor, or the option off, removes the overrides and the tokens fall back to Devot's palette.
- **Contrast:** every colour pair the UI draws meets WCAG AA in light and dark (4.5:1 for text, 3:1 for marks such as status dots and the caret), for the default palette and for every system accent. `src/renderer/src/theme/contrast.test.ts` computes the ratios from the token values, so a token edit that drops a pair below the line fails the unit tests. The editor's colours come from the same tokens: its highlight style (`editor/markdown.ts`) and theme (`NoteEditor.tsx`) use theme variables only, never CodeMirror's light-only defaults, and `tests/ui-csp` reads the computed colours of a link, a rule, the active line, the gutter and the selection in both appearances.
- **Tokens build:** `pnpm tokens` compiles `design/tokens` into `src/renderer/src/theme/tokens.css` and `tokens.ts` (committed); `pnpm tokens:check` fails CI when they are stale. Each built-in theme besides the default is listed in `scripts/tokens/themes.ts` and compiled from its own `design/tokens/themes/<id>.light|dark.tokens.json`; a test fails when a theme lacks a token of the default theme or has an extra one. Only theme colours and non-colour base tokens are exported, and a policy test rejects colour literals in UI styles.
- **Other themes:** independent of the system accent. Each provides light and dark appearances and follows the system's light/dark switch, unless it declares a single appearance. The built-in one is Ivory, a warm theme. The gradient themes (Dawn, Tide, Sage, Ember) are the default theme plus a translucent gradient over the sidebar and the note list (`--backdrop`, from `design/tokens/backdrops.tokens.json`); they follow the system accent like Default.
- **Theme setting:** each appearance has its own theme: Settings > Appearance > Light Mode and Dark Mode each choose Default, Ivory or a gradient, and the one for the appearance shown is marked Active. They are the `lightTheme` and `darkTheme` editor settings (`default`, `ivory`, `dawn`, `tide`, `sage` or `ember`), stored with the other editor settings, validated in Rust (`editor_settings::Theme`; an unknown stored value reads as Default, an unknown value in a change is refused with `E_EDITOR_SETTINGS_INVALID`) and sent to every window with the other settings (`editor_settings::announce`). A settings file from before them holds one `theme`, which fills whichever of the two it lacks (in Rust when the file is read, and in `parseEditorSettings`); the next write leaves `theme` out. The page marks the root element with the theme for the appearance it shows, `data-theme='ivory'` (`themeInEffect`, `theme/appearance.ts`; Default leaves it off), and marks it again when the system's appearance switches while the window follows it. The generated stylesheet scopes each built-in theme by that attribute, after the default theme's rules and one attribute heavier, so a theme wins in every combination of theme, chosen appearance and system appearance; `[data-theme-preview]` shows a theme in a card whatever the page has. Ivory ignores the system accent, so "Use the System Accent Color" is hidden while it is the theme in effect.
- **Token themes (phase 1):** a theme is a DTCG token file with the same structure as `design/tokens/themes/system.*.tokens.json`. Built-in themes use this format too.
- **Custom CSS (phase 2):** user CSS loads in `@layer user`, after the app's own layers. It targets stable `data-devot-part` attributes, which are a documented, versioned surface; class names are not. The CSP blocks external `url()` loads, so a theme cannot send data out.

## Quality

### Priorities

When trade-offs collide: **data integrity > security > performance > functional correctness > visual polish.** Losing or corrupting a note is the one failure that cannot be undone.

### Test layers

1. **Unit (Vitest):** most TypeScript tests. The core library is plain TypeScript and its unit tests run in milliseconds.
2. **Integration (Vitest + real SQLite):** the core with its better-sqlite3 adapter on temporary database files; the database is never mocked. Covers the data layer, import and export, the link index and MCP.
3. **Property-based (Vitest + fast-check):** random operation sequences checked against invariants, for example: Yjs edits converge in any order; the link index always matches note bodies; a purge deletes only the attachments no note left shows. Markdown export then import is checked by example round trips (`tests/core/export.test.ts`), not yet by a property test (phase 2).
4. **Rust (cargo test):** command validation, storage on temporary SQLite files, and native code. Tests that touch WebKit run on the main thread in harness-free test binaries (`harness = false`), because libtest's worker threads crash WebKit.
5. **UI integration (Playwright, WebKit engine, phase 1):** the real UI served by Vite in the UI tests' build (`vite.ui-test.config.ts`: notes in an in-memory storage), with Tauri's IPC mocked and `Object.prototype` frozen in the main frame, as the app does. Real keyboard input works here. Runs on Linux CI. A second project (`tests/ui-csp`) runs the built UI under the production CSP (`scripts/serve-csp.ts`), because `pnpm dev` relaxes the policy. Each checkout serves on ports derived from its folder (`tests/support/ports.ts`; `DEVOT_UI_PORT` and `DEVOT_CSP_PORT` move them), and a server already answering on one fails the run unless `DEVOT_REUSE_SERVERS=1`. Vite pre-bundles the core worker's dependencies up front (`optimizeDeps.entries`), and a test fails if Vite re-bundles under an open page. The window sets `data-ready` on `.window` once its lists have loaded and its last state is restored; tests open and reload the app with `openApp` and `reloadApp` (`tests/ui/fixtures.ts`), which wait for it, and check for a positive sign (a write, a notice) before they check that something did not happen. Timing tests poll or compare growth between sizes; none relies on a wall-clock limit that load can break.
6. **Full-app end-to-end (WebdriverIO + `@wdio/tauri-service`, phase 2):** a few critical flows in the built app on macOS, through the embedded WebDriver (debug builds only). Its `browser.keys` does not type into CodeMirror; text goes in with `addValue`. Real keyboard and IME input stay manual checks.

### Data integrity

- **Crash safety:** a test kills the app at random points during writes, reopens the database, and checks that every committed change is intact and the WAL recovers.
- **Schema migrations:** a fixture database is kept for every released schema version; each must upgrade to the current one.
- **Merge convergence:** property tests over Yjs edits (see above).
- **Automatic local backups (phase 1):** a daily snapshot through SQLite's online backup API into `<app data>/backups/devot-<UTC time>-<number>.sqlite`. A background thread checks 20 s after launch and then hourly; a backup is due when the last one taken is a day old. Each check, and every backup or restore, first removes what a quit during a snapshot left (its private folder), so a nearly full disk gets that room back even when the next snapshot fails. It copies from its own read-only connection in one step (a consistent read; WAL keeps writers going), checks the copy with `quick_check`, and renames it into place, never over another file (SQLite writes it in a new private folder in `backups/`, see Security). Devot > Backups… lists them, the last taken first; restoring asks first, copies the current data aside as a safety copy (`devot-<UTC time>-<number>-before-restore.sqlite`, listed with the backups), copies the snapshot into the open database, migrates it, and reloads the window. Every other window with a core of its own (each main window, `main` hidden too, and each note window) is asked first (`devot://restore-prepare`): it saves, holds compaction, stops its core and answers (`backup_restore_ready`); a window that has not answered in 5 seconds calls the restore off (`E_BACKUP_RESTORE_WINDOWS`). Once the restore is over, ran or not, each of them reloads (`devot://restore-done`). So no window writes the notes it held from before the restore back over it, and the compaction in `main` is held wherever the restore starts. Failures are logged by code and shown as a notice. Restore has its own test. Until sync ships, this is the only second copy of the notes.
  - **Order and retention** (`src-tauri/src/backups.rs`): backups go in the order they were taken, which the number keeps (one more than the highest in the folder), never by the time in the name, so a clock set back or ahead can neither make a new backup the first to go nor keep a future one the newest. Taking a backup (daily or Back Up Now) keeps the last 7 backups and, apart from them, the last 7 safety copies (enough to restore each backup in turn and still go back), and never removes the one just taken. It also keeps the first safety copy taken after each of the 7 backups it keeps, since that copy holds the notes from before a run of restores, which no backup has; it goes with the backup before it. A restore removes nothing. Names from before backups were numbered still list and restore, before every numbered one.
  - **Clock changes:** the thread takes a backup only when it has not taken one itself in the last 24 hours by a clock that setting the time does not move and that keeps counting while the Mac sleeps (`CLOCK_MONOTONIC`, through `native::macos::time_since_boot`; Rust's `Instant` stops during sleep), as well as when the newest backup is a day old by the wall clock. When the newest backup is from the future (the clock was set back), its age is unknown, and only the first rule applies. So a clock set back, or a slow clock set right, costs a backup a day, never one an hour, and a Mac that sleeps still backs up daily.
  - **Partial snapshots:** a quit or crash during a snapshot leaves its private folder behind. Every check and every backup removes such folders (with older builds' `.partial` files and the side files of backups that are gone) while this process takes no snapshot; a snapshot also locks its folder (`flock`) while SQLite writes in it, and a locked folder is never removed, whoever tidies. Links and anything outside `backups/` are never touched.

### Crash reporting and logs

- **Sentry:** the Rust SDK (`src-tauri/src/crash.rs`, ureq transport over the system TLS) for panics, the browser SDK (`src/renderer/src/crash.ts`, loaded only when a DSN is set) for uncaught UI errors, and a crash reporter process for native crashes (below). One Sentry project for all three.
- **Native crashes** (`src-tauri/src/crash_reporter.rs`; signals, aborts, crashes inside WebKit or AppKit): in a DSN build, a background thread at launch starts a second copy of the app binary as the crash reporter (`devot --crash-reporter <Mach service> <app data>/crash-reports`; the service name carries the app's process ID and a random token). Once the reporter says on its standard output that it holds the service (a name has one holder at a time, so no other process can stand in for it; a reporter that has not said so within 5 s is stopped), the app attaches a crash handler (Mach exception ports plus a `SIGABRT` hook; `native::macos::attach_crash_handler`, the only `unsafe` it needs). On a crash the handler hands the crashed task to the reporter over Mach IPC and waits up to 10 s for its answer. Then the app ends as it would have without the handler: the handler puts back the `SIGABRT` action and exception ports from before it was attached, a Mach exception goes on to those (by default the system's crash reporting, then the signal), and a `SIGABRT` (an abort, or one sent by another process) is raised again under the old action, which by default ends the app with that signal. The handler's own thread blocks `SIGABRT`, so a signal sent to the app never lands on the thread that must answer it. When the reporter ends (its output closes: it saved a crash, or something stopped it), the app detaches the handler, which could no longer report, and does not start another reporter: the reporter ends on its own only after a crash, and one stopped from outside could be stopped again; the app then crashes as it would in a build without a DSN. The reporter accepts a crash only from the app that started it (by process ID). It writes a minidump of the app **into memory**, walks each thread's frame-pointer chain through the dumped stack memory (on arm64 a leaf function's caller comes from the link register when that points into another binary; an abort's trace starts where the signal was raised, below the handler's own frames), and keeps only code addresses, the binaries they fall in (file names, never folders; debug IDs; frames in the app's own executable are in-app, so Sentry groups by them: that binary is found by the crashed process's executable path, since the minidump lists any plug-in bundle AppKit or WebKit loaded before it), the exception and signal numbers, and the OS version and CPU. A frame-pointer chain or a register can hold data instead of a code address (note text, when data is used as a pointer), so an address outside every binary is never a frame, and a bad access's fault address (the Mach subcode) is kept only near null (below 4 KiB) or inside a binary; otherwise the Mach exception's numbers are left out and its names stay in the error type. It builds a native Sentry event from those alone (the crashed thread and up to 63 others, 128 frames each), runs it through the same scrubbing as every other event, and saves it as `<event id>.json`. A minidump that fails to write (it happened in about 1 of 150 crashes while the machine was overloaded) is tried twice more, 100 ms apart; if no minidump can be written or read, the report still carries the exception, named as it would be with one, without stacks. The minidump itself holds stack memory, which may contain note text, so it never reaches the disk or the network, and registers are not kept. The next launch (DSN builds only) sends up to five saved reports, newest first, on its own thread and one request each (ureq over the system TLS, as Sentry's transport, but reading Sentry's answer, which the SDK's background transport drops), and deletes the rest. A report is deleted once Sentry has accepted it or refused it for good (another 4xx); without a connection, on a 429 or a 5xx it waits for a later launch, for up to 30 days, and nothing more is sent that launch. The reporter sleeps in the kernel until a crash arrives (no polling) and exits when the app's end of a pipe closes, which happens on any quit or kill. Builds without a DSN start no reporter, attach no handler and create no folder; a build without a DSN also refuses `--crash-reporter`. Release builds keep line tables in a separate `devot.dSYM` next to the stripped binary, so Sentry can name functions once it is uploaded (below). Crashes in WebKit's own processes (the page's content process) do not stop the app and are not reported. Tests: `tests/native_crash.rs` crashes a process for real (an abort, a `SIGABRT` sent from another process, a bad memory access and a call through a pointer made of note text, with note-like text and attachment bytes on its heap and stack and a plug-in bundle loaded) and checks that it ends with the signal and that the reporter saved one report and exited: no minidump, no home path, user name, note text, address made of text or attachment bytes, frames in named binaries, only the app's own frames in-app, the trace starting at the crash; it also checks that nothing starts without a DSN, that the reporter exits with the app, and that once the reporter has been killed the handler is detached and an abort ends the app without a report.
- **What native crash reports cost, measured on the reporter alone** (2026-10-11, M1 Pro, macOS 27.2, release builds, while the machine was heavily loaded; `cargo test --test native_crash -- measure <devot built with a DSN>`, which starts the reporter from a test binary, not from the app): builds without a DSN do no work at all (the binary grows by 16 KiB, 8.28 to 8.30 MiB, as the code is compiled out). In a DSN build, starting the reporter returns in under 0.2 ms (two threads); the reporter is ready 13 to 31 ms later on its own thread (about 300 ms on a cold disk cache), with a footprint of about 2.4 MB (7 to 9 MB resident, mostly shared system libraries), 0 % CPU and no wakeups while it waits. Not counted there: what the second copy of the 12 MB binary (it links AppKit and WebKit) takes from the app's own launch while both load, the `devot-crash-reports` thread that reads saved reports and sends them over TLS at launch, and the two threads the app gains, both blocked in the kernel: the exception handler's and one that waits for the reporter's output to close. The binary grows by 1.2 MB (10.8 to 12.1 MB) for the minidump writer and parser; that adds 28 crates (`crash-handler`, `crash-context`, `minidump-writer`, `minidump` and what they use), all MIT or Apache-2.0, which `cargo deny` checks.
- **Native crash reports against the budgets: pending a check on the real app.** Launch to first editor paint (< 700 ms) and the idle footprint (< 200 MB) have not been measured on the app with and without a DSN yet, so whether they stay within budget is open. Steps (macOS, Accessibility permission for the terminal, Devot quit, an idle machine; `sudo purge` asks for the password):
  1. `DEVOT_SENTRY_DSN= pnpm tauri build --bundles app` (the empty variable wins over `.env.local`), then `cp -R src-tauri/target/release/bundle/macos/Devot.app /tmp/devot-no-dsn.app`.
  2. `DEVOT_SENTRY_DSN=<the DSN> pnpm tauri build --bundles app`, then `cp -R src-tauri/target/release/bundle/macos/Devot.app /tmp/devot-dsn.app`. With no saved crash reports, launching it sends nothing.
  3. `bash scripts/perf/launch-cost.sh /tmp/devot-no-dsn.app`, then `bash scripts/perf/launch-cost.sh /tmp/devot-dsn.app`. Each prints 5 cold and 5 warm launches (milliseconds from starting the binary until the open note's editor is in the accessibility tree, with the empty shell's time beside it; `scripts/perf/first-paint.swift`), then, after 60 s idle, `footprint` and `top -stats pid,cpu,idlew,power` (5 s) for the app and, in the DSN build, the reporter (WebKit's own processes are not included; a DSN does not change them). The script runs the app with HOME in a temporary folder, so each build starts on a new data folder of its own (made by a first launch that is not timed and opens a first note, which the timed launches restore; the budget is judged on that library of one empty note) and never opens an installed Devot's notes or sends its saved crash reports.
  4. Record the ranges here: cold and warm launch with and without a DSN, the app's idle footprint and wakeups with and without, the reporter's footprint and wakeups. Within budget: the DSN build's launches under 700 ms and its app footprint plus the reporter's under 200 MB.
- **Source maps and debug symbols:** release builds upload the UI's source maps and the app's `devot.dSYM` to Sentry; neither ships. Tauri runs `pnpm ui:release` (`scripts/sentry/ui.ts`) before compiling the app, which embeds `dist/`: with the upload settings it builds hidden source maps (no `sourceMappingURL` comments), gives every script a Sentry debug ID (`sentry-cli sourcemaps inject`; the SDK moves it into the event's `debug_meta`, which scrubbing keeps, so Sentry matches each frame to its map), uploads the maps for release `devot@<version>`, and deletes them; without the settings it builds none. Either way the build fails if `dist/` still holds a `.map` file or a comment pointing to one, or the UI tests' in-memory storage (checked before uploading anything; see App data folder), and a failed upload fails the build (after deleting the maps). Tauri then runs `pnpm sentry:debug-files` (`scripts/sentry/debug-files.ts`) before bundling, which uploads the dSYM of that build. Rust panics list the binaries loaded at launch by debug ID (the SDK's `debug-images`; scrubbing keeps the ones a frame is in), so Sentry names the functions of a stripped release build's frames from that dSYM; a unit test prepares a panic with the app's client settings and a stand-in transport and checks that the binary its frames are in is listed. `pnpm ui:build` (development, tests, CI) never makes source maps. Tests: `tests/policy/source-maps.test.ts` runs both scripts against a stand-in sentry-cli.
- **One release and one environment per build:** the version is `src-tauri/Cargo.toml`'s alone. Rust reports `devot@<version>`; `tauri.conf.json` names no version, so Tauri gives the UI (`getVersion`) and the app bundle the same one; the source maps upload under that name. Rust reports `development` for a build with debug assertions and `production` otherwise; the UI reads Tauri's `TAURI_ENV_DEBUG` (`true` for `tauri dev` and `tauri build --debug`, `false` for `tauri build`) and reports the same, and a UI built outside Tauri's CLI reports `development`. `tests/policy/release.test.ts` checks that every side agrees.
- **Turning uploads on:** set `SENTRY_AUTH_TOKEN` (an organisation auth token, made in Sentry under Settings > Developer Settings > Organization Tokens; it can upload release files and nothing more), `SENTRY_ORG` (the organisation slug) and `SENTRY_PROJECT` (the project slug) in the environment or in `.env.local` (an environment variable wins), then run `pnpm build`. All three or none: some but not all stops the build. `tauri build --debug` never uploads. The token reaches `sentry-cli` (a pinned dev dependency, license FSL-1.1-MIT; it runs only on the developer's machine and is never shipped) through its environment, never as an argument, and Vite never exposes `SENTRY_` variables to the UI.
- **Scrubbing:** all PII collection off (`dataCollection` in browser SDK 11, `send_default_pii` in Rust), no session replay, tracing or breadcrumbs. Scrubbing is an allowlist on both sides (`src-tauri/src/crash_scrub.rs`, `src/renderer/src/crash.ts`): an event is rebuilt from a fixed list of fields, and each value is kept only in the shape its field must have. What is kept: codes (a message or exception value becomes the code it starts with, or `<redacted>`; a rejection that is not an Error, which the SDK wraps in text of its own, keeps its code too), error types (names only, without the numbers a crash reason can go on with), code locations (function names; source files and scripts, without a query and with the user name in a home folder path replaced; lines; addresses only inside a binary the event lists, at a page boundary, and those binaries by file name and debug ID), the UI scripts' source map debug IDs (`debug_meta`), the release and environment, and system details (OS name, version and build; CPU, model and family; never the device's or host's name). Everything else is left out: tags, fingerprints, extra data, breadcrumbs, user and request data, other contexts, registers, context lines, variables and mechanism data. `before_send` and `beforeSend` run it (breadcrumbs are dropped as they come); native crash reports run it when saved and again when sent. Devot's own errors carry codes and IDs, never content. Unit tests on both sides fill every field of an event with note text, titles, paths that name the user, attachment bytes and addresses made of text, and assert that none of it survives.
- **Consent:** on in the user's own builds; off in any build without a DSN. The DSN is injected at build time from `DEVOT_SENTRY_DSN`, set in the environment or in a git-ignored `.env.local` at the repository root (see `.env.example`; Rust reads it in `build.rs`, Vite through `envDir` and `envPrefix`; an environment variable, even an empty one, wins. `build.rs` watches `.env.local` only while it exists, because Cargo treats a missing path, or the repository folder with `target` inside it, as changed on every run and would rebuild the app each time; so a `.env.local` created for the first time takes effect after `touch src-tauri/build.rs`, or when the variable is set instead) and never committed; tests run without it. The CSP allows `https://*.ingest.us.sentry.io` in `connect-src`, nothing else.
- **Plan:** Sentry's free Developer plan. Over-quota events are rejected rather than billed; re-check the plan terms before integrating.
- **Local logs:** structured, size-rotated logs in the app data folder (`logs/devot.log`, JSON lines, 1 MiB per file, four older files kept). User names in paths are replaced before writing. The UI logs through `log_write`, which accepts only a code and IDs. Help > Export Diagnostics… writes a text bundle (versions plus logs) to Downloads as a new file (numbered when its name is taken: it never replaces a file or writes through a link there) and reveals it in Finder (`open -R`, reaped like a link's `open`). The core worker has a console of its own: its coded warnings and errors (a failed revision write, a swallowed notebook-order failure) and its uncaught errors and rejections (`E_WORKER_UNCAUGHT`, `E_WORKER_UNHANDLED_REJECTION`, by kind and code only) are posted to the page (`src/renderer/src/workerLog.ts`), which writes them through `log_write` like its own; the uncaught ones also go to Sentry by code (`reportCode` in `crash.ts`).
- **Error codes on the way to the log and Sentry:** a failed storage call is logged as `W_STORAGE_FAILED` with its code (the change watch, which reads every second, logs a run of failures once, as `W_WATCH_READ_FAILED` with its code), and a SQLite failure's code says its kind (`E_STORAGE_BUSY`, `E_STORAGE_FULL`, `E_STORAGE_READONLY`, `E_STORAGE_CORRUPT`, `E_STORAGE_IO`, `E_STORAGE_CANTOPEN` for a file that cannot be made or opened, else `E_STORAGE_SQLITE`), never SQLite's message. Commands reject with their code as a string; every command the UI runs goes through `src/renderer/src/ipc.ts` (a policy test keeps it so), which turns a rejection into an Error whose message is the code alone (`E_COMMAND_FAILED` for Tauri's own failures, which can quote what was sent). The core's `errorCode()` reads the code an Error or a string starts with wherever a failure is reported (notices, batches, revision writes, the UI log).
- Data region: US (the existing Sentry account).

## First-launch notes

A library that has never held anything (no live note, no note in the Trash, no notebook) gets a "Getting started" notebook with a welcome note and a Markdown example, once (`seedWelcome` in `src/core/welcome.ts`). The notebook and notes have fixed IDs, so deleting them never brings them back (a purged note is never written again, and a trashed one keeps the library non-empty) and devices that seed separately merge. Each body is seeded as a Yjs state every device builds alike (`NoteService.seed`: one insert by a Yjs client derived from the note's ID and text), so two seeded copies merge as one body; the note's later edits are made by the device's own client. A device whose build seeded another text gets another client; when sync merges two such copies and one of them was never edited (its state holds the seed's client alone), the merge deletes that copy's characters, so the note shows the other copy's text once and both lineages go on (`mergeNote` in `src/core/sync/records.ts`). Copies that were both edited keep both texts whole, one after the other, never mixed. The text is bundled Markdown in `src/renderer/src/welcome/`; `{{key:<command>}}` is replaced with the command's default key from the registry. The UI tests' libraries start empty unless a test sets `devotSeedWelcome`.
