# Markdown mirror

Part of the [architecture overview](../architecture.md).
Part of the [Markdown dialect](markdown-dialect.md).

Settings > Markdown Mirror (and the palette's Choose Markdown Mirror Folder… and, while it is on, Turn Off Markdown Mirror) keeps a folder the user picked up to date with every note as a Markdown file, so other tools (editors, grep, Git, Spotlight, agents) read the notes without an export.
It is off by default.
The notes database stays the source of truth: the folder is written by Devot and never read back, which the section says.

- **Layout and files** (`src/core/mirror.ts`): an export of every notebook at once (see Export and print): a folder per notebook (sub-notebooks nested), a `.md` file per note named after its title with Devot's front matter where import would not read the title, tags or status back, one `attachments` folder at the top; notes in no notebook (or a deleted one) at the top.
  Templates and the Trash are left out.
  Importing the folder gives the same notes (title, body, tags, status, notebook structure and images) inside one notebook named after it, checked on real files in `tests/core/mirror-sync.test.ts`.
  Export reads a note's Markdown once (`markdownFacts` in `src/core/import.ts`), and not at all when it cannot hold an image (it has neither `![` nor an `<img` tag, in any case), front matter or a level-one heading; a property test checks that against the functions that always parse.
- **The manifest** (`.devot-mirror.json` in the folder) maps note, attachment and notebook IDs to the paths Devot wrote, with each file's SHA-256 and size, and for a note what its file was written from (`source`, a hash of its update time, body version, title, status, tags, path and attachment paths; the body version moves with every write of the note, which an older edit synced in is, though it leaves the update time as it is; the note list reads it from the list's index, migration 0023) and the attachments it shows.
  Devot moves or deletes only paths the manifest lists, and only while they hold what it wrote; nothing else in the folder is ever changed.
  A folder that is not empty and has no manifest is used only after a confirmation (which writes an empty manifest); an empty folder or one with a manifest this library wrote is used at once.
  The manifest names the library that wrote it (a random ID kept in the mirror setting), so a folder another library mirrors (app data lost, a second Mac set up on its own) also asks first and starts from an empty manifest: the files it lists can be taken back but are never removed.
  A copy of the whole app data (moved to a new Mac, or restored to a second one) is the same library by any ID it keeps, the database's included: if both copies stay in use and mirror to one folder, each takes the other's new notes for its own deleted ones.
  A manifest from before manifests named their library is taken as this library's own only in the folder the mirror already uses, and gets its name.
- **Edited outside Devot:** before a file is rewritten, moved or deleted, what is on disk is compared with the manifest's hash.
  A file changed outside Devot is renamed in its folder to `<name> (edited outside Devot).md` (numbered when that is taken; the suffix is `strings::MIRROR_EDITED_SUFFIX`, used only by Rust), leaves the manifest, so it is never touched again, and Devot writes its own version.
  This holds for note edits, renames, moves, the Trash, purges, attachments and reconciles, and the files kept are listed in one notice until it is dismissed (Rust names the first 20 and counts them all, so a tool that changed every file keeps the status small).
  A file that already holds exactly what Devot would write is taken as Devot's; one replaced by a folder or a link is only forgotten.
- **Files the manifest does not list:** a batch's files reach the disk before the manifest that lists them, so a crash, a power loss or a quit in between leaves them unlisted (as does a folder chosen again after its manifest was lost).
  The plan takes such a file back rather than writing the note again under a numbered name: a file at the note's place that holds exactly the text rendered for it there makes the place the note's, and the operation goes without its text (Rust adopts the file).
  An attachment's copy likewise, when its bytes' SHA-256 (`mirror_hashes`, asked only when a file is in the way of a copy) matches the file.
  So the folder still imports without duplicates.
- **Names stay:** a note keeps its file, and a notebook its folder, while the name still fits (its title's file-safe stem, or the stem numbered; a folder's in any case or form of its accents, since moving files to another name macOS takes for the same folder leaves them where they are), so a change touches only the files it affects.
  A new name is the first of `Plan.md`, `Plan 2.md`, ... free in its folder, names compared by the rule export numbers them by (`nameKey`: what macOS takes for one name, whatever its case or the form of its accents, and, to be safe, a compatibility form; a folder keeps its name only across what macOS itself folds, `fileKey`, so `x²` renamed `x2` moves): not held by a file of the manifest (one moving away keeps its name taken until the next pass), nor given in the pass, nor anything else on disk (a folder Devot did not make may be shared, a file never).
- **Plan and executor:** the core worker plans (`planMirror`, a pure function of the database, the manifest and what is known of the disk, unit-tested in `tests/core/mirror.test.ts`): it asks for what it needs as it goes (note bodies without their Yjs state, `mirror_bodies`; attachment names, `mirror_files`; the hashes of attachments' bytes, `mirror_hashes`; disk states, `mirror_check`) and renders files in the worker, handing its event loop back between steps.
  Rust (`src-tauri/src/mirror/`) holds the folder and the manifest and runs each operation (`mirror_apply`: keep, forget, remove, write or move a note, copy or name an attachment, record a notebook's folder) after checking it again: plain visible paths inside the folder (notes `.md` and never in `attachments`, attachments `attachments/<name>`), never a file it did not write unless it holds exactly that, never through a link (every folder on the way must be a real one), never making the chosen folder.
  Each call opens the chosen folder once, by the path resolved when it was chosen and never through a link anywhere on it (a link there now pauses the mirror as a missing folder does), and finds every path in it folder by folder from that handle, so a check and the step that acts on it work in the same folders (see Security).
  One batch writes the folder at a time (a resume or a confirmation waits for it too), and it holds the mirror's state only to read the manifest and to record what it did, never across its file writes or attachment reads, so the status and the setting answer meanwhile; a batch under which the folder is turned off or chosen anew stops before its next operation, writes back its own folder's manifest and records nothing in the new state (`E_MIRROR_STALE`).
  Every file, the manifest and the setting included, goes through the app's one writer (`atomic_file.rs`, see Security): a new temporary file of a hidden random name, never opened where something already is, put in place.
  A new note file, an attachment's copy, a note moved to a new name, a file kept aside and a folder's first manifest go only where nothing is yet, so a file or a link that appeared there after Rust looked is never replaced or written through (the plan learns it is in the way; see Security for volumes that cannot rename that way in one step), and a move is whole: a file never stays under its old name too (a folder it cannot leave, locked say, fails the move), and one whose new text then cannot be written stays listed where it went, with what it holds (the manifest is written back and the core reads it again), so the next pass rewrites it there; only Devot's own file, found holding what Devot wrote just before, is replaced.
  Files are not flushed one by one (the database is the source of truth, and a file a crash left short is caught by the next reconcile, kept aside and written again), while the manifest is flushed after each batch.
  Attachment bytes go from the database to disk in Rust, never across IPC.
  A link to an attachment ID Devot never made (any UUID) is a link to no attachment and stays as written.
  Something in the way of an operation (a file that appeared, one changed meanwhile) makes the plan learn what is there and try again, three times per entry in a pass at most; a note whose file is rendered for a new place again and again (ten times in a pass) is left as it is until the next pass, logged as `E_MIRROR_UNSETTLED`, so it never holds up the others; an operation planned from a manifest Rust has moved past waits for the next pass, which reads the manifest again.
  A path that reads as `other` (a link, or under something that is not a real folder) makes the plan ask about each folder on the way: a notebook's folder that is no longer a real folder (a link or a file in its place) is lost and the notebook gets a new folder; while `attachments` is not a real folder, only attachment names are kept, as with Include Attachments off.
- **When it runs** (`createMirrorRunner`, started by the main window once it has restored its view): every write the mirror follows (notes, their tags, notebooks, tags and attachments; `observeWrites` wraps the worker's storage, so edits, renames, moves, tags, statuses, notebook changes, the Trash, restores, purges, batch actions, duplicates, notes from a selection or a template all count) starts a pass a second after the last one (five seconds after the first at most), never per keystroke: a note is saved 300 ms after typing pauses (longer for a large note).
  Passes run one at a time; each compares every note's `source` with the manifest and reads, renders and writes only notes that changed, so one edit writes one file and pinning writes none.
  A full reconcile, which also checks every manifest file on disk, runs when the mirror turns on, its folder or Include Attachments changes, it resumes, and two seconds after the window has restored at launch (also after a restore from a backup, which reloads the window).
  Notes another process writes are mirrored by the pass the window runs when it notices the database changed (`devot://db-changed`), or by the next launch's reconcile.
  A first mirror works in slices of 1,000 notes, written in batches of 200 operations (the manifest is written back after each batch that changed it); the 10,000-note benchmark (`tests/core/mirror.bench.test.ts`) keeps every stretch the worker computes under 200 ms and checks that an edit then writes one file.
  Quitting ends a running pass after its batch, so the manifest lists every file it wrote.
- **Include Attachments** (on by default): off, no attachment bytes are copied and the copies written before are removed (one changed outside Devot is kept); links still point at `attachments/<name>`, as in an export, and the manifest keeps those names.
  On again, the copies come back at the next reconcile under the same names, so no note's file changes.
- **Failures:** a folder that is missing (or has a link in its place) or cannot be written pauses the mirror with a code (Rust holds it; the main window shows a notice in the notice stack); a file or folder inside it that cannot be written (locked, say) only waits, logged, for a later pass.
  A manifest that could not be written back stays in memory and is written when the mirror resumes, never read again from the folder.
  A paused mirror checks its folder every 30 seconds and when the main window comes to the front (`mirror_open`) and resumes with a reconcile; Devot never makes the chosen folder itself.
  A manifest that cannot be read, or files without one, pause it too, until a folder is chosen again (or a missing manifest comes back), and the notice says so (`E_MIRROR_MANIFEST_MISSING`, `E_MIRROR_MANIFEST_INVALID`); so does a manifest another library wrote (`E_MIRROR_MANIFEST_FOREIGN`).
  Choosing that folder again asks first, then starts from an empty manifest, and the files that still hold what Devot would write are taken back (see above), so nothing is written twice.
  Logs carry codes and IDs only.
- **Setting and status:** the folder, Include Attachments and the library's ID live in `<app data>/mirror-settings.json`, a local preference like the editor settings (never synced, never in backups; read leniently).
  A file that cannot be read shows the mirror as off and is never written over: a change or a folder choice is refused with `E_MIRROR_SETTINGS_READ_FAILED`, the file is read again on the next call, and once a read works every window is told; a damaged file is copied to `mirror-settings.json.damaged` before the next change replaces it.
  After every change of the setting or of what the mirror shows (a pause, the size of the files in the manifest, the files kept) Rust sends `devot://mirror-changed` with the status and a revision to every window; the page's side shares `syncedStore.ts`.
  The size is unknown (null, and Settings shows none) until the folder's manifest has been read, and is sent once it is, even by a pass that writes nothing.
  `mirror_get`, `mirror_set`, `mirror_choose` (the folder panel over the calling window) and `mirror_confirm` are granted to the main and Settings windows; `mirror_open`, `mirror_check`, `mirror_apply`, `mirror_bodies`, `mirror_files` and `mirror_hashes` to the main window only.
  Turning the mirror off leaves its folder as it is; choosing that folder again later goes on from its manifest.
