# Performance

Part of the [architecture overview](../architecture.md).

- Budgets (the cost of native crash reports against the first two is still unmeasured on the app; see [Crash reporting and logs](quality.md#crash-reporting-and-logs)): launch to first editor paint < 700 ms; idle memory footprint < 200 MB; keystroke to paint < 8 ms on a 120 Hz display (one frame); full-text search over 10k notes < 50 ms; switching notes < 16 ms.
- In WebKit, `tests/ui/long-note-typing.spec.ts` keeps typing in a 200 KB note (prose, lists, tables, code blocks) within a looser budget for that engine on Linux: the median keystroke's editor work (CodeMirror's update and measure) under 25 ms and its key to the end of its frame under 80 ms; it stood at about 13 ms and 30 ms when added, of which the Markdown parser's incremental pass to the note's end is about 5 ms.
- Scrolling restyles nothing once a pane is past its top fade's depth (`size.scroll-edge`): the depth scrolled is clamped to it, written only when it changes, and set as a non-inherited `--scrolled-by` on the element whose fade it sizes, so the preview's blocks never inherit it.
  A value written on the panes every scroll event restyled the whole preview and held Split mode to a few frames a second on a 250 KB note; `tests/ui/glass-scroll-edge.spec.ts` holds it.
- The iPhone draws at its display's refresh rate: `CADisableMinimumFrameDurationOnPhone` in `src-tauri/gen/apple/devot_iOS/Info.plist` and `project.yml` (held by `tests/policy/iphone-info-plist.test.ts`) lifts the 60 Hz cap a ProMotion iPhone otherwise puts on Core Animation and the display link.
  The keyboard, system sheets and the web view's compositor transitions then run at 120 Hz; the page's `requestAnimationFrame` stays near 60 Hz, so motion drawn by script each frame does not gain from it.
  Judge the phone's smoothness on a release build on a device.
- A note left gives back what was kept for it, held by `tests/renderer/left-note-memory.test.ts`, `tests/core/preview-pieces.test.ts` and `tests/ui/preview.spec.ts`:
  - The worker keeps, besides the open note's preview pieces, pieces of at most 50,000 characters of source (`KEPT_CHARACTERS`; a tree takes about 100 bytes a character), so a long note left is rendered again when it opens (in V8, a 250 KB note left kept 25 MB of trees, now under 7 MB).
    When the preview closes (Edit or Write mode), the page tells the worker (`forgetShownPieces`), so the note it showed is kept within the same limit.
  - Write mode's table drawings live in the note's editor state and go with it; kept across notes, they held 11 MB after a 30-column, 800-row table was left.
    The note's base extensions hold them, so a switch to Edit mode and back draws no table again.
  - `@lezer/html`'s and `@lezer/xml`'s tag tokenizers keep the last input they read, and with it the last note with HTML (or an XML block), its syntax tree and what Write mode keeps by its text (about 10 MB in V8 for a 250 KB note); leaving a note, the editor parses a tag of no note's with each (`releaseParsedNote` in `editor/markdown.ts`).
  - The diagram frame, which holds the diagram libraries, is removed 30 s after no diagram is shown and no drawing is asked for (`preview/frameLifetime.ts`); drawings kept on the page come back without it.
    Write mode lets go of a diagram that scrolls out of view, so reading past a note's diagrams for 30 s also removes the frame; scrolling back to one the page no longer keeps (or after a resize or a theme change) loads the libraries again, which takes seconds.
  - Kept on purpose, each bounded by a count: the undo history of the last 10 notes left ([Data model](data-model.md)), the core's last 8 notes, the last 64 diagram drawings, and Write mode's last 200 rendered blocks (`trees`), 1,000 block heights (`heights`) and 500 inline drawings (`drawnInline`).
- The phase 2 harness measures them on macOS, in-app for typing latency, plus idle GPU power (`powermetrics`) with the transparent window against an opaque one.
- Core budgets, held by the benchmarks in `tests/core/*.bench.test.ts` (`pnpm test` and CI run them; `pnpm test:fast` leaves them out) against the test store on better-sqlite3, which runs the Rust store's SQL.
  Each holds on a developer machine and is stretched 5 times on a hosted CI runner (`tests/support/budget.ts`).
  Where the product has no number, the budget is a measured baseline with room.
  A growth check asks that four times the input take under 7 times as long (`tests/support/growth.ts`), so linear work passes and quadratic work fails on any machine.
  - Search over 10k notes (median, excerpts included): every query < 50 ms, whether words, a word start, a phrase, Chinese terms, tags, notebooks, statuses, exclusions or all of them combined, and each query typed on the way to two words; a scan of every body for text under three characters < 100 ms; a note's backlinks, a page of them or none, < 10 ms (the link index; the phrase search before it took 84 ms when every note holds a note link); saving an edit into the trigram and link indexes < 10 ms; counting 20 saved searches over the listed notes < 16 ms (one frame, on the UI thread).
  - Yjs on a 250 KB note: a remote keystroke or paste < 2 ms; a state vector and diff for sync < 2 ms; loading and encoding the whole state < 25 ms; merging two copies with 200 edits each < 60 ms; a body write of 20 changed lines, saved, < 100 ms; the line diff of a rewrite of every line of a 1 MB note < 50 ms.
    Linear: merging diverged copies, the line diff of a few changed lines, and the state's size against the edits typed.
  - Import: a Markdown folder with links, tags and images < 30 ms a note, linear in the notes, linear when every folder repeats the same names, and linear in thousands of folders (1,640 against 6,560 notebooks); a 600 KB file prepared < 3 s, linear in its length; HTML pages and bare links linear (`html-import`, `import` benches).
  - Link index: a note of 10,000 links saved < 150 ms; reading a body's links linear in its length.
  - Counting a note's words and characters (`noteCounts`, which the footer and Note Info share once per pause): linear in its length; on a 250 KB note of rich Markdown it took 23 ms in JavaScriptCore before the ASCII paths and takes 15 ms (`tests/core/note-counts.bench.test.ts`).
  - The list and links over 50k notes: the list's first 21 notes, templates left out, < 5 ms (a SQL `LIMIT` on the list's index; 148 ms when every note was read); the link targets of a note with 40 links < 10 ms (list rows read by ID; 160 ms); a two-character `[[` query that matches nothing < 20 ms (titles only; 208 ms when it scanned every body).
