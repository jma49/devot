# Performance

Part of the [architecture overview](../architecture.md).

- Budgets (the cost of native crash reports against the first two is still unmeasured on the app; see [Crash reporting and logs](quality.md#crash-reporting-and-logs)): launch to first editor paint < 700 ms; idle memory footprint < 200 MB; keystroke to paint < 8 ms on a 120 Hz display (one frame); full-text search over 10k notes < 50 ms; switching notes < 16 ms.
- In WebKit, `tests/ui/long-note-typing.spec.ts` keeps typing in a 200 KB note (prose, lists, tables, code blocks) within a looser budget for that engine on Linux: the median keystroke's editor work (the transaction, CodeMirror's update and measure) under 25 ms and its key to the end of its frame under 80 ms; it stood at about 13 ms and 30 ms when added, of which the Markdown parser's incremental pass to the note's end is about 5 ms.
  The same spec types a letter and Backspace at the top and at the end of a 600 KB note, in Edit and in Write mode, and holds the end within 1.5 times the top, for the editor's work and for the key to its frame, so no per-keystroke work may grow with the text before the caret.
  It types at a place only once the parser has drawn it and gone quiet: CodeMirror parses 100 KB past the view, so a first visit to the end parses the 500 KB before it, which took a whole round of keys on CI (in either mode) and is not a keystroke's cost.
  A jump into a long note's unparsed part (find, the outline, a link, the scroll bar) no longer waits for that worker: `editor/parseToView.ts` parses toward the view in 8 ms slices close together, hands the tree over once the view is reached, and goes on to 100 KB past it, where CodeMirror's worker then finds nothing left (#759).
  CodeMirror's worker alone parsed in 100 ms slices 100 to 500 ms apart, so the end of a 2 MB note stayed unstyled for about 1.8 s in Node and keys waited behind each slice; `parseToView.bench.test.ts` holds the time to styled within twice a whole parse.
  The one hold longer than a slice is the parser's last step, which builds the note's tree and finds its fenced code in one go (about 15 ms a megabyte, 60 ms at 4 MB in Node) and which CodeMirror's worker pays too; the bench holds the longest hold, at 1 MB and at 4 MB, within 40 ms beyond that step.
  Once caught up, a key at the end of a 4 MB note costs what it does in a note parsed whole (about 50 ms in Node, the parser's incremental pass); the bench holds the median within 1.5 times that.
  It pauses while changes come within 100 ms of each other: each change ends the parse under way, and the next starts over from its fragments at a cost that grows with the note, so slices between such keys would only add to them.
  The 1.5 times bound catches work of about half a keystroke; a smaller cost, such as the highlighting walk below, is held by its unit test.
  The editor's syntax highlighting (`editor/highlighting.ts`) highlights each top-level block in the visible ranges on its own, found from the range's start, because `highlightTree` from the root steps past every block before it (11,550 in a 600 KB note, about 2 ms a keystroke at the end in WebKit); `highlighting.test.ts` holds a range at the end to the steps of one at the top.
- Opening a note does not wait for the note left to be saved: its edits are in the core already, and the open asks the core to save once the note has opened (`useOpenNote.ts`).
  With Tauri storage that save still turns the note into JSON for `note_put` on the page's main thread (`storage/tauri.ts`), so that cost comes after the open instead of before it, and is not removed.
  The core sends a note's state as it read, sent or last saved it while nothing has changed it since, instead of encoding it again (`Live.state`); only a note in use, the notes an editor holds and the note left last keep that copy (see the notes in memory below).
  Leaving a note with no undo history keeps nothing, and one with history encodes its replica after the next paint (or a second later in a hidden window, which paints nothing), not in the switch (`editor/undo.ts`).
  Shown again with the same insertions and the same text, its history is restored without a second Yjs document; the text is compared too, because a deletion does not move the state vector.
  `tests/renderer/note-switch.bench.test.ts` holds these on a 2 MB note typed over several sessions: about 85 ms to leave and 550 ms to come back with history, and 85 ms for the core's open, before.
- Scrolling restyles nothing once a pane is past its top fade's depth (`size.scroll-edge`): the depth scrolled is clamped to it, written only when it changes, and set as a non-inherited `--scrolled-by` on the element whose fade it sizes, so the preview's blocks never inherit it.
  A value written on the panes every scroll event restyled the whole preview and held Split mode to a few frames a second on a 250 KB note; `tests/ui/glass-scroll-edge.spec.ts` holds it.
- The preview draws a diagram (Mermaid, PlantUML, Markmap) only while it is within one screen of the view, above or below it (an `IntersectionObserver` on the preview pane, `preview/islands.ts`), and keeps a drawing once made; exports and printing draw every diagram themselves (`exporter.ts`).
  Drawings that land in the same frame go into the page together, with one layout read before and after and one scroll-sync update, instead of one relayout of the whole preview per diagram (#717: a 1 MB note with about 170 diagrams kept WebContent busy for 2.5 minutes).
  A diagram not drawn yet reserves `size.diagram-placeholder`, or the height it was last drawn at for its kind, width and source (the last 500 kept).
  One that lands above the view moves the scroll position by its growth (one across the view's top edge by the share of it above that edge), so what is in view stays put; the move goes through the preview's scroll pane (`shiftScroll`), so synced scrolling does not take it for the user's.
  A restored preview position is a pixel offset, so after a relaunch it can sit off by the difference between the reserved heights above it and the drawn ones.
- In WebKit, `tests/ui/split-typing.spec.ts` keeps typing in Split view in a 200 KB note with a footnote and a reference definition in every section within 150 ms from the key to the end of the frame in which the preview shows it (the median keystroke).
  It stood at about 1 s on a loaded developer machine, and at about 115 ms on the same machine once definitions no longer made the note one piece; what remains is mostly the page's layout of the whole preview and the scroll sync's measure of its blocks.
  The scroll sync measures only the preview's blocks around the line or offset it looks for (`previewScrollPane` in `src/renderer/src/preview/scrollSync.ts`): it finds them by a search over the preview's pieces, by their first lines or by their first blocks' positions, and maps a place exactly as measuring every block would, as long as each piece reaches past every block before it somewhere (in line and offset), which a preview's flow of blocks does.
  What it measured inside a piece holds until the preview is laid out anew (an image or a diagram, a new width, a height that changed without a render); where a piece sits is read again after each render, and a kept piece's last block is read again too, so a change inside it that came with a render is not missed.
  Pieces the preview builds later (see below) show no blocks until they are built, so it maps the lines they hold to the bottom of what is built, and building them keeps what it measured of the pieces before them.
  The price is that scrolling reads a few boxes a step near where it goes (about 200 a step through a 600 KB note whose images and diagrams are still loading), where measuring every block read none until the next render.
  It measured every block after each edit that changed the line count or the height: about 6,000 box reads a keystroke in a 200 KB note and 61,000 (about 100 ms in WebKit) in a 2 MB one; `tests/ui/split-measure.spec.ts` holds a keystroke under 150 (it reads about 85 in a 2 MB note).
  The page's watchers of the whole window (`dialogMotion.ts`, `sidebarSurround.ts`) pass over changes inside the preview, so a render looks for no dialog in its new blocks and measures no sidebar.
- The live preview renders a note in pieces (`src/core/preview/blocks.ts`), cut at blank lines before a new top-level block, and renders again only the pieces whose text changed; the page patches only the pieces whose key changed (`src/renderer/src/preview/dom.ts`).
  Pieces are kept within `KEPT_CHARACTERS` besides those the note shows (see below), so a piece the note shows is never rendered again for the cache's sake.
  Link reference and footnote definitions reach across pieces without making the note one piece (`definitions.ts`): each piece is parsed with the labels the note defines seeded into the Markdown parser, and gets the definitions it uses from other pieces as tree nodes, so its links and calls come out as the whole note's would.
  A piece's key holds the definitions it was rendered with, so changing a definition renders again the pieces that use it.
  Footnote calls are numbered across the pieces, and the list of notes is one last piece of its own (`footnotes.ts`), sent again only when a note in it, its number or its count of calls changed.
  Each note in that list counts its lines and offsets from its own start, and the piece gives where each note starts (`parts`), so text added above a note moves it on the page without the list being sent again.
  Headings in notes are named after every other heading, as the whole note's render names them, and their ids are part of the list's key.
  `tests/core/preview-pieces.bench.test.ts` holds an edit in the middle of a 250 KB note with footnotes and reference definitions under 30 ms in the core (about 340 ms when such a note rendered whole); `tests/core/preview-pieces.test.ts` checks that the pieces together render as the whole note does.
  After an edit, the worker cuts the note again only from the piece before the first that changed until a cut meets a piece whose text runs unchanged to the end (`createBlockSplitter`), and the pieces it kept take their keys, task counts, line counts and heading slugs from the render before, so only the edited piece is read whole.
  The pieces renderer and the task and line counts read one shared cut (`shareSplitter`), and the cut compares the pieces it keeps as slices, which V8 compares as memory.
  Each edit still does a little work for every piece (keys, cache lookups, heading ids, the list it sends back), so its cost is far smaller but still grows with the count of pieces: on a loaded machine, about 5 ms at 250 KB, 8 ms at 1 MB, 9 ms at 2 MB and 15 ms at 5 MB, against 5, 9, 12 and 47 ms before the shared cut.
  The same benchmark holds an edit in the middle of a 2 MB note's live preview under 25 ms and of a 5 MB note under 30 ms in the core.
- A render builds on the page at once the pieces it changed up to `FIRST_CHARACTERS` (20,000 characters of source) past the last piece already built, and leaves the rest waiting (`patchPieces` with `defer`, `buildPending` in `src/renderer/src/preview/dom.ts`); the preview builds them in order in tasks of about 8 ms after it.
  Pieces still waiting are always the last ones, so what is built reads as the note does.
  What needs more of the note builds it first: a scroll-sync or outline jump to a line builds up to that line and a screen past it (nothing when that much is built), a restored scroll position builds until the preview is tall enough, and find, select all (the menu item or Cmd+A), copy and a link to a heading build all of it.
  Diagrams and copy buttons are added for what is built at once, every 250 ms while the build goes on, and when it ends.
  Opening a 2 MB note thus builds about 1% of it in the task that shows it (in happy-dom, about 30 ms instead of 3.4 s); `tests/renderer/preview-open.bench.test.ts` holds what that task builds from growing with the note.
  Another note opened in the preview replaces what the last one showed instead of being patched over it, and the worker is asked for all its pieces; the preview reads the note's id with its text when a render starts, so a text that arrives after the switch is not patched over the note before.
- Typing in Split view renders no React component: the preview follows the editor's text store itself (`textStore.ts`) and reads the text only when a render starts, so renders a newer one replaces never read it.
  Copy buttons render only when the list of code blocks changes, and that list is read once for each piece the page builds (a piece left waiting is read when it is built).
  On the page, offsets in the note (`data-task-at`, `data-image-from`, `data-image-to`) count from their piece, and `noteOffset` adds the piece's start when one is read, so typing changes no attribute after the edit; source lines stay the note's, which scroll sync reads.
  A piece built later is built the same way: an edit above it moves only its start until then, and building it shifts its lines alone.
  `preview/dom.test.ts` holds the offsets read from pieces built after an edit above them to a whole build's, and `preview/Preview.test.tsx` a note switch and typing through the text store while pieces still wait.
  `tests/ui/render-cost.spec.ts` holds typing in Split view to no render of the preview or its copy buttons and at most one media query per key (on a 250 KB note with 468 code blocks there were about 470 copy-button renders and 2,500 media queries per key before).
- The iPhone draws at its display's refresh rate: `CADisableMinimumFrameDurationOnPhone` in `src-tauri/gen/apple/devot_iOS/Info.plist` and `project.yml` (held by `tests/policy/iphone-info-plist.test.ts`) lifts the 60 Hz cap a ProMotion iPhone otherwise puts on Core Animation and the display link.
  The keyboard, system sheets and the web view's compositor transitions then run at 120 Hz; the page's `requestAnimationFrame` stays near 60 Hz, so motion drawn by script each frame does not gain from it.
- On the iPhone's native screens a note's push starts in the frame after the tap, and the cover over a pushed note is up at most 400 ms ([iPhone screens](iphone-screens.md#row-to-editor)).
  Switching notes, the budget above, covers `editor.show`: the page swaps the note into its one editor rather than building one.
- The iPhone's first native list paints within 400 ms of the process starting: it is one page of 200 rows read Rust-direct, before the page has started, with excerpts filled in as they come ([iPhone screens](iphone-screens.md#lists)).
  A list scrolls its rows without reading the database again; it asks for the next page near its end and for excerpts at most 60 at a time.
  The app's idle memory with the native lists stays under 200 MB.
  Judge the phone's smoothness on a release build on a device.
- A note left gives back what was kept for it, held by `tests/renderer/left-note-memory.test.ts`, `tests/core/preview-pieces.test.ts` and `tests/ui/preview.spec.ts`:
  - The worker keeps, besides the open note's preview pieces, pieces of at most 50,000 characters of source (`KEPT_CHARACTERS`; a tree takes about 100 bytes a character), so a long note left is rendered again when it opens (in V8, a 250 KB note left kept 25 MB of trees, now under 7 MB).
    When the preview closes (Edit or Write mode), the page tells the worker (`forgetShownPieces`), so the note it showed is kept within the same limit.
    A render still under way when the preview closes keeps its pieces within that limit too.
    The worker remembers the last rendered version of each footnote, to tell whether the list of notes changed (at most 2,000, `KEPT_NOTE_VERSIONS`); a version holds the note's text, so it goes when no kept piece defines that note.
  - The core keeps a note in memory as its Yjs document: its record holds neither the body nor the stored state (`HeldRecord`), only the state's byte length for the save delay.
    An encoded state, a second copy of the note, stays only with a note in use, the notes an editor holds and the note left last, so switching back to that one sends it without encoding (`keepsState` in `notes/memory.ts`).
    The note left last is the one whose last hold went last, shown or not: an open overtaken by another, or a body opened ahead and not used, can take its place, so switching back to the note shown before encodes its state again, which costs time and loses nothing.
    A save encodes the state once, only when it writes the body, and only a note that keeps a state keeps that one; a save of the fields alone neither encodes it nor drops the one kept.
    Four rich notes of 1 to 5 MB held 14 MB beyond their documents before; `tests/core/note-memory.bench.test.ts` holds the extra under 8% of their text, and `tests/core/note-open.test.ts` which notes keep an encoded state.
  - Write mode's table drawings live in the note's editor state and go with it; kept across notes, they held 11 MB after a 30-column, 800-row table was left.
    The note's base extensions hold them, so a switch to Edit mode and back draws no table again.
  - `@lezer/html`'s and `@lezer/xml`'s tag tokenizers keep the last input they read, and with it the last note with HTML (or an XML block), its syntax tree and what Write mode keeps by its text (about 10 MB in V8 for a 250 KB note); leaving a note, the editor parses a tag of no note's with each (`releaseParsedNote` in `editor/markdown.ts`).
  - The diagram frame, which holds the diagram libraries, is removed 30 s after no diagram is shown and no drawing is asked for (`preview/frameLifetime.ts`); drawings kept on the page come back without it.
    Write mode lets go of a diagram that scrolls out of view, so reading past a note's diagrams for 30 s also removes the frame; scrolling back to one the page no longer keeps (or after a resize or a theme change) loads the libraries again, which takes seconds.
    The frame loads each diagram engine only when a diagram needs it, so the first Mermaid diagram parses the frame and Mermaid (about 5.2 MB) instead of every engine at once (9.3 MB); `tests/scripts/mermaid-frame.build.test.ts` keeps a size budget.
  - Kept on purpose, each bounded by a count: the undo history of the last 10 notes left ([Data model](data-model.md)), the core's last 8 notes, the last 64 diagram drawings, and Write mode's last 200 rendered blocks (`trees`), 1,000 block heights (`heights`) and 500 inline drawings (`drawnInline`).
- `tests/scripts/startup-chunks.build.test.ts` holds what a window parses before its first paint and what the core worker parses before `init` answers, each under a byte budget.
  The main page loads no Markdown parser and no server renderer, as the core worker parses and converts Markdown.
  The core worker loads sync, the Markdown mirror, import, export and the AI service on their first use.
  A stop, or a later start, made while sync's code loads wins, and starts made while the mirror's code loads make one mirror (`lazyStart.ts`).
  Once the window is idle, warm-up renders a short sample with only the code languages, math and emoji that the open note and the first 20 listed notes use, so the next note opened from the list opens warm without a fixed set of grammars kept in memory.
- The phase 2 harness measures them on macOS, in-app for typing latency, plus idle GPU power (`powermetrics`) with the transparent window against an opaque one.
- Core budgets, held by the benchmarks in `tests/core/*.bench.test.ts` (`pnpm test` and CI run them; `pnpm test:fast` leaves them out) against the test store on better-sqlite3, which runs the Rust store's SQL.
  Each holds on a developer machine and is stretched 5 times on a hosted CI runner (`tests/support/budget.ts`).
  The real builds (`*.build.test.ts`) run before the benchmarks, never beside them.
  A check of work that writes to the store is timed in CPU time, as the store syncs each commit to disk and a hosted runner's shared disk made the wall clock vary tenfold; where it can, a check compares with work measured moments before on the same machine instead of a fixed number (a 1 MB save against the re-index it skips).
  Every CI run lists the time checks nearest their limits in the unit job's log and summary (`tests/support/budget-report.ts`).
  Where the product has no number, the budget is a measured baseline with room.
  A growth check asks that four times the input take under 7 times as long (`tests/support/growth.ts`), so linear work passes and quadratic work fails on any machine.
  - Search over 10k notes (median, excerpts included): every query < 50 ms, whether words, a word start, a phrase, Chinese terms, tags, notebooks, statuses, exclusions or all of them combined, and each query typed on the way to two words; a scan of every body for text under three characters < 100 ms; a note's backlinks, a page of them or none, < 10 ms (the link index; the phrase search before it took 84 ms when every note holds a note link); saving an edit into the trigram and link indexes < 10 ms; counting 20 saved searches over the listed notes < 16 ms (one frame, on the UI thread).
  - Yjs on a 250 KB note: a remote keystroke or paste < 2 ms; a state vector and diff for sync < 2 ms; loading and encoding the whole state < 25 ms; merging two copies with 200 edits each < 60 ms; a body write of 20 changed lines, saved, < 100 ms; the line diff of a rewrite of every line of a 1 MB note < 50 ms.
    Linear: merging diverged copies, the line diff of a few changed lines, and the state's size against the edits typed.
  - Import: a Markdown folder with links, tags and images < 30 ms a note, linear in the notes, linear when every folder repeats the same names, and linear in thousands of folders (1,640 against 6,560 notebooks); a 600 KB file prepared < 3 s, linear in its length; HTML pages and bare links linear (`html-import`, `import` benches).
  - Link index: a note of 10,000 links saved < 150 ms; reading a body's links linear in its length.
  - Counting a note's words and characters (`noteCounts`, which the footer and Note Info share once per pause): linear in its length; on a 250 KB note of rich Markdown it took 23 ms in JavaScriptCore before the ASCII paths and takes 15 ms (`tests/core/note-counts.bench.test.ts`).
  - A save of a 1 MB note, its title or Markdown changed, < 30 ms (median of six): it marks the note stale for search instead of re-indexing it (about 72 ms before, schema v29).
    The first search after it, with a word of three characters or more, re-indexes the note first: < 150 ms (about 50 ms here), the cost moved off the save.
    A search with only filters or shorter text reads no index and catches nothing up.
  - The list and links over 50k notes: the list's first 21 notes, templates left out, < 5 ms (a SQL `LIMIT` on the list's index; 148 ms when every note was read); the link targets of a note with 40 links < 10 ms (list rows read by ID; 160 ms); a two-character `[[` query that matches nothing < 20 ms (titles only; 208 ms when it scanned every body).
