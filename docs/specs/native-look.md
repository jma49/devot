# Native look

Part of the [architecture overview](../architecture.md).
Part of the [design system](design-system.md).

- The window is transparent with the `underWindowBackground` window effect behind all of it, always active (also while the window is inactive; the system's glass under the Glass sidebar follows the window's active appearance instead, so each main window keeps that appearance, `native::macos::keep_glass_active`, and its traffic lights stay coloured as a result); the page's root is transparent and each region paints a wash over the material: the sidebar `color.surface.sidebar`, the list `color.surface.list-wash`, the editor pane `color.surface.editor-wash` (CodeMirror's own background is transparent).
  The toolbar has no wash of its own; pop-ups and menus stay opaque (`color.surface.popover`).
- **Interface style** (Settings > Appearance > Interface style: Glass, the default, or Classic, an opaque window; stored as `sidebarMaterial`, true for Glass): with Classic, the main window drops its effect, the page's root behind every pane paints `color.surface.window` and the regions their opaque surfaces (`color.surface.sidebar-opaque`, `color.surface.list`, `color.surface.editor`), so nothing in the window is see-through.
  With Glass, Settings > Appearance > Glass Transparency (`windowTransparency`, a whole number from -100 to 100, default 0: the design washes) reaches the page as `--window-transparency`; app.css works each wash's alpha out from it (`color(from ...)`, 1 - (1 - a) x (1 + level / 100), clamped: -100 opaque, 100 twice as clear), so the tokens keep the design alphas.
  The slider is shown only for Glass, with its value beside it (0 is the design washes).
  The slider stores its value at most every 100 ms while it is dragged, and the last value when it stops (`settings/draggedNumber.ts`).
  The choice is stored with the editor settings (`sidebarMaterial` in `editor-settings.json`, same validation, same `devot://editor-settings-changed` event), so it follows a change in every window at once; the main window's root element carries `data-sidebar-material="on|off"` (`src/renderer/src/sidebarMaterial.ts`).
  Rust builds the main window with the configured effect only when the material is on, and hands the page the settings it was built with in an initialization script (`window.devotInitialEditorSettings`, which the CSP does not govern), so the first paint matches the window (the editor's font too).
  That script carries the settings read at launch into every load, so the page also keeps the newest snapshot it has confirmed in `sessionStorage` and, after a reload (a backup restore reloads it), starts from that one when it is newer.
  After a change the page calls `sidebar_material_sync` (main window only, no arguments), which removes or restores the effect to match the stored setting through Tauri's `set_effects` (AppKit work on the main thread) and answers once the main thread has applied it (`src-tauri/src/sidebar_material.rs`).
  The order keeps the desktop from showing through a bare wash: turning it off paints opaque first and asks Rust once that has been painted; turning it on asks Rust first and turns translucent only after Rust answers that the window shows the material (on a failed answer, or when Rust has stored a later change to off already, the regions stay opaque).
  Rust applies stored revisions in order and leaves the effect alone when another setting changed.
  The window itself stays transparent (that is fixed when it is built): an opaque window removes the material view, which is what costs GPU time, and paints every pixel.
- Overlay title bar: traffic lights in the sidebar's top bar, a unified toolbar over the list and editor.
- macOS type scale: body 13 pt, captions 11 pt, sidebar rows 28 px.
- The menu bar and context menus are native (Tauri menus).
  Settings live in the app menu.
- Context menus are tables of entries (`src/renderer/src/contextMenu.ts`): each entry has an action, a catalog label (fixed or chosen per target), an optional accelerator, and optionally a `shown` or `checked` rule.
  Each menu is built once per window with every item it can show; before it pops up, the same native menu shows, hides, relabels and checks its items for the right-clicked target, and a picked item acts on that target, never on the open note (the note menu's target is every selected note when the right-clicked row is one of them; see Multiple selection).
- The note context menu (`src/renderer/src/noteMenu.ts`): its shortcuts work only while the note list has focus and act on the row that has the keyboard (a right-click focuses its row, a filter can hide the open note): on every selected note while several are selected (see Multiple selection), otherwise on that row's note alone.
  When the row that has the keyboard leaves the list while the view stays the same (Move to Trash from the keys, the menu or the palette, Delete Permanently or Restore in the Trash, a move out of the notebook, a change the filter hides), the open note's row takes the keyboard if it is still listed; otherwise the next row (the previous one at the end) takes it and opens (unless another note, hidden by the filter, is open), and an empty list keeps it itself (arrow keys and `/` work there), so the list's keys go on working.
  A row whose focus went elsewhere first (a click on a toolbar button or on blank space) hands nothing on, and switching views opens no note.
  Copy items write through the `clipboard_write_text` command, because WebKit lets a page write the clipboard only during a gesture in the page, and a native menu click is not one.
- The note context menu also opens Revision History… (Option+Cmd+Y, also in the View menu).
- **Multiple selection** (`src/renderer/src/listSelection.ts`, `SelectionSummary.tsx`, `src/core/batch.ts`): in any note list (the library, search results, Templates, the Trash) Cmd-click adds a note to the selection or takes it out (the clicked note becomes the anchor), Shift-click selects the notes from the anchor to the clicked one, Shift+Up and Shift+Down move the far end of that range, Cmd+A selects every note listed (the registry's `list.*` commands; in the editor Cmd+A stays Select All for the text) and Escape goes back to the open note alone.
  The listbox is `aria-multiselectable` and each selected row `aria-selected`.
  The open note stays open while it is selected (when it leaves the selection, the anchor opens); a plain click, an arrow key, opening a note from anywhere, Next, Previous, Back, Forward or Return on a row show one note again, from the open note, and another view starts without a selection.
  With two or more selected, the editor pane shows a summary instead of the editor: how many, their titles (eight, then a count), and buttons for every batch action: Move to Notebook… (the Move dialog), Pin or Unpin (Unpin when all are pinned), the status pop-up (Mixed while they differ), the tags any of them has (removing a chip takes it off all; Add Tag puts it on all), Copy Note Links and Move to Trash.
  In Templates the summary has no status or tags (a template's own are not used); in the Trash it offers Restore and Delete Permanently (which asks first, with the count).
  The same actions come from the list keys (M, P, Cmd+C, Cmd+Delete), the status keys, the palette (the note commands relabelled for the selection, plus Add Tag to Selected Notes… and Remove Tag from Selected Notes…, which open a tag picker) and the note context menu: on a selected row it acts on the whole selection, with plural labels, a Status submenu (checked when all share one) and the tag items, and without the items for one note (Revision History, Duplicate, Copy Note URI and ID, and the export and print items); on any other row it acts on that note only and leaves the selection alone.
  Copy Note Links writes one link per line through `clipboard_write_text`, which takes as much text as a note may hold (`src/renderer/src/clipboard.ts`: longer text goes through the page's clipboard API, which only a click or a key in the page allows); a copy that fails (links, a URI or an ID) shows a notice with its code.
- **Batch changes** (`applyBatch` in `src/core/batch.ts`): one change (notebook, status, pin, add or remove a tag, trash, restore, purge) is applied note by note through the note and tag services, each note written before the next, so every note gets its own HLC and its own history event, never one SQL update for all.
  Every note named gets the write, even one that seems to have the value already (the lists may not have caught up with a change just made).
  A note that fails (deleted meanwhile, its write refused) does not stop the rest; the window logs `W_BATCH_FAILED` with the count and the first code, and a notice in the notice stack, with the other notices (not above the editor), says how many notes could not be changed.
- **Dragging notes:** a row drags the whole selection when it is selected, else itself (the payload is the note IDs, one per line).
  Dropped on a notebook they move there, on a tag they get it, on a status they get it, on the Trash they move to the Trash; the row under them shows as a drop target.
  Templates drop only on notebooks and the Trash; the Trash's rows do not drag.
- Quick tagging (`src/renderer/src/QuickTagPopover.tsx`, `quickTag.ts`): the command `note.quickTag` (T, rebindable; only outside the editor and text fields, and only with one note open) or a click on "+ Tag" opens a pop-up at the tag row: a field, matching tags with counts (recent first when empty; recents are tag IDs in this device's localStorage, never synced or logged), "Create …" for a new name, and swatches for the tag being created.
  Return applies and stays open, Escape closes and gives the keyboard back.
  On the phone the "+ Tag" chip opens the same list in a sheet.
- The tag context menu (`src/renderer/src/tagMenu.ts`, drawn by `TagMenuPanel.tsx`; a menu of our own, since a native one cannot show swatches: arrow keys, Return, Escape, focus back, click outside, kept inside the window): Tag Settings… (name and colour), a row of colour swatches (None, the palette, and last a Custom Color swatch opening `ColorPicker.tsx`), Filter by Tag (a check item; toggles the filter), Copy Tag ID (through `clipboard_write_text`) and Delete Tag (Delete or Backspace on the focused row; it asks first, since the tag leaves every note; hidden in a workspace).
  Renaming in place is F2 on the row, and the keyboard goes back to the row afterwards.
  A coloured tag shows a dot in place of its sidebar icon and on its chips; the dot is named after its colour for assistive tech.
  A context menu entry may hold a submenu, whose items are relabelled and checked per target like the rest.
- The image context menu (`src/renderer/src/imageMenu.ts`), for an image in the preview or under its line in the editor: Copy Image and Save Image As… (attachments only) and a Size submenu of check items (Auto, Small, Half Width, Full Width; shown when the size can be set).
  Copy Image calls `image_copy`, which reads the attachment by ID and puts it on the general pasteboard as PNG and TIFF data (decoded off the main thread by `native::macos::pasteboard_image`, a PNG keeping its own bytes; only the pasteboard write runs on the main thread).
  The decode runs in an autorelease pool of its own, so AppKit's temporaries (decoded copies of the image) are freed when it returns, not when its blocking-pool thread ends seconds later (`tests/main_thread.rs` checks that the thread's exit frees nothing more).
  An image whose header gives it more than 100 megapixels (`MAX_COPY_PIXELS`, twice a 48-megapixel photo) is refused with `E_IMAGE_TOO_LARGE` before anything is decoded: its decoded copies would take gigabytes, and a file of a few MB can ask for that.
  Save Image As… writes the bytes as they are, at any size: it calls `image_save`, which shows the system save panel over the window (the attachment's name with the extension for its type) and writes the bytes beside the chosen path before renaming them over it.
  The path is written as chosen: the panel asked before replacing a file there, so Rust never adds an extension that could replace another file.
  The page names attachments by ID only, never a path.
  The same actions are registry commands (`image.copy`, `image.save`, `image.size*`), which the palette offers while the cursor is on a line with an image.
- Status shortcuts (`src/renderer/src/statusKeys.ts`): Control+Command+1 to 5 set the open note's status (none, active, on hold, completed, dropped) anywhere in the window, also while typing, but not over a sheet.
  They are the registry's `status.*` commands (`window` scope), so the palette lists them while a note is open and Settings > Keyboard Shortcuts can change them.
  Unit tests check that they take no key another command, a context menu, the menu bar or macOS already uses.
- Notebook drag and drop (`src/renderer/src/Sidebar.tsx`): dropping a notebook on the top quarter of another puts it before that one, on the bottom quarter after it (after an open notebook's sub-notebooks too; the top quarter of a first sub-notebook puts it first inside), in the middle inside it; a line on the row's edge shows where it will go (after an open notebook: under its last visible sub-notebook, at its indent).
  A drag that ends anywhere, dropped or cancelled, clears the drop marks.
  A notebook never drops on itself or among its own sub-notebooks.
  The Notebooks header puts it first at the top level.
  A note dropped anywhere on a row goes into that notebook.
- The notebook context menu (`src/renderer/src/bookMenu.ts`): New Notebook Inside, Rename (Return or F2), Move Up and Move Down (Option+Up and Option+Down; when there is a sibling that way; the way to reorder without a drag), Move to Top Level (nested notebooks only), Allow AI Access (a check item) and Delete Notebook (Delete).
  The right-clicked notebook is outlined while its menu is open and stays unselected.
  A notebook with AI access on shows a small sparkle before its count while its row is under the pointer, has the keyboard, is selected or has its menu open; at rest the sparkle takes no room, so the name gets it, and its accessible name stays.
  Every action of a notebook or tag row has a keyboard route: Shift+F10, the menu key or Control+Return (the registry's `sidebar.rowMenu`, scope `sidebar`) opens the focused row's native menu under the row, where the arrow keys and Return pick (Allow AI Access, the exports, New Notebook Inside, the tag Colour submenu and the rest); Rename, Move Up and Move Down and Delete also have keys of their own.
  The menu key is a named key (`ContextMenu`) of the shortcut notation, so Settings > Keyboard Shortcuts can record it.
- **Sidebar sections and footer** (`Sidebar.tsx`, `sidebarSections.ts`, `SidebarFooter.tsx`): Notebooks, Status, Tags and Agents have one header shape: the title on the left; on the right the section's own actions (search, add) and then its disclosure chevron, shown while the header is under the pointer or has the keyboard inside it.
  A collapsed section keeps its chevron shown, so its state shows.
  Each section folds, and each window remembers which are folded in local storage (`devot.sidebarCollapsed.<window label>`); naming a notebook opens a folded Notebooks section.
  The footer is one button that opens the backup and mirror status: it reads the last save time ("Saved at 11:37:02") once a note was saved in this window, else the panel's name.
- **Row time** (`relativeTime` and `rowDate` in `src/renderer/src/format.ts`): with Note List Dates set to Relative, a list row and a board card say how long ago the note changed, "Just now" under a minute, then "7 min ago", "3 hr ago", "3 days ago" (the locale's short units in the catalog's `time.ago`), and the date after 30 days; the time is secondary text, and its tooltip is the full date and time.
- **Untitled notes in lists** (`headline` in `src/core/extract.ts`, `src/renderer/src/headlines.ts`): a note with no title shows the first line of its body as its row title (and in the multiple selection's list), so a list of new notes can be told apart.
  The line is the first one with readable text after front matter, as the preview shows it (heading, list, quote and task markers and link syntax out; a line with only an image is skipped), cut to 120 characters.
  It is a display fallback only: the title stays empty (the title field shows its placeholder, links, exports and the Markdown mirror still name the note Untitled), and it is never written to storage.
  The list does not read bodies: the rows that render ask the core (`NoteService.headlines`, which reads pending edits too and works for Trash notes) for the notes they show with no title, only the start of each body is read, and the answer is kept until the note's `updatedAt` changes (at most 2000 are kept).
  A note with no text shows Untitled.
  Return in the title field moves to the body (not the Return that picks an input method's candidate).
- **Duplicate** (`duplicateNote` in `src/core/duplicate.ts`): the copy has the original's body (as Yjs state), notebook, status and tags, and the title "<title> copy" (the suffix comes from the message catalog; an untitled note's copy stays untitled, and a title is cut to the title limit).
  It is not pinned: a pin is a place in the list, and two pinned twins would crowd it.
  A tag that cannot be put on the copy is left off and logged by code; the copy is still made.
- Note list order (`src/core/sort.ts`, `src/renderer/src/noteSort.ts`): a sort button in the list header opens a native pop-up under it with six check items (title A to Z or Z to A; date updated or date created, newest or oldest first) and Use as Default.
  The order is a view preference kept in the webview's local storage, never in the database, so it does not sync.
  Each library view keeps its own order: All Notes, each notebook, and each filter (a filter is keyed by itself, whatever notebook narrows it).
  Views without their own order follow the default (newest updated first until the user picks Use as Default, which makes the current view's order the default and checks the item while a view follows it).
  Pinned notes keep their own section, sorted the same way.
  Titles compare with `Intl.Collator` (numbers by value, case and accents ignored) in the macOS preferred languages, then the UI locale, so Chinese titles sort by pinyin for a Chinese-language system; untitled notes come last and equal titles put the newest updated first.
  Search results stay in relevance order, with Relevance as a seventh item, until the user picks another order (remembered for search results only; Use as Default is not offered there).
  The Trash keeps its deletion order and has no sort button.
- Focus mode (the toolbar button or Shift+Cmd+D) hides the sidebar and the note list; each window remembers it.
  Turning it on with the keyboard in a hidden area moves the keyboard to the editor (see Keeping the keyboard on the page).
- **Board layout** (`src/renderer/src/NoteBoard.tsx`, `board.ts`): a List / Board control at the end of the list's filter row (and Show as Board or Show as List in the palette, `view.toggleBoard`) shows All Notes, a notebook (a workspace too), Pinned or a tag as five columns, one per status (No Status, Active, On Hold, Completed, Dropped), each with its count; a status filter is one column already, and search results, Templates and the Trash have no board.
  The choice is kept per view (the list's view key: filter and notebook) in the window's last state; nothing else is stored.
  Every column shows, empty ones too, and takes drops; Settings > General > Dropped Column on Boards (`boardDropped`, an editor setting, on by default) turned off leaves the column and its notes off boards.
  A card shows the title (an untitled note's first line), the date and a dot per tag (the tag names are in the card's accessible name, as hidden text); clicking one opens it, and the cards of a column keep the view's order (pinned first).
  There is no manual order, so a drop within a column changes nothing.
  Each column is a listbox; the selection is the list's (`listSelection.ts`, the cards column by column as its order), so Cmd-click, Shift-click, Shift+Up and Down, Cmd+A and Escape work as in the list, and the note keys, the context menu and Return act as there.
  The arrow keys move up and down a column and sideways to the same place in the nearest column with cards.
  A card drags the selection when it is selected, else itself, with the list's payload (so the sidebar's notebooks, tags, statuses and Trash take it too); dropped on a column, the notes get its status.
  Control+Command+Right and Left (`status.next` and `status.previous`, in Settings > Keyboard Shortcuts, the palette, and the note menu on a board) move each selected card, or the focused one, to the next or previous column; a card in the last column stays.
  Status changes go through the note service as a batch (`applyBatch`), so sync, history and AI tools see ordinary status events; a moved card shows in its new column at once.
  Each move (a drop or a key press) is one step of the board's own undo history (`createMoveHistory`, the last 50 moves of each board view, kept in memory for the last 20 boards shown, so it lasts across a visit to another view): Cmd+Z and Shift+Cmd+Z while a card or column has the keyboard take the last move back or make it again, each note whose status changed since left alone.
  A move whose write failed keeps only the notes that were written, and a step that changes nothing any more is passed over.
  A view with no notes shows the list's empty message and tip in place of the columns.
  A board of more than 200 cards renders, in each column, only the cards near the part that shows, as a long list does (`columnWindow`, with `listWindow.ts`), so headlines are read for those cards only.
  The board has its own width (`size.board-default-width`, room for the five columns at their narrowest, dragged from `size.board-min-width` to `size.board-max-width`); in a narrow window it gives way before the editor, and its columns keep `size.board-column-min-width` and scroll sideways, a focused card scrolling into view.
  While a board shows, the editor keeps `size.board-editor-min-width` (380 px, the least at which its toolbar, title and metadata row are not clipped) in place of the usual two panes' width, so at laptop widths the board scrolls rather than the editor being squeezed.
- **Gallery layout** (`src/renderer/src/NoteGallery.tsx`, `gallery.ts`, `galleryPreviews.ts`): the third segment of the layout control (Show as Gallery in the palette, `view.toggleGallery`) shows a view as a grid of cards, each a scaled-down, read-only first page of the note (its title, then the start of its body) with the pin and the time under it.
  It is offered where a board is, and in a status filter and a search within such a view too (the results show as cards); Templates and the Trash have none.
  The choice is kept per view beside the boards' (`ViewLayouts` in `lastState.ts`, a view in one list at most).
  Cards keep the view's order and filters, the selection is the list's (`listSelection.ts`), and the arrow keys move across and down the grid (`galleryStep`); Home, End and Page Up and Down, the note keys, the context menu and dragging work as in the list.
  The grid is virtual: only the rows near the part that shows render (`galleryWindow`).
  A card's page comes from the core worker (`cardPreviews`): the core cuts the body to whole blocks under 1,200 characters, 12 blocks and 40 lines (`cardExcerpt`, which reads at most 4,800 characters of the note), and renders them with the preview's parser and sanitizer and only the light built-in renderers (`renderCardPreview`); diagrams, math, frames and images from the web become a labelled placeholder, and code is not highlighted.
  Pages are cached in the window by note ID and `bodyVersion` (the last 500) and read only for the cards that render.
  The gallery shares the board's pane width (`BOARD_PANE`) and its editor minimum.
  The phone has no gallery.
- **Restoring the last state** (`src/renderer/src/lastState.ts`): a window opens where it was left.
  It restores the library view (All Notes, a notebook or Templates) with its filter, the library views shown as a board (see Board layout; at most the 100 switched last), the view mode (write, edit, split or preview; a window that kept none opens in the install's default, see Write mode), the open note, the note's selection, and its scroll position: in edit and split mode the editor's, kept as the line at the top and an offset into it so it finds the same line at another width or font size (in split mode only the editor's: the editor leads), in preview mode the preview's (applied again while images and diagrams load, until it is reached or the user scrolls); an editor restored hidden in preview mode goes to its place when it shows.
  The editor takes the keyboard again if it had it, but only while the keyboard is nobody's: a search typed or focus put anywhere since launch (`keyboardIsFree` in `focus.ts`), checked when the restore starts and again when the editor has loaded, keeps the keyboard where the user put it.
  Like focus mode it is a view preference of one window: a JSON value in the webview's local storage (`devot.lastState.<window label>`, versioned; a window File > New Window opened keeps it in session storage instead, see Several main windows), never in the database and never synced; every part is checked when read and a part that is not valid falls back on its own.
  What is gone since is skipped quietly: a notebook shows All Notes, a filter on a deleted tag shows no filter, and a note deleted, in the Trash or purged leaves the view with no note open.
  The Trash and search results are not restored: while the Trash shows, the state from before it is kept, and a search leaves the view under it.
  It is saved at once when the view, filter, note or mode changes, 400 ms after the selection or a scroll position stops changing (never per keystroke; the editor measures its top line only when it scrolls, and moves it with edits made above it), and when the page goes away or out of sight and at the start of the quit handshake.
  Nothing is saved until the window has restored, so a window that is still loading never overwrites it, and a view or note picked while it loads is kept rather than replaced.
  The restored note opens like any other, as the first entry of Back and Forward's trail.
- **Keyboard navigation** (`src/core/navigation.ts`, `src/renderer/src/areas.ts`, `src/renderer/src/Sidebar.tsx`):
  - **Back and Forward:** each window keeps the trail of notes it opened (up to 100, in memory): opening a note from anywhere (the list, the palette, a link, Next or Previous) drops the entries ahead and adds it; Cmd+[ and Cmd+], and the Back and Forward buttons (SF Symbols `arrow.left` and `arrow.right`) after the focus mode button at the start of the editor's toolbar, move along it.
    They skip notes deleted since and the open note itself, and are disabled (the keys do nothing, the palette does not offer them) with nowhere to go.
    Notes opened in the Trash are not entries; Back from the Trash leaves it for the last note opened.
    Each press steps on at once, so quick presses each go one note further.
    A key pressed in the editor leaves the keyboard in the editor of the note it opens.
  - **Next and Previous:** Shift+Cmd+] and Shift+Cmd+[ open the note after or before the open one in the list shown (pinned section first; search results; the Trash's list), from anywhere; with no note open, the first or last.
    They stop at the ends.
    A list row with the keyboard follows; from the editor the new note's editor takes the keyboard.
  - **Window keys over the editor's:** the window's keys are window-wide, so CodeMirror's own bindings for them are left out of the editor (Cmd+[ and Cmd+] indent and outdent, Cmd+/ toggle comment, and the search keys that find takes; `editor/settings.ts` drops every built-in binding a `window` command takes, but an arrow key, which moves the caret in text).
    In the editor Tab and Shift+Tab indent and outdent (a table's Tab and Shift+Tab come first and move between cells).
    A held window key runs its command once, and its repeats are stopped, so they reach no native menu item either.
  - **Areas:** Tab and Shift+Tab on a sidebar row or in the note list (`panes` scope) move the keyboard to the next or previous area: sidebar, list, editor, and round again, skipping one that is hidden or has nothing to focus.
    The sidebar's area is its tab stop row; the list's its open note's (or first) row, else the list itself; the editor's the note's text, else the rendered note (Preview mode and the Trash: the preview is a scrolling region with `tabIndex=0`, an accessible name and a focus ring for the keyboard, so the arrow keys, Page Up and Page Down, Home and End read a long note), else its title, else the first button of the note.
    Control+Tab and Control+Shift+Tab do the same from anywhere, the editor and its title too (the macOS key for leaving a control that uses Tab itself).
    Escape then Tab (or Shift+Tab) leaves the editor as well: CodeMirror leaves the Tab after Escape alone for two seconds, and it moves on like a pane's.
    As in macOS's own panes, the toolbar buttons are not in this loop: each has a key or a palette command (the list's sort pop-up is Sort Notes… in the palette), and the editor's are still reached with Shift+Tab from the title.
  - **Keeping the keyboard on the page** (`src/renderer/src/focusRescue.ts`): when the element that has the keyboard is removed, hidden or disabled (a row deleted, a button that goes away with its action, Focus Mode hiding an area, a sheet that closes), the web view drops focus on `<body>` and keys stop reaching the window.
    A hook in the window watches for that (focus events and a mutation observer, checked a frame later, so components that move the keyboard themselves go first) and moves the keyboard: on a sidebar row to the same row if it is still there (moved or renamed), else the next row of its kind (notebook, status, tag), the one before it at the end, else any other row; elsewhere to the note list, else the editor area, else the sidebar.
    It leaves alone focus the user moved on purpose (a click on blank space) and any window with a sheet open; a sheet that closes without giving the keyboard back (the hook remembers what had it before the sheet) hands it back.
    The note list keeps its own recovery (next row, open note's row); Backups and Import open in a layout effect on their Done button (so Return dismisses them and never takes a backup) and `close()` on unmount so the keyboard returns to what had it.
    Buttons that turn off while the keyboard is on them (Empty Trash, Clear Usage Data, the Backups buttons while busy) use `aria-disabled` and a guarded handler, not `disabled`, so they keep it; a tag chip's remove button hands the keyboard to the tag field when pressed from the keyboard.
    The note list always keeps a Tab stop: the open note's row, else the first row (the open note may not be listed).
  - **The list:** Return on a row edits the open note's title (caret at its end), Cmd+Return its body (showing the editor in preview mode); with no note open, the row's note opens first.
    Not in the Trash's list.
  - **The sidebar:** it is one tab stop, the row of the view shown (its filter, else its notebook, the Trash or All Notes).
    Up and Down (Home and End) move through every row in order (All Notes, Pinned, the notebooks shown, the statuses, the tags, Templates, the Trash), and the view follows: All Notes or a notebook shows without a filter (a click on one keeps it; the keyboard shows the row it is on), the Trash shows, and a filter row turns its filter on (narrowing the notebook shown, as a click does).
    On a notebook Left closes it (or goes to its parent) and Right opens it (or goes to its first sub-notebook).
  - **Hiding the sidebar:** Cmd+/, View > Hide Sidebar (which reads Show Sidebar while it is hidden; the page relabels it through `sidebar_menu_set`, main window only), or the button in the sidebar's title bar hide it; the button that shows it again sits at the start of the list's toolbar.
    Each window remembers it in local storage (`devot.sidebarHidden.<window label>`, like focus mode).
    In focus mode the sidebar is hidden anyway: Cmd+/ leaves focus mode and shows it.
    Hiding it with the keyboard in it gives the keyboard to the list.
    The key reaches the page first, which runs it and stops it; the menu item runs it only when the page did not (so a picked item or a key the page never saw still works), and the first menu toggle within half a second of the key's is dropped as an echo.
    Shown again from its Show Sidebar button, the sidebar takes the keyboard.
- **Commands and shortcuts** (`src/renderer/src/commands/`): every app command is declared once in the registry (`registry.ts`) with an ID, a catalog label, a group (note, notebook, tag, view, search, find, format, table, image, app), a scope and its default keys.
  Keys use one platform-neutral notation (`keys.ts`): modifiers `Mod` (Command on macOS), `Ctrl`, `Alt`, `Shift`, then a letter, digit, punctuation mark or named key (`Mod+Shift+D`, `Mod+Backspace`, `Enter`); the registry writes them in canonical order, and `keys.ts` turns them into what macOS shows (`⇧⌘D`), native menu accelerators (`Shift+CmdOrCtrl+D`) and CodeMirror key names.
  A key press matches by the character it types, as the menu bar matches key equivalents, so Cmd+Q is Q on a French keyboard (where Q is on the A key) and Cmd+Z is Z on a Dvorak one (`pressedKey`); the recorder and the reserved keys read presses the same way.
  A press whose character is not the key's own (Option, or Shift on a digit or punctuation key) is read from the character that physical key was seen to type (`rememberKey`, fed by every key press of a window), else from its US position; the page cannot ask the system for the layout, so a layout map from `UCKeyTranslate` was not added.
  The keypad matches by its keys, whatever the layout (`=`, `-`, `.`, `/`, `+` as `=`, digits).
  Exactly the modifiers named must be held; auto-repeat never runs a command.
  A scope says where a command's keys work, and scopes nest: `window` (anywhere, also in the editor) holds `editor` and `outsideEditor`; `outsideEditor` holds `panes` (the sidebar's rows and the note list, not toolbars or fields); `panes` holds `sidebar` (a sidebar row, which holds `notebookRow` and `tagRow`) and `list` (any note list); `list` holds `noteList` (the library's or search results' list) and `trashList` (the Trash's).
  Two commands may share a key only where their scopes never overlap, that is unless one scope lies within the other (so Cmd+Delete is Move to Trash in `noteList` and Delete Permanently in `trashList`, and Delete deletes a notebook or a tag by the row it is on); a unit test checks the whole registry, and keys macOS keeps (Cmd+Q, Cmd+H, Cmd+M, Cmd+W, Cmd+Comma, ...) are refused.
  Window keys are dispatched by `useWindowCommands` (none while a sheet is open, none that the list or editor already handled); the note list, the Trash's list, notebook rows and tag rows match their own keys through the registry (`noteShortcut`, `trashShortcut`, `bookShortcut`, `tagShortcut`, `commandMatches`), including `/` in a list (search the view it shows); no key is handled outside it; a held key with Command or Control that is a command's key does nothing after its first press and is stopped (`heldCommandKey`) in the list and the sidebar's rows, as in `useWindowCommands`, so it never repeats into the Edit menu (Select All, Copy); the context menus (note, notebook, tag, and the toolbar's Alert pop-up) take their labels and accelerators from it; the editor's format, table, Paste as Plain Text and New Note from Selection keymaps and its F3 find keys are generated from it; find (`findShortcut`) and the status keys read it too.
  The window binds a handler to each command it can run at the moment (a note, status or find command only while a note is open, a format or alert only while the editor shows), and only those are offered.
  Native menu items that run a command (View > Revision History…, Command Palette…, Hide Sidebar and Synced Scrolling, and Devot > Backups…) are built in Rust with the command's default key (`tests/policy/native-menu-keys.test.ts` checks each against the registry and keeps the menu's own keys, Quit and Settings, clear of every command) and get the keys in effect from the main window (`command_menu_set`, below).
  Rust sends such an item's event to the main window whichever window has the keyboard, so the main window ignores it while it does not (`document.hasFocus()` is false: Settings or a native panel is the window the user is in): Cmd+K in Settings opens nothing behind it.
  The editor's own keymaps (format, table, find) are matched by CodeMirror, which reads the character like the menu bar for letters and falls back to US key positions with Option or Shift.
  The Format menu takes its keys from the registry at run time (below).
  Every reader takes a command's keys through `commandKeys`: the registry'sdefaults with the user's changes (see Keyboard shortcuts).

- **Format menu** (`src-tauri/src/format_menu.rs`, `src/renderer/src/commands/formatMenu.ts`): the menu bar has a Format menu between Edit and View with every format command: the inline formats (Bold, Italic, Strikethrough, Highlight, Inline Code, Link), a Heading submenu (1 to 6), the block formats (Code Block, Bulleted, Numbered and Task List, Quote), an Alert submenu (Note to Caution) and Horizontal Rule.
  It exists for the keys: in the app Command-I reached neither the page nor the menu bar.
  AppKit offers a key equivalent to the key window's views before the menu bar, and the web view took Command-I without passing it on.
  So on macOS a local key-down monitor (`native::macos::give_format_menu_keys_priority`, installed with the main window) runs before both: a key with Command or Control in the main window, while it is the key window, is offered to the Format menu alone (`performKeyEquivalent:` on the menu bar's Format submenu, found by its title on every key, since muda keeps a separate NSMenu per attachment), and a key the menu takes is dropped, so the web view and the other menus never see it; every other key goes its usual way.
  While an input method composes in the window (its first responder, the web view, has marked text: `hasMarkedText`, asked only for keys with Command or Control) no key is offered: the web view hands it to the input method first, which may use Control keys, and a format would end the composition (see Input methods).
  The decision is a pure function (`native::offers_to_format_menu`, unit-tested); the AppKit part is checked on a throwaway menu bar, and the marked text on an offscreen window (a text view, and that the web view answers the same question), by the main-thread test (`tests/main_thread.rs`).
  Debug builds log `I_FORMAT_KEY_MENU` each time the menu takes a key, and `I_FORMAT_KEY_SEEN` for every key with Command or Control: the outcome (`TAKEN`; `REFUSED`, the menu said no; `NOT_OFFERED`, the window check failed or an input method composes; `NO_MENU`), the event's window and the key window (0 none, 1 main, 2 other), whether the main window has marked text, the modifier bits, the key code, auto-repeat and whether a menu item has that key (0 none, 1 enabled, 2 disabled).
  `format_menu_set` runs one call at a time and takes a turn-off only from the main window that turned the menu on (or once that window is gone), since the blur of the window left can land after the focus of the window entered.
  It takes every key off the menu (natively, on the main thread) before it sets the planned ones: the menu library cannot remove an accelerator (setting none keeps the old one), and AppKit lets a disabled item with a key take that key without running it, so a greyed-out Format menu would otherwise swallow Option+Cmd+K outside the editor.
  Rust holds the items (labels from `strings.rs`) but no keys: while the editor has the keyboard the UI sends the registry's keys for them (`format_menu_set`, which accepts only format commands and accelerators with Command or Control that none of the menu bar's own items has, `MENU_BAR_KEYS`) and the items are enabled; when the keyboard is anywhere else, or another window (Settings) is the key window, it takes the keys away and the items are greyed out, so a format key never shadows what that key does elsewhere (Shift+Cmd+C copies a note's URI on a note list row).
  Keys the user changed (Settings > Keyboard Shortcuts) reach the menu through the same call, at once.
  A picked item, by mouse or key, sends `devot://format` with the command ID to the main window, which runs it only when it is a format command and the editor has the keyboard; while an input method composes in the editor the format does nothing (`formatCommand`).
  A format runs once per key press: when the menu has the key, the page never sees it (the monitor drops it); when the page sees it, the editor's keymap (kept for Linux CI, which has no monitor, and in case the menu does not match a key) runs the format and stops the key; and should the same key reach the menu as well, its event is dropped once as an echo when the keymap ran that format within the last half second.
  Like any menu key equivalent, a held format key repeats.
  A format's key is offered only where the format does something: the editor reports the formats that would do nothing at the caret after a pause of 150 ms (`inertFormats`, `editor/formatKeys.ts`; every inline format in code, Strikethrough on an empty line start; nothing is reported for a selection over 5000 characters or while the parser has not reached it), and `format_menu_set` is sent without their keys, so the key reaches the editor's other bindings (Cmd+I selects the parent syntax in code).
  The policy test checks that the menu lists exactly the registry's format commands, with the app's labels and no keys of its own, and that the registry's format keys are ones `format_menu_set` accepts: each has Command or Control and none is in `MENU_BAR_KEYS`, and they equal `src-tauri/tests/fixtures/format-menu-keys.json`, the key map Rust's tests run through the same checks (a refused map would leave the menu without keys and Cmd+I lost again).
- **Keyboard shortcuts** (Settings > Keyboard Shortcuts; `src/renderer/src/commands/keymap.ts`, `shortcutSettings.ts`, `src/renderer/src/settings/KeyboardSection.tsx`, `src-tauri/src/keyboard_shortcuts.rs`): every registry command can take other keys or none.
  - **Model:** the user's changes are a map from command ID to that command's whole list of keys (an empty list: no key; at most four), layered over the registry's defaults; a command not in the map has its defaults.
    `effectiveKeymap` merges the two in one place and hands the result to the registry (`setCommandKeys`), so the window's keys, the note list, Trash, notebook and tag row keys, find and status keys, the editor's keymaps, the Format menu, the View menu's command items, context menu accelerators, the palette's key hints, button tooltips (`commands/titles.ts`) and the font size hint all read the keys in effect.
    A key a command may not take, or an unknown command, in the stored map is ignored.
    If the stored map still holds a clash (edited by hand, or a later default), a key the user set wins over a default, and between two the user set the command declared first keeps it.
  - **What a command may take** (`keyProblem`): a key in the registry's notation, never one of `RESERVED_KEYS` (Cmd+Q, Cmd+H, Option+Cmd+H, Cmd+M, Cmd+W, Cmd+Comma, Cmd+Tab, Cmd+Space, Control+Cmd+F, Control+Cmd+Space, Control+Cmd+Q, Control+Cmd+D) nor Escape (it closes and cancels everywhere), nor an arrow key, Home, End, Page Up or Page Down (the lists, the sidebar and text move on them whatever the modifiers).
    In the `window`, `outsideEditor`, `editor` and `panes` scopes, where text is typed (the panes' Tab also leaves the editor's text after Escape), a key needs Command or Control (a key without them types text) and may not be an Edit menu key (Undo, Redo, Cut, Copy, Paste, Select All).
    On list and sidebar rows (the scopes within `panes`) any other key goes, as the defaults there use M, P, Delete and Cmd+C.
    A command's own default keys stay allowed (the table keys Tab, Return and Option+Up, F3).
    A stored list none of whose keys a command may take is ignored (the command keeps its defaults); an empty list means no key.
  - **Clashes:** a key another command has where both apply (their scopes overlap, as the registry's clash test defines) is shown with that command's name, and taken from it only when the user agrees (Reassign); Reset does the same when a default key now belongs to another command.
    Recording replaces the command's keys with the one recorded (Reset brings back a second default key).
  - **Pane:** a card per command group (App, Notes, Notebooks, Tags, View, Search, Find, Edit, Format, Tables, Images; `GROUP_ORDER`), each row the command's name (and where it works) with its keys in a field at the right, under a filter field that matches names, group names and keys (as shown, as written, or typed with cmd, ctrl, opt, alt and shift: `cmd+k` finds the commands bound to Mod+K alone; `shortcutSearch.ts`).
    Left of the field, Reset shows while the command is changed, Copy and Clear while the row is under the pointer or has the keyboard; Reset All Shortcuts… is in the toolbar's More menu (an in-page menu: arrow keys, Home and End move, Escape closes).
  - **Recorder:** each command's shortcut is a button named "<command> shortcut: <keys>".
    Pressed, it captures the next key combination, read as the character the key types (`shortcutOfPress`, as `keyMatches` reads it): modifiers alone wait for a key, keys an input method is composing are left to it, Escape cancels, and leaving the button cancels; Backspace and Delete are recorded like any key (some row commands use them), so removing a key is the row's Clear button.
    Reset gives a command its defaults back; Reset All Shortcuts… asks first.
    Clear, Reset and Reset All use `aria-disabled` rather than `disabled` when there is nothing to do, so the one just pressed from the keyboard keeps the focus.
    A unit test (`commands/bindings.test.ts`) checks that every command the page lists runs from a key set for it.
    What happened (the new keys, a refusal and why, a cancel) is announced through a live region, and a refusal also shows under the row.
  - **Store:** a local preference like the editor settings: Rust keeps the changes in `<app data>/keyboard-shortcuts.json` (outside the database: never synced, never in backups), written through a temporary file and a rename.
    `keyboard_shortcuts_get` is granted to the main, note and Settings windows, `keyboard_shortcuts_set` (a patch: new keys, or null for the defaults) to the Settings window only.
    Rust checks command IDs (dotted camelCase words), the notation in canonical order, the reserved keys and Escape, four keys at most, each once, 256 commands at most, and refuses a bad patch as a whole; reading the file drops only a bad entry.
    A file that cannot be read is never written over, as with the editor settings: the defaults apply, a change is refused with `E_KEYBOARD_SHORTCUTS_READ_FAILED` until a read works again, and a damaged file is copied to `keyboard-shortcuts.json.damaged` before the next change replaces it.
    What only the registry knows (which commands exist, scopes, clashes) the UI checks.
    After each change Rust sends `devot://keyboard-shortcuts-changed` with all changes and a revision to every window (re-sent in the page as `devot:keyboard-shortcuts-changed`), which applies the newest revision.
    The page side shares its revision and in-flight handling with the editor settings (`src/renderer/src/syncedStore.ts`), and the atomic write with them in Rust (`atomic_file.rs`).
  - **Live everywhere:** the editor's registry keymaps (format, table, find, Paste as Plain Text, New Note from Selection, and CodeMirror's own bindings less every key a window command has and every key the user gave an editor command, compared as key presses however CodeMirror spells them, `codeMirrorKey`; an editor command's default keys, such as Tab in a table, fall through to CodeMirror's binding where the command does not apply) sit in compartments (`editor/registryKeys.ts`) and are rebuilt in the open editor in one transaction; context menus are built again on their next use; the Format menu gets its keys again; and the main window sends the View menu's command items their keys through `command_menu_set` (in one queue with `format_menu_set`, the command items first, so a key moved between the two menus is never on both; a failed call is sent again when the window comes to the front) (main window only; command ID to accelerator or null; Rust accepts only those three commands and accelerators with Command or Control that the menu bar's own items do not have, takes every key off them natively, `native::macos::clear_item_key_equivalents`, since the menu library cannot remove one, and sets the planned ones).
- **Window shortcuts:** Cmd+N New Note (in the Trash it opens All Notes first and creates the note there; in Templates it makes a template), Cmd+T New Note from Template, Shift+Cmd+F and Shift+Opt+Cmd+F search, Shift+Cmd+D focus mode, Opt+Cmd+Y Revision History, Cmd+K the command palette, Cmd+P split view, Cmd+F and the other find keys, Control+Command+1 to 5 the note status, Cmd+= (also Shift+Cmd+=) and Cmd+- the editor's font size and Cmd+0 its default size, Cmd+[ and Cmd+] (also Cmd+Left and Cmd+Right while no text field has the focus) Back and Forward, the editor too, Shift+Cmd+] and Shift+Cmd+[ the next and previous note, Cmd+/ the sidebar, Control+Tab and Control+Shift+Tab the next and previous area (see Keyboard navigation).
  Shift+Cmd+P prints the open note.
- **Editor line keys** (`src/renderer/src/editor/lineCommands.ts`, the `edit.*` commands): Shift+Return starts a plain line, Cmd+Return a blank line below (caret moves to it), Shift+Cmd+Return one above, Cmd+D deletes the line, Cmd+L selects it, Option+Up and Option+Down move it, Shift+Option+Up and Shift+Option+Down copy it, Tab and Shift+Tab indent and outdent (Indent and Outdent have no keys of their own, so Cmd+[ and Cmd+] stay Back and Forward), Control+Shift+O opens the link or note link under the caret, F5 and Shift+F5 sort the selected lines ignoring case (Control+F5 and Control+Shift+F5 case-sensitively), Control+J joins lines.
  Return on an empty quote line continues the quote; Shift+Return or Backspace on the empty `> ` leaves it.
  A backtick typed over a selection wraps it in backticks.
  In a table the alignment keys are Option+Cmd+Left, Right, Up and Down (left, right, centre, none) and a row moves on Shift+Option+Cmd+Up and Down (Shift+Option+Up and Down copy the line, so the row keys add Cmd and no other command shares them).
  Full screen is the system's Control+Cmd+F.
  The keys are registry commands, so the Keyboard settings table lists them and a stored override keeps working when a default changes.
- **Input methods** (`src/renderer/src/ime.ts`): the keys an input method composes with (pinyin, kana, dead keys) are its own, so the Return that picks a candidate never also submits a field or starts a line, and the Escape that cancels a composition never also closes or clears anything.
  `isImeKey` tells them apart as WebKit sends them: during a composition (`isComposing`); with key code 229 when the input method took the key (the Return or Escape that ends a composition arrives after `compositionend`, with `isComposing` false); and as the first key down within 100 ms after `compositionend`, whatever its code (`watchCompositions`, started in each window before any key handler).
  Every key handler asks it first: the window shortcuts (`useWindowCommands`), the find keys and the find bar's Escape, the panes' Tab, and the Return, Escape and arrow keys of every field (Move to Notebook, the find bar, the tag field, renaming a notebook or tag, the search field, the template and tag pickers, the palette, the shortcut recorder).
  In the editor (`editor/imeKeys.ts`) keys typed into a composition stop before the editor's handlers but are never prevented, so keys the input method passes on (Command-Q, Command-V) still reach the menu bar; the key that ended a composition stops ahead of every keymap once CodeMirror has seen it (CodeMirror itself ignores it only for a moment after the composition ends).
  Nothing changes the editor's text while it composes: a format (from the Format menu, the toolbar or a key) does nothing then (`formatCommand`), and the Format menu's key monitor offers no key while the web view has marked text (see Format menu).
- **Command palette** (`src/renderer/src/palette/`): Cmd+K anywhere, the editor too (Link is Option+Cmd+K), or View > Command Palette….
  One field finds commands, notebooks, tags and notes by fuzzy match (`src/core/fuzzy.ts`: the query's letters in order, case, accents and spaces ignored, word starts and runs scoring higher).
  Results are grouped by kind, each group best match first and the group with the best match first (ties keep the order commands, notebooks, tags, notes); matched letters are bold, commands show their key.
  With nothing typed it lists every command it can run and the first five notebooks, tags and recently edited notes; a query shows up to 20 of each kind (50 commands).
  Return runs a command, opens a notebook (as clicking it in the sidebar), filters by a tag, or opens a note (leaving the Trash; the open note stays as it is).
  In the Trash the commands include Restore from Trash and Delete Permanently for the open note, and Empty Trash whenever the Trash has notes; notebook and tag row commands act on a row and are not listed.
  Option+Return (or Option-click) is the second action: move the open note to that notebook, or add that tag to it; it is offered only when it would change something, and a line under the results names both actions for the selected result.
  Arrow keys move, Escape or a click outside closes; keys that end an input method's composition are left to it.
  Closing gives the keyboard back where it was (into the editor with its selection), then runs the picked action.
  Once the action has finished (it may wait on the worker: opening a note, Move to Trash, Duplicate) and the window has rendered, if the place that had the keyboard is gone or hidden (Show Preview, focus mode, a replaced editor), the open note's row (or the list's first row), its editor, its title, or else a toolbar button takes it.
  A note an action opens while the palette came from the editor takes the keyboard into its own editor once it has loaded.
  The field is a combobox over a listbox of groups (`aria-activedescendant`).
  Notes come from the window's note list in memory, never from a search request.
- 120 Hz: the WebKit 60 fps preference is turned off when the main window is created.
- Icons: the `symbol_png` command renders an SF Symbol through AppKit, or UIKit on iOS (`native/ios.rs`), in black at two pixels a point for the UI to tint.
  UIKit lays the symbol out for a display scale of 1, on whole points as AppKit does: its PNG is then within a pixel of the Mac's in size and in where the symbol sits, 8 bits a channel in sRGB like AppKit's (laid out for the screen's scale, UIKit sizes it in thirds of a point and it sits higher).
  It is an async command whose render runs on a blocking thread, one render at a time (AppKit uses an image on one thread at a time) in an autorelease pool of its own, never on the main thread: Tauri runs a synchronous command there, and at launch the main thread also routes the page's first IPC, which the first paint's 22 icons held up for about 115 ms (80 of them on the first, when AppKit loads the symbols).
  The UI caches results per name, size and appearance, and re-requests them when the appearance changes.
- Share sheet (iPhone): `phone_share` presents UIKit's share sheet (`native/ios.rs`) over the key window's top-most view controller, so it rises from the bottom as every iPhone app's does.
  A page's own share sheet shows in the web view as a clipped popover.
  A popover, as an iPad would show, points at the bottom middle of that controller's view, so the sheet always has a source.
  The command resolves at the share sheet's first answer, a cancel included (a cancel inside another app's share extension dismisses the whole sheet and answers once), and answers `E_SHARE_FAILED` when nothing could be presented.
  It shares the Mac License Key alone (docs/licensing.md, Get a Mac License Key): a message that holds a licence key this build verifies, and that key's `devot://licence?key=` link, checked in Rust.
- Icon placement (`src/renderer/src/icons/symbols.ts`): `boxPoints` chooses the source point size from the role's box.
  `inkBounds` measures actual alpha coverage, and `placeInCanvas` centres that ink in a fixed canvas, preserving its scale unless it exceeds the box.
  Oversized ink is reduced to fit; transparent PNG padding contributes no size and never creates overhang or negative layout margins.
  Masks fill their CSS box.
  The list title has a separate `title` role: a `1.4cap` box fits SF ink to roughly 1–1.3 capital heights and uses the title baseline to centre it on the capitals.
  Lucide's title glyph uses the same text-relative box and a 1.75-unit light stroke.
  The title role also reaches custom notebook symbols; toolbar roles retain their own sizes.
  A disabled button only fades (`opacity.disabled`).
