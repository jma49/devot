# Records are filed under names derived from their IDs, so the store does not learn when they were made

Status: accepted (2026-11-05). Amends ADR 0002 (Records, risk 10) and ADR 0015 (the record mapping, the moved marker, what the iCloud account sees).

Record IDs are UUIDv7, which carry their creation time. The relay saw them as each record's `id`, and iCloud as each `CKRecord`'s name, so the store learned when every note, notebook, tag, saved search and attachment was made. The bodies were sealed; the timing was not.

## Decision

- **Store name.** A record is filed under `r` followed by the base64url of HMAC-SHA256 of its record ID, 44 characters. The key is derived from the vault key (HKDF-SHA256, salt the vault ID, label `devot/sync/record-name-key/v1`), so only the vault's devices can compute a name and nobody can turn one back into an ID. The same name serves both transports: the relay's `id` (at most 64 base64url characters) and the `CKRecord` name (ASCII, never a leading underscore, which the `r` rules out). A name is stable for the record's life, so the store links a record's versions as before; it learns nothing else from it.
- **Where it happens.** Rust names, seals and opens (`src-tauri/src/sync/names.rs`), for the relay client and the CloudKit transport alike. The core keeps working with record IDs; a store name reaches it only as the key it counts skipped records by.
- **The ID stays bound.** The sealed payload is `ID length (u8) || record ID || record plaintext`. Each chunk's additional data keeps ADR 0002's layout with its own label, `devot/sync/record/v2`, and the store name where the record ID was. A pulled record opens under the name it came under; Rust then reads the ID and refuses the record (`E_SYNC_RECORD_ID`) unless that ID's store name is the same name. The core's `decodeRecord` checks the ID in the record's header against it again. A record that does not open is reported to the engine under its store name, which is not secret. Every pulled record also carries its store name (`name`), and the engine counts skipped records by it, so a record that opens on a later pull leaves the count whichever way it was reported before.
- **The moved marker** (ADR 0015) keeps its reserved ID, `00000000-0000-7000-8000-000000000000`, as its name, sealed as before. Its time is 0, so it reveals nothing, and builds that know the marker but not store names still find it there and stop with `E_SYNC_VAULT_MOVED`.
- **Moving to store names is a new epoch.** Rust hands the engine the store's epoch with a mark (`<epoch>+names`). The store's own epoch (the relay's, `meta-<vault ID>` on iCloud) does not change. The first connect on this build sees an epoch it has not stored, so the engine takes its existing path: every record back to version 0, a pull from the start and a full upload, now under store names.
- **Records filed under their IDs are left.** A name that is a UUIDv7 (other than the marker's) is a record from before store names. Rust leaves it on the store and does not hand it on (`I_SYNC_LEGACY_LEFT` with a count, no IDs). Mixing them in would put two version counters on one record, and a newer state could be skipped as a replay. They are not deleted either: the relay has no delete, and they are the only copies a device on an older build can read. Removing them once every device runs this build is follow-up work.

## Consequences

All devices are the owner's for now, and the quirks below are accepted on that basis.

- **A device still on an older build** skips the records under store names, which it reads as records with an invalid ID on a relay (`E_SYNC_RECORD_ID`) and as records that do not open on iCloud (`E_SYNC_CHUNK_AUTH`), and Settings shows its existing line that a change from another device could not be read and that Devot should be updated. It keeps syncing under IDs with other devices on older builds. Updated devices do not see its changes until it updates. Its first connect after the update then uploads its whole library under store names, which merges those changes in. Nothing is lost, since every device holds all its records.
- **Each device uploads everything once** when it updates. On a relay a record costs about 4 rows written (ADR 0002, risk 5), so a large vault may take more than a day per device under the quota cap; on iCloud the upload is subject to CloudKit's rate limits.
- **The store holds the old copies too** until they are removed, roughly doubling what the vault takes there. On a relay, a vault whose attachments take more than half of the 3 GB share can reach `E_SYNC_ATTACHMENTS_FULL` during the upload: notes keep syncing and those attachments wait, as ADR 0003 describes.
- **Going back to an older build** is another epoch change: that device uploads everything again under IDs.
- **A full pull from the start downloads the old copies too**, once per device on the first connect after the update: the store sends them with the rest, and Rust skips them only after their chunks have arrived.
- **What a store sees now:** the number of records, their sizes and kinds, when they are written and which device wrote them. Records made after the move do not show when they were made, with one exception: a backlog upload (the move itself, a first upload, any later epoch) sends records in ID order (`SYNC_PENDING_SQL`, `pushBatches`), and UUIDv7 IDs sort by creation, so each backlog upload gives away the records' creation order, though not their times. Uploading a backlog in another order is #639.
- **Records made before the move stay linkable** by a store that kept its logs: their old copies still name them by ID, and the new copies go up in the same order, each payload exactly 37 bytes longer (the ID's length byte and the 36-character ID), so the store can pair new names with old IDs, and so with their creation times. Removing the old copies does not undo what a store already logged.

## Considered

- **A local table from name to ID.** A new device holds none, so it could not tell which record a pulled name belongs to without the ID inside the sealed payload anyway.
- **Random names.** Every device must file a record under the same name, a device uploading it again after a new epoch included; a random name per record would need a table every device shares.
- **Reading the old copies after the move.** Their version counters are unrelated to the new names', so the engine's replay check could skip a newer state; a new epoch keeps one counter per record.
