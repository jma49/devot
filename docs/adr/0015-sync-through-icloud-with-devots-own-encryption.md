# Sync can go through the owner's iCloud, which stores only records Devot sealed

Status: accepted (2026-11-04). Amends ADR 0004 and ADR 0008 for vaults on iCloud, and lifts ADR 0011's "no other sync backend (CloudKit included)".

A vault can sync through the private CloudKit database of the owner's Apple ID instead of a relay. Devot's own end-to-end encryption stays: CloudKit stores the same sealed records (AES-256-GCM under the vault key, chunks of at most 1.9 MB, the same additional data), never plaintext, and never the vault key. Devices signed in to the same Apple ID join the vault with no code: the vault key reaches them through the iCloud Keychain. The pairing code (ADR 0008) and the recovery key stay as the way in when that keychain item does not arrive. A vault uses one transport, iCloud or a relay; switching is a new epoch and a full upload, the path a relay move already takes. The self-hosted relay stays, as an advanced option. The App Store release waits for this; the work runs beside the in-app purchase work.

## What the probe settled

A Developer ID signed build against the Production environment (`spikes/cloudkit-transport/` on branch `spike/cloudkit-probe`, 2026-11-02) verified:

- `accountStatus` on a signed-in Mac;
- creating a custom zone in the private database;
- saving a record of sealed-looking bytes;
- compare-and-set: a save with a stale change tag under `.ifServerRecordUnchanged` fails with `serverRecordChanged`, which carries the server's record;
- a delta fetch by `CKServerChangeToken` (`fetchRecordZoneChanges`);
- assets sit outside the 1 MB record limit, `quotaExceeded` is what a full iCloud returns, and nulling an asset field leaves the asset to the server's cleanup;
- 400 items or 2 MB per request without assets (`limitExceeded`).

Not verified, and each a test in the bulk test plan: a first upload of a large vault, a new device's first download, rate limits and their `retryAfterSeconds`, a full iCloud during an upload, signing out during sync, and whether a silent push reaches a closed or sleeping Mac and an iPhone.

## Mapping the relay protocol onto CloudKit

Every vault on iCloud lives in the private database of the container `iCloud.io.github.jma49.devot`, in three custom zones:

- `devot`, one per Apple ID: `current` (type `DevotVault`), the pairing offers (`DevotPairing`), the vault's epoch (`DevotMeta`, named `meta-<vault ID>`) and its device rows (`DevotDevice`, named `device-<vault ID>-<device ID>`, the device ID a random value the device keeps beside its vault);
- `devot-<vault ID>`, one per vault: only `DevotRecord`s, so its change feed carries notes and files and nothing else;
- `devot-clock`, one per Apple ID: one `DevotClock` record per device, for the clock check. No subscription watches it.

| Relay                                                    | CloudKit                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Vault on the relay                                       | Zone `devot-<vault ID>`. The record `current` in zone `devot` names the Apple ID's one vault, saved only if absent, so two first devices at once end with one vault.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Record `(id, version, chunks)`                           | One `CKRecord` per Devot record, type `DevotRecord`, record name the Devot record ID. Fields: `version` (a Devot field, since a change tag is not a counter), `kind`, `chunkCount`, and either `inline` (bytes, a single sealed chunk of at most 700 KB: the 1 MB record limit less the other fields and CloudKit's own overhead) or `chunk0` … `chunk15` (assets of at most 1.9 MB each; 16 chunks is the relay's limit too).                                                                                                                                                                                                                                                                     |
| `push(id, base, chunks)` with compare-and-swap           | `CKModifyRecordsOperation`, save policy `.ifServerRecordUnchanged`, not atomic, so one refused record does not fail the rest of a batch. A client cannot set a record's change tag: the tag the device keeps per record (an opaque string beside its version) is the record's system fields as `encodeSystemFieldsWithCoder:` archives them, base64. A push rebuilds the `CKRecord` from them, sets its fields and saves; a record with no tag yet is created. A saved record's new system fields become its tag. `serverRecordChanged` becomes `rejected` with the server record's `version` and its system fields as the new tag, so the push after the merge saves against the server's record. |
| `seq`, `pull(since)`                                     | `CKFetchRecordZoneChangesOperation` from a `CKServerChangeToken`. The cursor becomes an opaque string (the archived token, base64); on the relay it is the decimal `seq`, so nothing changes there. `changeTokenExpired` restarts the pull from the beginning; versions already seen keep replays out, so this is not a new epoch.                                                                                                                                                                                                                                                                                                                                                                 |
| `changed(seq)`                                           | A `CKRecordZoneSubscription` with silent pushes on `devot` and `devot-<vault ID>`, a hint only. The device also fetches on launch, on wake, when a window comes to the front, after it pushes, and every 5 minutes while it runs, because delivery to a closed or sleeping app is not promised.                                                                                                                                                                                                                                                                                                                                                                                                    |
| `welcome`: time, epoch                                   | Connecting saves this device's `DevotClock` record and reads the server's `modificationDate` back, which is the time for the 5-minute clock check; since no subscription watches `devot-clock`, a connect wakes no other device. The `DevotDevice` row (sealed name and last-seen day) is saved only when the name changes or its last save is a day old. The epoch is a random value in `meta-<vault ID>`, saved only if absent.                                                                                                                                                                                                                                                                  |
| Epoch                                                    | A new epoch, versions back to 0 and a full upload (the existing path) when the vault's zone was made again or the vault changed transport. The device that makes the zone again saves a new epoch in `meta-<vault ID>` under `.ifServerRecordUnchanged`, so two devices doing it at once end with one. A zone that is gone (`zoneNotFound` or `userDeletedZone`) is made again on its own only for a vault that never synced and that `current` names; a device that has synced this vault, or whose vault `current` no longer names, asks first (below).                                                                                                                                          |
| `E_SYNC_QUOTA` until 00:00 UTC; the self-imposed 80% cap | Gone: Apple meters the requests. `requestRateLimited`, `zoneBusy` and `serviceUnavailable` with `retryAfterSeconds` become `paused` until now plus that wait (no daily reset). The client circuit breaker and the push timing stay.                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `E_SYNC_STORAGE_FULL`, the 3 GB attachment share         | `quotaExceeded` is the owner's iCloud storage full: `E_SYNC_ICLOUD_FULL`, a pause with no end time, checked again on launch, on focus and hourly; it lifts when the owner frees or buys iCloud storage. The share of ADR 0003 is a relay rule and does not apply: attachments and notes share the owner's iCloud storage, which Devot does not read. Settings shows what Devot stores there.                                                                                                                                                                                                                                                                                                       |
| Purge tombstones, kept forever                           | Ordinary records whose sealed state says `purged`. Devot never deletes a CloudKit record, because a delete is seen only by a device whose change token is still valid; only Leave This Vault deletes, and it deletes whole zones. A tombstone that replaces an attachment drops its assets, which the server cleans up.                                                                                                                                                                                                                                                                                                                                                                            |
| Batches                                                  | Three caps per modify operation: 200 records, about 1.5 MB of inline bytes (under the verified 2 MB per request without assets), and 16 MB of assets (not verified; measured in #607). A `limitExceeded` halves the batch and tries again. Assets for an upload are written to files in a folder in the app's data folder, not in Caches, which the system may purge while an upload runs; the folder is emptied after each upload and swept on launch. A fetched asset's file URL is temporary, so its bytes are read before the fetch operation ends and are not kept.                                                                                                                           |
| Devices list, Remove                                     | The `DevotDevice` records list the devices, without Remove: an Apple ID decides who is in, and a device signed in to it can always join again. Locking a device out is removing it from the Apple ID; key rotation stays a follow-up (#614).                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Enrollment, device token, relay secret                   | None on iCloud: the Apple ID is the access check and the vault key the read check.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

The engine's compare-and-swap loop, merges, tombstones, replay check, epoch reset, revisions before merges and restore choice (ADR 0013) stay as they are. `CKSyncEngine` is not used: it owns scheduling, batching and conflict handling, which the engine already does, and it is Swift-only.

### Seam changes in the core

`SyncTransport` (`src/core/sync/transport.ts`) already hides the socket and the sealing. It changes in these ways, with the relay's behaviour unchanged:

- The cursor is an opaque string in `PullPage.next`, `Welcome`, `SyncEvent` `changed` and `sync_state.since`. `''` is the start; a stored `'0'` reads as the start. The engine stops reading meaning into it: "has synced before" (ADR 0013's check) becomes its own state, and "the page advanced" becomes "the cursor changed".
- A record carries an opaque `tag` beside its version (on iCloud the archived system fields), stored per record, passed back with the base of a push, and returned with a successful push and with `rejected` (`''` on the relay).
- `push` gains a batched form; the relay transport runs it one record at a time.
- `paused` takes an end time without a daily reset, and the code says which pause it is. `E_SYNC_ICLOUD_FULL` is a pause without an end.
- Pairing moves behind an interface with a relay and an iCloud implementation (`src-tauri/src/sync/pairing.rs`).
- **The moved marker** is an ordinary sealed record of kind `record` under one reserved ID, `00000000-0000-7000-8000-000000000000` (a valid UUIDv7 whose time is 0, so no device ever makes it for a note), whose sealed body names the vault's transport. A device that pulls one naming another transport stops with `E_SYNC_VAULT_MOVED`, so a fleet never splits silently across two transports; Settings offers to follow. The switching device writes it on the transport it leaves, after recording in its sync settings that the move started; a device that quits before it switches finds that record when its engine stops on the marker, and finishes the move itself instead of offering to follow.
  - Not a new kind: the relay refuses any kind but `record` and `file` (`E_SYNC_BAD_MESSAGE`, `relay/src/vault.ts`), so a `vault` kind could not be written to a relay that was not updated, and the devices that most need the marker would never see it. Gating the switch on an updated relay (`E_SYNC_RELAY_OUTDATED`) would make every switch wait on a relay change for no other gain.
  - Older builds read the marker as a record they cannot decode: Rust opens it, since its ID is a valid record ID, the core's `decodeRecord` refuses its body (`E_SYNC_RECORD_INVALID`), and the engine skips it, counts it, and Settings shows its existing line that a change from another device could not be read and that Devot should be updated. They never write it, since no note of theirs has that ID, and they delete or change nothing local.

## Devices on one Apple ID join without a code

- **The handover item.** Beside its own device-only item (ADR 0008, `keychain.rs`, unchanged), a device in an iCloud vault keeps a second keychain item: synchronizable, in the access group `<team ID>.io.github.jma49.devot` that the Mac and the iPhone app share, readable after first unlock, service `io.github.jma49.devot.sync.icloud`. It holds a version, the vault ID, the vault key and the transport. The device-only item stays the device's own copy, so signing out of iCloud or turning keychain sync off never takes the key from a device that has it.
- **Joining.** A device that holds no vault, with iCloud available and sync allowed (licence or trial), reads `current` in zone `devot`. When the handover item names that vault:
  - with an empty library, the device keeps the vault in its device-only item, turns sync on and says so in Settings > Sync and in a notice, with no code and no question;
  - with notes in its library, it asks once, naming how many notes will go into the vault, and joins only on yes; declining leaves sync off and the offer in Settings > Sync. So no note goes into a vault without the owner choosing it, as with a pairing link (ADR 0008), and a library with nothing to merge is not asked about (ADR 0013). The first-launch notes (fixed IDs, ADR 0013) are not counted while they are as seeded, which is a single write whose change time equals its creation time; one the owner has changed counts, since it merges like any note. Rust cannot compare against the seeded text, which depends on the locale and the build, so a library seeded by an older build, which pinned the welcome note in a second write, is asked once.
  - A device that already holds another vault never joins (`E_SYNC_VAULT_EXISTS`, ADR 0008).
- **The handover item names another vault.** When the item names vault A and `current` names vault B, the device takes neither on its own and offers the fallback below for B. A device in vault B that finds the item naming A writes it again with B (#613).
- **Fallback.** When `current` exists and the handover item does not arrive (iCloud Keychain off, or not yet synced), Settings > Sync says the other devices sync through iCloud and offers the two ways in:
  - **a pairing code** from a device in the vault: the same 128-bit secret, text form and derivation as ADR 0008. The offer is a `DevotPairing` record in zone `devot` named by the pairing ID; taking it is a save of its `taken` state under `.ifServerRecordUnchanged`, so only one device takes it; the sealed `expires` and a sweep by the showing device stand in for the relay's alarm, and the subscription stands in for polling. The QR form is `devot://pair?via=icloud&code=<32 characters>`. The offer's format version goes up, to carry the transport;
  - **the recovery key**, which needs no relay address on iCloud. On iCloud it works only for the vault `current` names, or, while there is no `current`, one whose zone is already there, which then claims it. A key for any other vault would start a second copy that never meets the first, so it is refused: `E_SYNC_ICLOUD_OTHER_VAULT` when `current` names another, `E_SYNC_ICLOUD_NO_VAULT` when the vault is not on this Apple ID's iCloud.
- **Leaving the vault.** The Apple ID is the membership, so a device cannot leave an iCloud vault alone. Leave This Vault removes the vault from the Apple ID: the owner confirms by entering the vault's recovery key, and the device deletes zones `devot-<vault ID>`, `devot` and `devot-clock`, then the handover item, then its own device-only item. Notes stay on every device; the other devices find the zone gone and ask first (below). Turning sync off is separate and keeps the vault (#613).
  - The vault's zone goes first, so a device that syncs meanwhile stops on the missing zone rather than on a fresh epoch. `devot` and `devot-clock` go only when `current` names this vault or none, so leaving never takes another vault's `current` and pairings. A key for another vault is refused (`E_SYNC_RECOVERY_OTHER_VAULT`), and so is a leave while the device is signed in to another Apple ID than the vault syncs with (`E_SYNC_ICLOUD_ACCOUNT_CHANGED`), so the zones of an Apple ID the vault never used are never deleted. A vault made here and never connected has no Apple ID kept yet: it is left only when `current` on the Apple ID signed in names it (`E_SYNC_ICLOUD_NO_VAULT` otherwise), and that Apple ID is then kept, so a retry is checked like any other.
  - Sync is off before anything is deleted, and the device-only item goes last: a leave that fails part way keeps the key here, and leaving again ends in the same state. The handover item is removed only if it names this vault.
- **The handover item on another Apple ID.** On `E_SYNC_ICLOUD_ACCOUNT_CHANGED` the device removes a handover item naming its vault, so the vault key does not stay in the iCloud Keychain of the Apple ID now signed in; Move to This Apple ID writes it again. When `current` there names the vault (another device moved it first), or cannot be read, the item is that Apple ID's own and stays. Signing out (`noAccount`) leaves it: that status does not say iCloud Keychain is off, and removing the item there would have devices remove and write it in turn.
- **Another Apple ID.** A device signed in to another Apple ID cannot join: it sees another private database. A pairing link shown on the other Apple ID is refused (`E_SYNC_ICLOUD_OTHER_ACCOUNT`), and the recovery key like any key for a vault `current` does not name (above). Such a fleet syncs through a relay.

This changes ADR 0004 and ADR 0008 for iCloud vaults: the Apple ID, not pairing, says which devices may join, and the iCloud Keychain carries the vault key. Devot still has no account of its own, and nothing about a vault on a relay changes.

**Checked first (#612, 2026-11-05): the Mac can hold the item.** A Developer ID signed and notarized Mac build can add, read, update and delete a synchronizable generic password in the data-protection keychain, in the access group `WMG3HG38DV.io.github.jma49.devot`, readable after first unlock: add, copy, update and delete return 0, and a copy after the delete returns -25300 (`errSecItemNotFound`). The probe was built in CI (run 41984395295, commit cf2fb857 on branch `spike/keychain-probe`) with the Devot App ID and its "Devot Mac Developer ID" profile, not a separate probe App ID; its entitlements are `com.apple.application-identifier`, `com.apple.developer.team-identifier` and `keychain-access-groups`. So the Mac reads and writes the handover item as the iPhone does.

Not answered yet, and checked on the owner's devices with the first build that writes the item (#604): the round trip to an iPhone, how long an item takes to arrive, and what `SecItemAdd` does with iCloud Keychain switched off. On a runner with no Apple ID the add returns 0 and keeps the item locally, marked `sync=1`, so an add alone cannot tell whether the item will reach another device. Joining never waits on it: a device whose item has not arrived offers the fallback.

## Builds without Devot's container

Before anything touches `CKContainer`, which raises an Objective-C exception in a process without the entitlement, Rust checks that the build carries the container: on macOS by reading the entitlement (`SecTaskCopyValueForEntitlement`), on iOS by the container ID that a build with the iCloud entitlements (`DEVOT_ICLOUD=YES`, `docs/releasing.md`) writes into its `Info.plist`, and on both inside `guarded`. A build without it (`.dev`, local, forks, CI) reports `E_SYNC_CLOUDKIT_UNAVAILABLE` and offers only the relay.

## Native code: `objc2-cloud-kit`, not a Swift shim

CloudKit is called through `objc2-cloud-kit` with `block2` completions, inside `src-tauri/src/native/macos.rs` and `src-tauri/src/native/ios.rs`, every `unsafe` block with a `SAFETY` comment and every call inside `guarded`. A safe module beside `client.rs` (`src-tauri/src/sync/cloudkit/`) holds the transport logic once and calls a small set of primitives each native file exposes: account status and user record ID, zones, modify, fetch changes, subscribe, and the handover item. Why not a Swift package, even though the App Store work brings one to iOS for StoreKit:

- Swift cannot catch an Objective-C exception, and the rule asks that every one is caught; `guarded` already does that.
- CloudKit's Objective-C API covers everything this design uses. StoreKit 2 needs Swift; CloudKit does not, since `CKSyncEngine` is not used.
- The Mac build has no Swift today. A shared package would bring a Swift toolchain step (swift-rs) into every Mac `cargo` build and into CI, for one framework.
- Devot's other native code already goes through `objc2`, with the same exception handling and tests.

If the first step of #603 finds a method or block type the bindings lack, that piece goes into a small Swift C-ABI function in the App Store's package, and this section is amended. The primitives repeat in both native files, since `unsafe` is allowed only there; whether a shared file for code compiled on both platforms is allowed is left to the owner.

## Signing and release

- **Mac:** Developer ID with iCloud needs `Contents/embedded.provisionprofile` and entitlements on the main executable: `com.apple.application-identifier`, `com.apple.developer.team-identifier`, `com.apple.developer.icloud-services` (`CloudKit`), `com.apple.developer.icloud-container-identifiers`, `com.apple.developer.icloud-container-environment` (`Production`), `com.apple.developer.aps-environment` and `keychain-access-groups`. `scripts/release/macos-sign.sh` refuses any entitlement today (`E_SIGN_ENTITLEMENTS`); it changes to require exactly the checked-in set on the main executable and still none on any other Mach-O, and to check the profile's team, App ID, entitlements and expiry. `docs/releasing.md` gives the reasons.
- **iPhone:** `devot_iOS.entitlements` gets the same iCloud, push and keychain keys; the App Store profile comes from the same explicit App ID as the in-app purchase work.
- **CI:** a secret with each profile (base64); a release fails when a profile is missing or expires within 30 days.
- **Schema:** the record types are made in the Development environment and deployed to Production before the first release that uses them. Production never creates types on its own; a field added later is deployed the same way, before its release.

## Threats and failures

| Case                                                                                                                          | What happens                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Someone with access to the iCloud account's data, or Apple                                                                    | Sees sealed records only: their count, sizes, kinds (note or file), record IDs (UUIDv7, so creation times), write times and which device record wrote. Never a title, body, name or key. The same as a relay sees (ADR 0002, risk 10). Record names derived from the IDs under a vault-derived key would hide the creation times on both transports, and are a follow-up (#615).                                                                                                                                          |
| Someone who can read the owner's iCloud Keychain                                                                              | Gets the vault key, through the handover item. | Signed out, or iCloud restricted                                                                                              | `accountStatus` is not `available`: sync pauses with `E_SYNC_ICLOUD_SIGNED_OUT` or `E_SYNC_ICLOUD_RESTRICTED`, and local work goes on. The device keeps its vault. `CKAccountChanged` makes it look again.                                                                                                                                                                                                                                                                                                                |
| The Mac or iPhone switches to another Apple ID                                                                                | The device keeps a hash of the CloudKit user record ID. On a mismatch it stops with `E_SYNC_ICLOUD_ACCOUNT_CHANGED` and uploads nothing. Settings offers to move the vault into this Apple ID (a new epoch) or to turn sync off. | Two first devices make a vault at once                                                                                        | `current` is saved only if absent. So one vault wins, and the other device keeps nothing: it joins the winner like any new device, and its notes sync into that vault.                                                                                                                                                               |

## Consequences

- Settings > Sync's first question on a device with no vault becomes iCloud or a relay; the relay is under an advanced choice. A device that finds an iCloud vault joins and skips the question. The relay paths, pairing and recovery stay as ADR 0008 has them.
- ADR 0004 and ADR 0008 hold for vaults on a relay. For vaults on iCloud the Apple ID decides who joins, and the pairing code is the fallback. ADR 0011's "no other sync backend (CloudKit included)" no longer holds; the rest of ADR 0011 stands: iCloud is the owner's own storage, Devot runs nothing and bills nothing for it.
- ADR 0003's 3 GB share applies to relays only.
- Follow-up work, one pull request each: the Mac keychain probe, first (#612), core seam changes (#602), the native CloudKit transport on macOS and iOS (#603), joining through the iCloud Keychain with its fallback (#604), signing, profiles and schema deployment (#605), Settings > Sync on the Mac and the iPhone (#606), the bulk test plan on a throwaway Apple ID (#607), and leaving an iCloud vault (#613). Key rotation (#614) and record names that hide creation times (#615) cover both transports.
